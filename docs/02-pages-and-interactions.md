# 最低页面与交互组件设计

> **文档版本：** v0.2
> **更新日期：** 2026年9月11日

> 本文保留早期目标交互草案。当前实现是 `frontend/app/page.tsx`：进入应用先由身份选择页（`features/care/actor-picker.tsx`）选「就诊人本人 / 家属 / 志愿者」，就诊人走首页、事项、助手、我的四个标签，家属和志愿者进入独立的协同照护端；并没有下文示意的独立工作台/事项路由。协同照护端页面清单见第五节。需求对齐以 [Design.md](../Design.md) 为准：当前版本计划应持续可查看，修改后更新；返回、取消、人工入口需固定可达。打印、朗读等仍属可选扩展，按钮存在不代表功能实现。

## 先区分“页面”和“组件”

成熟项目不会为每个小动作创建一个新页面。这个 Demo 建议页数保持在个位数：身份选择页加下文 3 个正式页面，预约时段、确认、冲突处理等都作为主工作台中的独立组件出现。这样既能展示完整流程，又不会让老年用户频繁跳转。

## 一、至少需要的页面

### 页面 0：身份选择页 `/`

当前实现的第一步不是登录，而是选身份。进入应用先渲染身份选择页（`features/care/actor-picker.tsx`），给出三个选项：

- **就诊人本人**（`ELDER`）：进入就诊人端，即下文页面 1~3 与四标签导航。
- **家属**（`FAMILY`）：进入协同照护端（见第五节）。
- **志愿者**（`VOLUNTEER`）：进入协同照护端（见第五节）。

选完即进入各自界面，不做注册、密码、验证码等与命题无关的功能。演示时可用构建变量钉死身份，省掉手动选择这一步。

### 页面 1：就诊人端首页 `/`（身份选择之后）

当前实现中没有独立的“演示入口页”，全应用只有 `app/page.tsx` 一个路由。选完身份后：

- 选 **本人** → 落到就诊人端四标签壳层，默认停在首页；
- 选 **家属 / 志愿者** → 落到协同照护端（见第五节）。

就诊人端首页（`features/home/home-view.tsx`）当前包含四块：

- **下一次复诊**摘要，以及进入助手、事项、出行等常用入口。
- **提醒**：一次性或可重复的备忘提醒，可在此删除。
- **长期备忘**：每天 / 每周 / 每月重复的备忘，与「提醒」分块展示。
- **健康记录**：老人自己量到的血压、血糖等数值。

首页顶部保留“本系统使用模拟数据，不连接真实医院”的说明。

> **后续规划（尚未实现）**：原设计稿中的“演示模式场景选择（正常办理 / 无号源 / 日程冲突 / 越界问题）”和“当前模拟用户摘要”目前没有对应界面，后端 `DemoController` 也只有 `/health` 一个端点、没有场景重置接口。演示时通过固定演示脚本与模拟数据覆盖这些场景，不依赖页面上的场景切换器。注册、密码找回、验证码等与命题无关的功能不开发。

### 页面 2：复诊助手工作台 `/assistant/:conversationId`

这是项目的核心页面，绝大多数 Demo 都在这里完成。

布局建议：

```text
┌──────────────────────────────────────────────────────────┐
│ 银发复诊助手     模拟环境     返回 / 取消 / 人工帮助     │
├────────────────────────────────┬─────────────────────────┤
│                                │ 办理计划                │
│ 对话区                         │ ① 补齐信息   已完成     │
│                                │ ② 查询号源   进行中     │
│ 用户消息                       │ ③ 检查日程   等待中     │
│ Agent 回复                     │ ④ 规划出行   等待中     │
│ 时段选择 / 异常方案            │ ⑤ 提醒通知   等待中     │
│                                ├─────────────────────────┤
│ [按住说话] [输入消息] [发送]   │ 工具调用过程            │
└────────────────────────────────┴─────────────────────────┘
```

工作台包含的组件：

1. `ChatPanel`：消息列表。
2. `MessageInput`：文字输入。
3. `VoiceInputButton`：模拟语音或真实浏览器语音转写。
4. `PlanPanel`：显示计划步骤及状态。
5. `SlotSelector`：显示可预约时段。
6. `ConflictCard`：显示日程冲突和替代选择。
7. `ConfirmationCard`：关键操作确认。
8. `ToolCallPanel`：展示工具名、参数、结果和耗时。
9. `BoundaryAlert`：医疗越界和紧急情况提示。
10. `HelpActions`：返回、取消、人工帮助。

### 页面 3：办理结果页 `/tasks/:taskId`

目的：办理完成后让用户再次确认最终结果，也用于录屏收尾。

最低内容：

- 办理状态：全部完成、部分完成或已取消。
- 预约时间。
- 医院和科室。
- 材料清单。
- 建议出发时间和交通方式。
- 提醒创建状态。
- 家属通知对象和状态。
- “返回助手”“修改计划”“打印/保存卡片”按钮。

如果时间或能力有限，“打印/保存”可以只做页面按钮和浏览器打印，不必生成复杂文件。

## 二、不是独立页面，但必须设计的关键组件

### 1. 预约时段选择卡片

显示：

- 日期。
- 上午/下午。
- 医生或门诊类型（可以使用模拟名称）。
- 剩余号源状态。
- 选中后的明显反馈。

不要一次展示几十个按钮。每次显示 2 至 4 个推荐时段即可。

### 2. 操作确认卡片

必须显示：

- 即将执行什么操作。
- 医院和科室。
- 日期与时间。
- 是否创建提醒。
- 是否通知家属以及通知谁。
- 操作影响。

代他人办理（家属 / 志愿者）时，确认卡还须列出：

- **服务对象**：本次替哪位长辈办理。这是按下确认前唯一的关口，写错对象等于替错人动了别人的预约和提醒。
- **代约归属**：这份预约记在谁名下、会通知其他照护者。

代他人办理时**不问“通知哪位家属”**：操作者本人就是被通知方，代约本身会通知其他照护者。

按钮使用：

- 主按钮：“确认办理”。
- 次按钮：“返回修改”。

不能使用含义模糊的“好的”“我知道了”。

### 3. 工具调用记录

每条记录显示：

```text
工具：appointment.querySlots
参数：医院、科室、期望日期
状态：调用成功
结果：找到 2 个可预约时段
```

普通用户默认看摘要；录屏时可以展开 JSON 详情，证明不是预设对话。

### 4. 最终事项卡片

这是一个可复用组件，不负责调用 Agent。它只接收后端返回的数据：

```ts
interface TaskCardViewModel {
  taskId: string
  status: 'COMPLETED' | 'PARTIAL' | 'CANCELLED'
  appointmentTime: string
  hospital: string
  department: string
  materials: MaterialItem[]
  departureTime: string
  transportMode: string
  reminderStatus: string
  familyNotificationStatus: string
}
```

`userId` 属于会话上下文，不应成为事项卡片必须知道的参数。

## 三、适老化页面规则

- 主要正文保持清晰大字号，关键日期和状态进一步放大。
- 背景与文字使用高对比配色。
- 一次只突出一个主按钮。
- 一次只询问一个主要问题。
- 不依赖悬停才能看到重要信息。
- 重要结果同时使用文字、图标和状态，不只依赖颜色。
- 始终能找到返回、取消和人工帮助。
- 日期既显示“下周三”，也显示具体年月日。
- 操作成功后明确说明“什么已经完成、什么没有完成”。

## 四、可以后加，但不属于最低页面的功能

- 材料拍照检查：作为材料清单卡片中的“拍照检查”入口，不需要单独开发完整影像系统。
- 语音播报：在 Agent 回复旁增加“朗读”按钮。
- 倒计时提醒：结果卡片显示距离出发时间，不需要后台真实定时推送。

> 注：本节原先“家属端页面：比赛只要求模拟通知，最低版本不需要再开发一套家属 App”一句已过时——家属 / 志愿者现在有独立的协同照护端，见第五节。

## 五、协同照护端页面（家属 / 志愿者）

就诊人端见第一、二节；家属和志愿者共用同一套协同照护端（`frontend/features/care/`），底部导航为 **首页 / 消息 / 助手 / 我的**。已实现的视图：

- `care-home-view`：协同首页，长辈服务入口（帮助预约 / 就诊动态 / 复诊预约 / 长辈信息）、需要关注的动态、我协同的长辈总览。
- `care-elder-picker-view`：一位照护者绑定多位长辈时先选长辈。
- `elder-timeline-view`：某位长辈的就诊动态时间线。
- `care-appointments-view` / `care-appointment-detail-view`：某位长辈的复诊预约卡片与只读详情。
- `care-booking-view`：代长辈预约（新建 / 改期 / 取消）。
- `care-elder-info-view`：长辈资料与联系人（只读）。
- `care-my-elders-view`：我协同的长辈清单。
- `care-inbox-view`：按长辈聚合的协同消息。
- `care-assistant-view`：助手页，接的是与就诊人端**同一个智能体**。
- `care-profile-view` / `care-settings-view`：我的页与设置入口（设置项为后续版本占位）。

协同照护端助手能做的三类事：

1. 查询长辈的复诊安排、材料与就诊动态；
2. 代长辈预约复诊，走确认卡；
3. 给长辈留一条提醒，落进长辈自己的备忘并标明是谁留的。

对应的只读接口：`GET /api/caregivers/{cid}/elders`、`GET /api/caregivers/{cid}/elders/{uid}/timeline`、`GET /api/caregivers/{cid}/notifications`；代约写接口为 `POST /api/caregivers/{cid}/elders/{uid}/book`（另有 `/book/modify`、`/book/accompany`、`/book/cancel`）。会话仍由 `POST /api/agent/conversations?userId=<服务对象>&actorId=<操作者>` 建立：不传 `actorId` 表示本人自办，传了表示代他人办理，后端按 `care_relations` 校验关系，未绑定会返回 400「没有权限查看这位就诊人的信息」。
