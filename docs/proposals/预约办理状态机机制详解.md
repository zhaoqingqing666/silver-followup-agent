## 0. 先正面回答那个问题：项目里到底有没有状态机？

**有，而且不止一个。但「预约办理」这条主流程用的不是课本上那种状态机。**

项目里同时存在三种性质完全不同的"状态"机制，混在一起看就永远看不懂：

| # | 机制 | 在哪 | 性质 |
|---|------|------|------|
| ① | **4 个正交状态层**（枚举字段） | `CS` 的四个字段 | 纯数据，不做转移 |
| ② | **槽位填充漏斗**（主流程） | `FAS#advance`（3039-3099） | 软推进：找第一个空槽问它 |
| ③ | **真正的状态机**（两处） | `FAS#confirm`（1546-1560）、`stopped()` 守卫（1847-1849） | 硬边界：唯一写入路径 + 停机拦截 |

所以标准答案是这样的：

> **预约办理主流程采用「槽位填充（slot filling）」范式，而非状态转移表范式；状态机思想被收敛到"出口"——由确认门禁与停机守卫构成带边界的写入状态机。更准确的完整表述是：软漏斗（可乱序、可回退、可挂起）+ 硬出口（唯一写入路径、凭据一次性）。**

对照着看最清楚：

| | 课本上的状态机 | 本项目的漏斗 |
|---|---|---|
| 驱动方式 | `(状态, 事件) → 新状态` 转移表 | `字段是否为空 → 问它` |
| 代码形态 | `switch/state transition map` | 一长串 `if (x == null)` |
| 加一个字段 | 要改所有涉及它的转移边 | 加一行 `if` |
| 支持乱序输入 | 需额外写合并转移 | 天然支持 |
| 回退 | 要写"从 A 回到 B"的边 | 清空字段，重算即可 |
| 主流程阶段字段 `stage` | 是权威 | **是投影**，给进度展示用 |

## 1. 四层正交状态：各管各的，别混成一个

`CS` 里四个枚举字段（`CS:14-15`、`CS:21-41`、`CS:55-59`）：

| 状态层 | 字段 | 管什么 | 取值 |
|---|---|---|---|
| 会话状态 | `status` | 这段对话还能不能接着用 | `ACTIVE` / `CLOSED` / `EXPIRED` |
| 任务状态 | `taskStatus` | 这次办理走到哪一步了 | `NONE` / `ACTIVE` / `PAUSED` / `AWAITING_CONFIRMATION` / `COMPLETED` / `CANCELLED` |
| 办理阶段 | `stage` | 现在正在问哪一句（展示用） | 21 个，见下 |
| 对话模式 | `dialogueMode` | 这一轮在办事还是在聊天 | `FOLLOWUP_FLOW` / `GENERAL_CHAT` / `SUPPORT` / `SMALL_TALK` |

**为什么必须拆成四层？因为它们本来就是独立的。** 三个真实组合：

1. **"对话已结束，但预约确实办成了"** → `status=CLOSED` + `taskStatus=COMPLETED`。挤进一个变量就表达不出来。
2. **"用户在闲聊，但办理停在『要不要家属陪同』"** → `dialogueMode=GENERAL_CHAT` + `taskStatus=PAUSED` + `needCompanion=null`。这是**正常状态**，不是异常。
3. **"已经约成功了，但提醒没建完"** → `appointmentId != null` + `taskStatus=COMPLETED` + `stage=PARTIAL`。写成"办理失败"就是事实错误。

`stage` 的 21 个值按用途分四段（`CS:35-41`）：

- **漏斗段（8 个）**：`ASK_HOSPITAL` → `ASK_DEPARTMENT` → `ASK_DATE` → `ASK_ALTERNATIVE` → `ASK_COMPANION` → `ASK_TRAVEL` → `ASK_TRANSPORT` → `ASK_NOTIFY`
- **选号段（5 个）**：`SELECT_PERIOD` / `CONFIRM_SLOT` / `SELECT_SLOT` / `NO_SLOT` / `CONFLICT`
- **出口与异常段（5 个）**：`READY_TO_PLAN` / `AWAITING_CONFIRMATION` / `PARTIAL` / `TOOL_ERROR` / `MEMO_TIME`
- **终态段（3 个）**：`COMPLETED` / `CANCELLED` / `EMERGENCY_PAUSED`

## 2. 漏斗：下一句问什么，由"哪个槽空着"决定

### 2.1 心脏长什么样

`FAS#advance`（3039-3099）是一串**按顺序的空值判断**，没有任何转移表：

```java
private AgentTurnResponse advance(ConversationState state, ExtractedFacts facts) {
    if (state.hospital == null)      return askHospital(...);          // 3040
    if (state.department == null)    return askDepartment(...);        // 3041
    if (state.date == null)          return askDate(...);              // 3044
    if (state.selectedSlot == null) {                                  // 3045
        if (state.alternatives.isEmpty()) return querySlots(state);     // 3046
        if (state.requestedTime != null)  return recommendSpecificTime(...);
        if (state.timePreference != null) return recommendPeriod(...);
        return respondWithPlan("请先告诉我想上午还是下午…");              // 3049
    }
    if (state.acceptAlternative == null) { ... }                       // 3051  → ASK_ALTERNATIVE
    if (state.needCompanion == null)     { ... }                       // 3057  → ASK_COMPANION
    if (state.needTravel == null)        { ... }                       // 3063  → ASK_TRAVEL
    if (state.transport == null)         { ... }                       // 3069  → ASK_TRANSPORT
    if (!notifySettled(state))           { ... }                       // 3078  → ASK_NOTIFY / SET_CONTACT
    if (state.materials.isEmpty()) {                                   // 3090
        state.materials = callTool(state, "materials.checklist", ...);  // 只读工具
    }
    state.stage = READY_TO_PLAN;                                       // 3094
    return checkSchedule(state);                                       // 3098
}
```

**读法：从上往下，第一个 `== null` 的就是"这一轮该问的事"。**

### 2.2 三个组成部分，对应你熟悉的三个概念

| 本项目的东西 | 概念名 | 作用 |
|---|---|---|
| `CS` 里的业务字段 | **槽位（slot）** | 医院、科室、日期、号源、陪同、交通、通知… |
| `#advance` | **槽位遍历器** | 找到第一个空槽，去问它 |
| `#ready(state)`（1929-1935） | **终止条件** | 所有必填槽非空 → 放行到确认 |

`ready()` 比 `advance()` 更严——它额外校验**号源与草稿是否自洽**：

```java
return state.hospitalId != null && state.department != null && state.selectedSlot != null
    && state.date != null && state.date.equals(state.selectedSlot.date())
    && state.hospitalId.equals(state.selectedSlot.hospitalId())
    && state.department.equals(state.selectedSlot.department())
    && state.acceptAlternative != null && state.needCompanion != null && state.needTravel != null
    && state.transport != null && notifySettled(state) && !state.materials.isEmpty();
```

这三行"slot 与草稿必须一致"是关键防线：**用户改了日期但号源没跟着重新查时，`ready()` 不成立**，流程不会带着一个过期号源去确认。

### 2.3 为什么槽位必须是 `Boolean` 而不是 `boolean`

`CS:65-68`：`acceptAlternative` / `needCompanion` / `needTravel` / `notifyFamily` 都是包装类型 `Boolean`。

因为 `advance` 判的是 `== null`：

- `null` = **还没问过** → 该问
- `false` = **问过，明确不要** → 跳过
- `true` = 问过，要

如果只有一个原始 `boolean`，`false` 同时表示"不要"和"没问过"，`advance` **永远不知道该不该问这一项**——要么反复骚扰老人，要么悄悄替老人做主。

> 所以"「还不知道」和「明确不需要」必须分开"不是风格偏好，而是这套范式的**结构性前提**。这句话建议直接写进报告。

### 2.4 白拿的两个能力

**能力一：天然支持乱序。** `#applyFacts`（5314-5361）一轮把一句话里所有能认出来的字段全部落进草稿；`advance` 下次调用自动跳过已答的项。老人一句"9月23号去第一人民医院心内科"就能填掉三个槽。经典状态机得从"问医院"状态逐条走边。

**能力二：天然支持"改一项就重算"。** 见第 3 节——失效和回退是**同一个机制的两面**。

### 2.5 `stage` 与字段的分工（报告里值得单独说一句）

`#syncPresentationStage`（1197-1211）的类注释直说了：

```java
/** Stage 只为旧前端进度展示服务，不参与模型模式的意图决定。 */
```

它的实现就是把第 2.1 节那串判断**又写了一遍**，只是写成赋值而非提问——**它是槽位组合的投影函数**。接了主模型之后，`stage` 已退化成给进度条看的字段。

但要精确：**`stage` 没被完全架空，而是形成二分——业务漏斗看字段，异常分支看 `stage`。** 三处仍在真的用它：

1. `#clarificationDraft`（约 2530-2543）：按 `stage` 决定"把哪一问重述一遍"
2. `#keepConflict`（3829）：`if (state.stage != CONFLICT)` 才认保留冲突这个动作
3. `#confirm` 第③道门禁（1554）：`state.stage != AWAITING_CONFIRMATION` 直接拒

## 3. 失效：改一步不用从头来

### 3.1 统一入口 `invalidate`

```java
private void invalidate(ConversationState state) {          // 1921-1927
    state.confirmationId = null;      // 旧确认凭据作废（关键！）
    state.pendingAppointmentIds = List.of();
    state.scheduleChecked = false;    // 日程检查要重做
    state.travelPlan = null;          // 出行方案依赖时间，作废
    if (state.stage == AWAITING_CONFIRMATION) state.stage = READY_TO_PLAN;  // 退出确认卡
}
```

每一个 `SET_*` 动作都会触发它。**它刻意不动业务字段**（医院、科室、日期…）——那些由各入口按自己的"失效半径"处理。

### 3.2 四级失效半径

| 用户改的是 | 清掉 | 保留 | 为什么这么切 | 代码 |
|---|---|---|---|---|
| **某个细节**（陪同/通知/交通） | 确认卡、日程检查结果、出行方案 | 医院、科室、日期、号源 | 细节变了，前面选好的都还作数 | `invalidate` 1921 |
| **日期** | 上面那些 + 号源、日期偏好、材料 | 医院、科室、陪同、交通、通知 | 换一天只影响那天有没有号 | `resetAfterDate` 5363-5374 |
| **科室** | 科室往下几乎全清，连陪同、交通、通知一起清 | 只留医院 | 科室一换，"怎么去""要不要人陪"这些结论可能都不成立 | `resetAfterDepartment` 5395-5414 |
| **医院** | 除医院医疗之外全清，含选医诉求、待确认候选 | 什么都不留 | 医院都换了，等于重来 | `resetAfterHospital` 5376-5393 |
| **重开一次办理** | 全部槽位 + 进度位 + 打断栈 | 无 | 全新一次 | `clearDraft` 5423-5456 |

### 3.3 最妙的一点：失效不指定"回到哪一阶段"

`resetAfterDate` 结尾虽然写了 `state.stage = ASK_DATE`（5373），但**即使不写，流程也一样对**——因为 `advance` 下次一进来就发现 `date == null`，自然去问日期。

也就是说：**不需要写"从 `READY_TO_PLAN` 回到 `ASK_DATE`"这条边**。清空字段 = 回退，这两件事在这套范式里是同一个动作。

### 3.4 还有一条自动失效：`applyFacts` 里

```java
// FAS:5352-5359
if (!Objects.equals(oldHospital, state.hospitalId) || !Objects.equals(oldDepartment, state.department)
        || !Objects.equals(oldDate, state.date)) {
    state.selectedSlot = null;    // 三要素任一变了 → 号源作废
    state.recommendedSlot = null;
    state.alternatives = List.of();
    state.materials = List.of();
    invalidate(state);
}
```

**注意这里是"精准失效"而非"整段清空"**：改医院时 `applyFacts` 只清 `department`（5319-5322），号源由上面这段兜掉；真正的"全清"发生在专门的 `resetAfterHospital` 路由里。所以口径要写准：**失效有两个来源——`invalidate` 统一清凭据类，各 `resetAfter*` 按依赖清业务字段。**

## 4. 出口：唯一写入路径 + 四道门禁

### 4.1 门禁原文（`FAS#confirm` 1546-1560）

```java
public synchronized AgentTurnResponse confirm(String conversationId, boolean approved, String confirmationId) {
    ConversationState state = requireSession(conversationId);
    if (closed(state))              return closedResponse(state);   // ① 会话未结束
    reactivateIfExpired(state);
    if (stopped(state))             return stoppedResponse(state);  // ② 未停机（取消/紧急）
    if (state.stage != AWAITING_CONFIRMATION || confirmationId == null
            || !confirmationId.equals(state.confirmationId)) {      // ③ 阶段 + 凭据匹配
        return respondWithPlan(state, "这份确认已经失效或已办理，请查看当前计划后重新确认。", ...);
    }
    state.confirmationId = null;                                    // ④ 消费掉凭据（单次使用）
    ...
}
```

**四道门禁的性质：**

| 门禁 | 拦什么 | 为什么需要有 |
|---|---|---|
| ① `closed` | 已结束会话里还开着的旧确认卡 | 少了这条，"结束后只读"就是空话——关掉的会话仍能写库。源码注释称之为**所有写入路径里最要紧的一道** |
| ② `stopped` | 取消态、紧急暂停态下的任何提交 | 停机态不接受写入 |
| ③ `stage + confirmationId` | 过期卡、他人卡、重复点 | 凭据绑定的是**"当时那份操作快照"**；状态一变，快照就不再作数 |
| ④ 消费凭据 | 同一次确认被点两次 | 一次性凭据，用完即废 |

### 4.2 写入不是一步，而是"分步执行 + 每步存档"

`1621-1657` 的执行顺序：

1. `appointmentTool.submit` / `reschedule` → 拿到 `appointmentId` → **立刻 `conversations.save`（1626）**
2. `materialReminderDone` 建材料提醒 → `save`
3. `departureReminderDone` 建出发提醒 → `save`
4. `notificationDone` 通知家属 → `save`
5. 初始化材料准备清单 → `stage = COMPLETED`

**这就是"可续执行"的实现基础**：任何一步抛异常，前面成功的步骤都已落库，三个 `*Done` 标志位记着"哪些做过了"。所以重试只会补失败的那几步，**绝不重复预约**。

### 4.3 所有输入路径都收敛到这一个出口

按此顺序（`FAS:429-666`）：

```
文本  ─┐
按钮  ─┼─→ chatInternalBody → dispatchOutcome → （漏斗/规划器）→ buildConfirmation(3866)
图片  ─┘                                                            ↓
                                                    stage=AWAITING_CONFIRMATION + confirmationId
                                                                    ↓
                                              confirm() 四道门禁 ← 确认按钮 / CONFIRM_PENDING(843)
```

图片路径的注释写得很明确（674）：

> 不新开一条绕过确认门禁的旁路。本方法不会触碰 `confirmationId`，也不会调用 `act/confirm`。

## 5. 全局守卫链：每轮消息都要过的关卡

`chatInternalBody`（429-666）是一个**按序的守卫生效链**。顺序本身就是设计，不能随便调：

| # | 守卫 | 代码 | 命中后 |
|---|---|---|---|
| 1 | 会话已结束 | 419 `closed(state)` | `closedResponse`：说清"这里办不了了"，**刻意不落库**（否则一个还开着确认卡的页面每重试一次就多一条"已经结束"） |
| 2 | 过期但回来 | 420 `reactivateIfExpired` | `EXPIRED` → `ACTIVE`（只是显示口径，回来就接着办） |
| 3 | 空输入 | 431 | "我没有听清，请再说一次。" |
| 4 | 关键词安全预检 | **435 仅在 `!modelAvailable()` 时** | 命中 EMERGENCY → `emergency`；命中 MEDICAL_BOUNDARY → `medicalBoundary` |
| 5 | 挂起态专用待答 | 450-478 | `MEMO_TIME`/`MEMO_DAY`/`MEMO_REPEAT_DAY`/`MEMO_EDIT_TIME`/`MEMO_DELETE_CONFIRM`/`RECORD_CONFIRM` 各自分流。**`RECORD_CONFIRM` 解析不出来返回 `null`**，让这句话照常走主链，不把老人卡死在这个问题上 |
| 6 | 逐字念图 | 484 `readVisionAloud` | 只要求照抄的请求**不走模型**（过一手模型可能把规格、文号、日期改写掉） |
| 7 | 模型规划 + 安全评估 | 489-495 | `evaluateModel` / `evaluate`，EMERGENCY → `emergency`，MEDICAL_BOUNDARY → `medicalBoundary` |
| 8 | 回退模式关键词路由 | 498-533 | 备忘、健康记录、周报；紧急词兜底（499） |
| 9 | **停机拦截** | 539 `stopped(state) && !allowedWhenStopped(route)` | `stoppedResponse`：只给"查看事项 / 新建办理" |
| 10 | 待确认候选 → 记忆候选 | 547-552 | 刚问出口的候选优先于长期记忆 |
| 11 | 支线承接 → 挂起判定 → 分流 | 553-666 | 见第 6 节 |

### 5.1 停机白名单（1267-1275）

停机（`CANCELLED` / `EMERGENCY_PAUSED`）期间**只放行只读与求助类路由**：

```java
case DIRECT_ANSWER, EMOTIONAL_SUPPORT, SMALL_TALK, CLARIFY_DISCOMFORT, RESTART_TASK,
     QUERY_CARE_GUIDE, MULTI_READ_TOOLS,
     QUERY_MY_APPOINTMENTS, CANCEL_EXISTING_APPOINTMENT,
     QUERY_TRAVEL_GUIDE, QUERY_LOCATION_GUIDE -> true;
default -> false;
```

**注意注释里的理由（446-449）**：停机出口不能提前无条件 `return`，否则紧急暂停期间老人问"到医院怎么走"只会听到"旧操作不会继续执行"，**反倒把 120 求助信息盖掉了**。所以判断按"本轮落在哪条路由"来。

## 6. 异常处理机制（老师重点要问的部分）

异常在这套系统里有明确分层：**安全级 > 会话语义级 > 业务级 > 交互级**。下面逐类给"触发 → 代码 → 反应 → 理由"。

### 6.1 会话级异常

| 情况 | 反应 | 理由 | 代码 |
|---|---|---|---|
| 会话被结束（`CLOSED`） | 只读；确认一律拒 | 结束即快照失效 | 419 / 1551 |
| 太久没说话（`EXPIRED`） | 不惩罚，回来说话即恢复 | 不因为离开一会儿就要求老人重说一遍 | 1878-1880 |
| 空输入 | 重问一次 | — | 431 |

### 6.2 安全级异常：紧急 vs 医疗越界（★ 处置方向相反，且都是故意的）

**这是整套异常处理里最容易被评委追问、也最值得单独成节的设计。**

| | 紧急（`emergency` 1888-1897） | 医疗越界（`medicalBoundary` 1227-1239） |
|---|---|---|
| 触发 | 模型/预检判 EMERGENCY；或老人点"真紧急，需要帮助" | 模型/预检判 MEDICAL_BOUNDARY（诊断、病因、看检查单、调药） |
| `confirmationId` | **清空**（1889） | **保留**（刻意不清） |
| `taskStatus` | `ACTIVE` → `PAUSED`（1890-1892） | 不动 |
| `stage` | **强制 `EMERGENCY_PAUSED`**（1893） | **不动**（注释 1224：刻意不动 stage） |
| 旧确认卡 | 作废 | **原样交回**（`pendingConfirmation(state)` 1238） |
| 协同通知 | `notifyArranger("emergency", …)` 通知安排者 | 无 |
| 恢复方式 | 必须显式点「新建办理」 | 直接接着办，什么都不用重做 |
| 落地话术 | "普通办理已暂停…旧操作不会继续执行。" | "…您的复诊办理没有中断，接着往下办就行。" |

**为什么方向相反？** 因为语义不同：

- **紧急**意味着"当下有更重要的生命安全问题，办理必须先冻住"——所以**必须**清凭据、冻结任务。
- **越界**只是"这句话我不该答"，**不等于老人想中断办理**。他手里那张确认卡是有效的，如果因为问了一句用药就把它清掉，他会以为办不成了。注释原文（1234-1235）：

  > 越界回答不能把等着按的确认卡挤掉：老人问到一半药，正要按的「确认办理」若跟着消失，他会以为办不成，而服务端那张卡其实一直是有效的。

- 越界还要给前端一个**提示块**（`Notice(MEDICAL_BOUNDARY)`，1237）。理由（1221-1222）：**视觉上必须和普通聊天不一样，否则评审看不出它是"服务边界的拒绝"，以为只是助手随口回了一句。**

**一个必须知道的口径差异：** 关键词预检 `safetyGuard.precheck` **只在模型不可用（回退模式）时执行**（435）。越界那侧还有一条 `looksLikeMedicalAdvice` 规则兜底，**紧急这侧没有关键词兜底**——`containsAny(value, "胸痛", …)` 也在 `!modelAvailable()` 分支内（499）。这个差距已记录在 `docs/13-demo-scenarios-workflow.md` §7.1，建议在报告里主动写明。

### 6.4 业务冲突异常：日程冲突 与 重复预约

**日程冲突（`checkSchedule` 3812-3826）**

```java
if (!ready(state)) return advance(state, ExtractedFacts.empty());
if (state.conflictKept && !state.conflicts.isEmpty()) return checkDuplicate(state);  // 3819 短路
List<Conflict> conflicts = slotConflicts(state);
if (!conflicts.isEmpty()) return conflictReply(state, conflicts);
state.conflicts = List.of();        // 3823 通过了就清掉旧冲突
state.scheduleChecked = true;
return checkDuplicate(state);
```

- **提示时机**：冲突在**号源锁定的那一刻**就提示，不是等陪同、交通、通知全答完才说。理由（3814-3816）：那样"前面的答案全白答"。
- **`conflictKept` 标记（`CS:96`）**：用户明确"仍保留这个时间"后要记住。**没有这个标记，老人答完陪同/出行/通知后会被同一个冲突拦第二次，永远到不了确认卡。**
- **为什么它刻意不放进 `invalidate`**（`CS:93` 注释）：答"需要陪同"这类问题**不该作废"保留时间"这个决定**，而 `invalidate` 会被每一个 `SET_*` 触发。所以判据只认 `conflictKept`，**不能拿 `scheduleChecked` 当判据**——它每个 `SET_*` 都被清。
- **`keepConflict`（3828-3841）要求 `stage == CONFLICT`**，否则回一句"当前没有需要保留的冲突时间"。

**重复预约（`checkDuplicate` 3858-3864）**

口径是 **同一位就诊人 + 同一天 + 同一个时刻**，**不再比医院和科室**。理由（3846-3851）：老人只有一个身子，同一时刻不可能同时坐在两个科室里；原条件带医院科室，等于只在"同科室重复约"时才拦得住。同一天**换时段仍然放行**——一天看两个科室是正常需求。

改期（`originalAppointmentId != null`）时把原来那条自己排除掉，否则"原时间不动、只换医生"会被自己拦下。

### 6.5 执行级异常：`toolError` 三分类（1827-1845）

确认放行之后，执行中任何一步抛异常都会落到这里。**分类依据是"有没有 `appointmentId`"，因为那决定了"预约到底成没成"。**

| 分类 | 判据 | 状态设定 | 话术 | 为什么 |
|---|---|---|---|---|
| 取消未完成 | `pendingAction == CANCEL` 且有 `appointmentId` | `pendingAction=CREATE`；`stage=COMPLETED` | "取消未完成，原预约保留：…" | 取消失败等于没动，原预约还在 |
| **`PARTIAL`** | 有 `appointmentId`（预约已成功） | `stage=PARTIAL`；`taskStatus=COMPLETED` | "预约已保留，后续事项未全部完成：…。可补办未完成事项，**不会重复预约**。" | **绝不写成"办理失败"**——预约确实办成了 |
| `TOOL_ERROR` | 无 `appointmentId` | `stage=TOOL_ERROR`；`taskStatus=ACTIVE` | "本步骤未完成：…。已保留信息，请重试或修改。" | 草稿还在，可重试/改期 |

三者都先 `state.confirmationId = null`（1828），并记一条 trace（1829）。

### 6.6 交互级异常：老人答非所问 / 走神 / 情绪

**这类不算"异常"，是常态。** 处理方式就是第 3 节的失效机制 + 一段内联挂起逻辑。

挂起逻辑在 `dispatchOutcome` 尾部（642-656），**没有独立的 `pauseActiveTask` 方法**——它就是一段内联判断：

```java
// 办理正停在一个待答问题上时，一句没被接住的话不该把整个办理挂起
if (!outcome.modelDriven() && route == CURRENT_FLOW && !hasTaskFacts(facts)
        && ("UNKNOWN".equals(facts.intent()) || "PROVIDE_INFORMATION".equals(facts.intent()))) {
    List<QuickReply> waitingReplies = state.taskStatus == ACTIVE ? modelSuggestedReplies(state) : List.of();
    if (!waitingReplies.isEmpty()) return respond(state, clarificationDraft(state), waitingReplies);  // 先把这一步再问一遍
    if (state.taskStatus == ACTIVE) state.taskStatus = PAUSED;     // 651-653
    state.dialogueMode = GENERAL_CHAT;                             // 654
    return respond(state, clarificationDraft(state), resumeReplies(state));
}
```

要点：

1. **先试"重述当前那一问"**（`clarificationDraft` 按 `stage` 决定重述哪一问）。只有重述也接不上才挂起。
2. 挂起只改 `taskStatus` 和 `dialogueMode`，**从不碰 `stage`，也不碰任何草稿字段**。
3. 挂起后按钮变成 `resumeReplies`：有打断记录时给「继续刚才办理」，否则给「继续办理」。
4. 恢复时反向（657-662）：`advancesTask(route)` 成立就把 `PAUSED` 拉回 `ACTIVE`。

**行为对照表：**

| 老人说的事 | 系统反应 | 办理进度 |
|---|---|---|
| 情绪表达（害怕、孤单、累） | 走安抚回复 | 挂起，草稿不动 |
| 普通闲聊 | 陪着聊两句 | 挂起，草稿不动 |
| 身体不舒服但说不清 | 安抚 + 复述 120 提示 | 挂起，草稿不动 |
| 只读查询（查流程/查医院/查我的预约/看地图） | 正常回答 | **状态完全不动** |
| 流程内的追问 | 继续问下一项 | 保持办事状态 |

**支线打断栈（`rememberInterruptedTask` 2981-2991）**

```java
if (taskInProgress(state) && state.interruptedStage == null
        && state.stage != COMPLETED && state.stage != CANCELLED) {
    state.interruptedStage = state.stage;      // 只记第一次
    state.interruptedPendingAction = state.pendingAction;
    state.interruptedPendingAppointmentId = state.pendingAppointmentId;
    state.returnPolicy = "ASK_TO_RESUME";
}
```

**只记第一次被打断的状态，后面再插话不覆盖**，保证"继续刚才办理"永远回到真正的原处。而改医院/科室/日期时直接 `discardInterruption`（2378 `changeTime`、各 `resetAfter*`）——用户已经明确转向了。

## 7. 设计取舍：写报告可直接引用的论证

### 7.1 为什么选槽位填充，不选 21 状态转移表

如果把 21 个阶段写成经典状态机，**理论上需要几百条转移边**；而且每加一个字段（例如后来加的"选医诉求" `doctorQuery`/`doctorId`/`wantsExpert`），都要回去修改所有涉及它的边。用槽位填充，加字段只是**在 `advance` 里加一行 `if (x == null)`**。

### 7.2 三条主干原则

1. **改一步不用从头来** —— 失效半径由依赖决定（第 3 节）
2. **暂停 ≠ 清空** —— 挂起只改 `taskStatus`，不碰 `stage` 和草稿（6.6 节）
3. **写入路径唯一** —— 文本/按钮/图片全部收敛到 `confirm` 四道门禁（第 4 节）

### 7.3 一句话小结（建议作为报告第四节收尾）

> **漏斗是软的（槽位驱动、可乱序、可回退、可挂起），出口是硬的（唯一写入路径、凭据一次性、停机拦截）。软的负责适应老人的表达，硬的负责守住"什么情况下才真的写库"。**

## 8. 三处口径差异（建议在报告里主动写明理由）

这三处不是 bug，但**文档/话术与代码不完全一致**，被追问时要说得出理由：

1. **`resetAfterDepartment` 不调用 `invalidate`**（`resetAfterDate` / `resetAfterHospital` 都调）。它靠 `stage` 移出 `AWAITING_CONFIRMATION` 让门禁第③道拒绝；`changeTime`（2377-2384）同此模式。结果安全，但**"失效"实际有两个来源**，报告里不宜说成单一机制。
2. **模型模式下安全关键词不前置**：`SafetyGuard#precheck` 只在 `!modelAvailable()` 时执行（435）。越界侧有 `looksLikeMedicalAdvice` 规则兜底，**紧急侧没有**。已记录于 `docs/13-demo-scenarios-workflow.md` §7.1。
3. **`全量分支梳理.md` 说改科室会"联系人全部置 null"** —— 代码只清了 `notifyFamily`，`contact` 不在 `resetAfterDepartment` 的清单里（5395-5414）。属轻微夸大，**以代码为准**。
