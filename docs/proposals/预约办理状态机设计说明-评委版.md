# 预约办理状态机设计说明


## 先给一句话结论

这套状态机其实就两条原则：**改一步不用从头来，聊别的也不丢进度。**

展开是四件事：

- 用户要改上一步 → 只清被这一步影响的那些结果，其它已经答过的全留着。整单重来必须是他自己明说「重新办」。
- 用户答非所问 → 办理原地挂起，草稿一个字不动，旁边放一个「继续办理」的按钮。
- 碰到医疗问题（越界） → 只插一句「这个我不能答」，手里的确认卡原样留着。
- 碰到紧急情况 → 反过来，直接冻结，旧的确认卡作废。

还有一条贯穿全局：不管用户是打字、点按钮还是发图片，最后确认办理只走同一条路。

---

## 一、状态不是一条线，是四层叠在一起的

| 状态层 | 管的是什么 | 取值 |
| --- | --- | --- |
| 会话状态 | 这段对话还能不能接着用 | 进行中 / 已结束 / 已过期 |
| 任务状态 | 这次办理走到哪儿了 | 没开始 / 进行中 / 挂起 / 等确认 / 办完了 / 已取消 |
| 办理阶段 | 现在正在问哪一句 | 21 个，从「问医院」一路到完成、取消 |
| 对话模式 | 这一轮是在办事还是在聊天 | 办事 / 普通聊天 / 情绪安抚 / 闲聊 |

为什么要拆成四层？因为这几件事本来就是独立的。比如「对话已经结束了，但那次预约确实办成了」是正常情况；「用户正在聊别的，但办理流程停在『要不要家属陪同』这一问上」也很正常。如果把它们挤进一个状态变量，这些组合就永远表达不出来。

**这里有个实现上的选择值得说**：接了大模型之后，「办理阶段」这个字段其实已经不太参与业务判断了，它更像是给进度条看的。真正决定下一句问什么的是草稿里哪些字段还空着——空着就问那一项，齐了就走确认。

---

## 二、用户说一句话进来，系统按什么顺序处理

顺序本身就是设计。大致是这么几关：

1. 输入是空的吗？空的直接让重说，不落库。
2. 会话是不是已经结束了？是不是处于停机状态（取消过、紧急过）？是的话按规则拒绝。
3. 这轮用户到底想干嘛：回答问题、要改某个字段、还是在聊别的？
4. 进到具体业务分支。
5. 生成回复。

中间有几处是刻意加的兜底。比如用户正在等一句是非题的答案，这轮又没提取到任何业务信息，系统不会直接甩一句「我没太听明白」，而是把当前这一问原样再问一遍。对我们这个适老场景来说，「没听懂」这三个字很容易让老人觉得自己被踢出来了。

还有一条：**真正写进数据库，只发生在用户点「确认办理」的那一刻。** 而且确认卡里的时间、地点、陪同、带什么材料、通知谁，都是系统照着草稿直接拼出来的，不经过语言模型改写。理由很实在——这张摘要就是用户"签字授权"的依据，交给模型压缩一遍可能就悄悄变味了，所以「用户看到的」和「系统会执行的」必须一字不差。

---

## 三、「我想改上一步」——按依赖清场，不是回到起点

这是整件事里最关键的一条。用户说要改，系统做的不是「退回上一步」，而是看**这个字段被后面的哪些结果依赖**，只清那些，其它全部保留。

| 用户改的是 | 清掉 | 保留 | 为什么这么切 |
| --- | --- | --- | --- |
| 某个细节（陪同、通知谁、交通） | 确认卡、日程检查结果 | 医院、科室、日期、号源 | 只是细节变了，前面选好的还作数 |
| 日期 | 上面那些 + 号源、材料 | 医院、科室、陪同、交通、通知 | 换一天只影响那天有没有号 |
| 科室 | 科室往下几乎全清，连陪同、交通、通知也一起清 | 只留医院 | 科室一换，怎么去、要不要人陪这些结论可能都不成立了 |
| 医院 | 除了医院之外全清 | 什么都不留 | 医院都换了，等于重来 |

光看表可能还没感觉，举几个例子。

**例 1：改日期不清陪同。** 老人把复诊日从 18 号改到 20 号，之前答的「需要家属陪」不会被清掉。道理很朴素——陪不陪是跟着人走的，跟哪天去医院没关系，为这个再问一遍纯属骚扰。

**例 2：改科室才连偏好一起清。** 老人把科室从心内科改成骨科，这时候不只是后面没问的，连已经问过的「要不要人陪」「怎么去」「通知谁」也一并清掉。因为科室换了，这些答案可能都不再成立。这就是「按依赖清场」和「按步骤位置清场」的区别。

**例 3：不管从按钮改还是从一句话改，走的是同一套逻辑。** 用户用自由文字改字段时，系统会做一次前后比对，发现医院/科室/日期变了就触发同样的清场。我们特意堵掉了「按按钮清干净了、说话却没清」这种两套行为——同一个功能有两套实现，迟早会走散。

**例 4：改的是已经办成的预约。** 这种情况不会动原来那条记录，而是先另开一份「变更草稿」，同时把原预约记着；等用户确认了新方案，才去换号源。好处很明显：**改期失败等于什么都没发生**，原预约和提醒都在，不会出现「旧的撤了、新的又没拿到」的空档。

**全量重来只留了三个入口**：点「重新办理」按钮、明确说「重新办一次」、以及在已经办完或已取消的状态下点「开始办理」。改一个字段永远触发不了整单重来。

## 四、用户答非所问的时候

适老场景里这是最高频的情况——老人正答着「去哪家医院」，突然说一句「我闺女明天来」，或者「我有点害怕」。

系统的处理可以概括成一句：**暂停 ≠ 清空。**

| 用户说的事 | 系统反应 | 办理进度 |
| --- | --- | --- |
| 情绪表达（害怕、孤单、累） | 走安抚回复 | 挂起，草稿不动 |
| 普通闲聊 | 陪着聊两句 | 挂起，草稿不动 |
| 身体不舒服但说不清 | 安抚 + 复述 120 提示 | 挂起，草稿不动 |
| 只读查询（查流程、查医院、查我的预约、看地图） | 正常回答 | **状态完全不动** |
| 流程内的追问 | 继续问下一项 | 保持办事状态 |

挂起这个动作只改一个字段，从「进行中」变成「挂起」，**阶段不动、草稿里任何字段都不动**，同时给一个「继续刚才办理」的回程按钮。用户聊完点一下就回到原来那一问，不用重新答一遍。

顺带还专门治过一个小毛病：有些对错题（「需要家属陪同吗」），模型经常嘴上说记住了、实际没往字段里填，结果同一句话被反复问。现在这三处系统会自己认领短肯定句，不等模型了。

---

## 五、越界和紧急：方向正好相反

这两个特别容易混在一起讲，其实处置方向是反的，而且都是故意的。

**越界**（问到诊断、用药、看检查报告这类）：

- 回一句标准话术：不能诊断、不能判断原因、不能解读报告、不能调整用药，建议咨询医生。
- 这段提示单独渲染成一个橙色警告块，**上面不放任何按钮**——它不是一步操作。
- 手里那张确认卡，连同原来的凭据，**原样还回去**。阶段也不动。

为什么这么设计？老人问到一半药，如果手里那张「确认办理」跟着消失了，他会以为事儿办不成了——可服务端那张卡一直是有效的。所以越界的原则是**「只插话、不改办」**。

**紧急**（胸痛、呼吸困难、昏迷、想不开这类）方向完全反过来：

- 清掉确认凭据，任务冻结。
- 所有入口的旧操作全部拦下，包括那张旧确认卡，直接作废。
- 给求助提示 + 一个「人工帮助」按钮，**绝不自动跳页**。
- 想恢复办理必须显式点「重新办理」，「继续」是通不过的。

最后这一条很关键：不能让一个之前留在页面上的旧按钮，把紧急状态悄悄解除了。

顺便说，冻结之后仍然放行「这附近医院怎么走」这类问路请求，因为那时候最需要的恰恰是求助信息，一刀切拦掉反而把要紧的话盖住了。

## 六、用户插了句话，待会儿还得接着办

办到一半去看地图、查自己有哪些预约，这在老人身上很常见。系统为此单独存了一个「打断点」：只记第一次被打断时的状态（正在问什么、有没有待办的事），后面再插话也不会覆盖掉它。

回来的时候按打断点恢复。如果打断前正好停在确认卡那一步，就把那张卡重新摆出来。

有个细节：如果用户直接改了医院、科室、日期，那就说明他已经明确转向了，旧的回程点没意义，直接丢掉。

## 七、其他几个容易卡住的地方

| 情况 | 系统怎么处理 | 为什么 |
| --- | --- | --- |
| 选的日期没号了 | 先问「接不接受附近日期」，用户拒绝就尊重他的选择 | 不擅自替他换一天；「附近」只往后算 3 天，往前会捞出已经过去的时段 |
| 新时间撞上已有日程 | 一发现就提示，让用户换号源或明确保留 | 不等陪同、交通全答完才说「这个时间您有约了」，那样前面的答案全白答 |
| 同一时刻已经约过 | 提交前拦下，给三条出路 | 只比「同一天同一时刻」，不再比医院科室——一天看两个科室是正常需求，只有时刻撞上才矛盾 |
| 日期太远或已经过去 | 说明可查范围（今天到一个月后） | 直接说清边界，比报一个莫名其妙的错好 |
| 已经约成功了，但提醒没建完 | 说「预约已保留，还有事项没完成」，给补办入口 | 绝不写成「办理失败」——预约确实办成了，而且重试只会补失败的那几步 |
| 确认卡已经失效或重复点 | 拒绝，提示查看当前计划后重新确认 | 确认凭据是一次性的，用完就废 |
| 医院/科室名字对不上 | 不猜，列真实选项，或者引导问家属、问服务台 | 绝不把系统里不存在的名字写进流程 |

## 八、可以写进设计文档的几条结论

1. **失效是按依赖算的，不是按步骤位置算的。** 改日期不清陪同、改科室才清——这个区别让体验比「改任何一步都回起点」好一个量级，同时又比「改了什么都不清」安全。
2. **「还不知道」和「明确不需要」是两个不同的值，不是同一个空值。** 前者驱动的是「再问一次」，后者驱动的是「跳过这一问」。
3. **越界和紧急方向相反，而且都是有意的。** 越界是「只插话、不改办」，因为用户没说想中断；紧急是「冻结 + 作废旧确认」，因为继续办就是错的。
4. **异常不终止对话。** 每个异常都给得下去的选项（换日期、换号源、保留、稍后再查、人工帮助），只有「已取消」和「紧急暂停」两个状态需要用户显式重新开始。
5. **展示和事实同源。** 确认卡、完成卡、计划卡都是照着草稿直接拼的，不经模型改写，所以「用户看到的」和「系统会执行的」不可能分叉。

---

## 附：几处我们自己还没完全对齐的地方

写文档时想说的是「设计如此」，但读代码发现有三处口径不完全一致，列出来免得被问住：

1. 「改科室」这条路径没有自己清确认凭据，是靠阶段已经移出确认态来兜住的。结果是对的，但「失效」这件事实际上有两个来源，不能说成单一机制。
2. 规则模式下紧急关键词是前置拦截的，接了大模型之后这条前置没有补上对应的规则兜底——越界那侧补了，紧急这侧没有。
3. 三个「清场」的范围差异挺大（改日期留偏好、改医院不留、改科室连偏好一起清），各自理由说得通，但文档里最好明确写清楚，别让人以为是随手写的。
