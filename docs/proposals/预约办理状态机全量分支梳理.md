# 预约办理状态机：全量分支梳理

> 用途：供 `docs/设计思路报告.md` 第四节「任务拆解机制」与第七节「异常处理」扩写取材。
> 口径：只写**当前源码事实**，引用一律用 `类名#方法名`，不写行号（行号会漂移）。
> 主实现集中在 `FollowupAgentService`（约 5800 行）与 `ConversationState`。

---

## 0 一句话结论

这套状态机的设计原则是**「字段依赖驱动的最小失效 + 单一终态出口」**：

- 用户改上一步时，**不做整流程重来**，而是按「这个字段被谁依赖」清掉受影响的派生结果，其余已答字段全部保留；只有三个显式入口才做全量重来。
- 用户答非所问时，**不丢草稿、不退回起点**，任务从 `ACTIVE` 转 `PAUSED`，阶段与字段原地保留，并给一个「继续办理」的回程按钮。
- 越界（医疗）、紧急、取消三类是**全局守卫**，优先级高于任何业务分支；越界是「只插话、不改办」，紧急与取消是「冻结/终结 + 旧确认作废」。
- 所有写入只有一条路径：`confirmationId` 匹配 + 阶段为 `AWAITING_CONFIRMATION`。模型、按钮、图片输入都绕不过去。

---

## 1 四层互相正交的状态

理解这套状态机的前提：它**不是一个**状态机，而是四层各自独立、彼此正交的状态叠在一起。新人最容易犯的错是把它们混成一个。

| 层 | 字段 | 枚举 | 语义 | 谁会改它 |
| --- | --- | --- | --- | --- |
| 会话生命周期 | `status` | `ACTIVE` / `CLOSED` / `EXPIRED` | 这段对话还能不能继续用 | 用户点「新对话」、空闲超时 |
| 任务状态 | `taskStatus` | `NONE` / `ACTIVE` / `PAUSED` / `AWAITING_CONFIRMATION` / `COMPLETED` / `CANCELLED` | 这次预约办理走到哪一步了 | 各业务分支 |
| 办理阶段 | `stage` | 21 个值（见 §3.1） | 此刻在问什么 / 停在哪个岔口 | 各业务分支 |
| 对话模式 | `dialogueMode` | `GENERAL_CHAT` / `FOLLOWUP_FLOW` / `SUPPORT` / `SMALL_TALK` | 这一轮是办事还是聊天 | 分流函数 |

四条正交的实证：一段会话可以「已经结束（`CLOSED`）但办理结果仍在历史里（`taskStatus=COMPLETED`）」；也可以「还在聊（`GENERAL_CHAT`）但办理暂停（`PAUSED`，`stage=ASK_COMPANION`）」。

**关键设计：`dialogueMode` 只描述当轮语气，不参与业务判定；`stage` 在模型模式下退化为「给旧前端进度展示用」的呈现字段**（见 `#syncPresentationStage` 的类注释），真正的业务判定看草稿字段是否齐全，而不是看 stage 数字。

## 2 一轮的完整骨架：从入口到出口

自由文字的统一入口是 `#chatInternalBody`，它的守卫是**有严格先后顺序**的，这个顺序本身就是设计：

```
1  空输入 → 直接要求重说                                    （不落库）
2  【仅规则回退模式】SafetyGuard#precheck 关键词前置拦截      ← 紧急/越界第一道
3  备忘子流程 pendingAction 分派（MEMO_TIME / MEMO_DAY / …）
4  数值反问 RECORD_CONFIRM：答不上来就作废暂存、放行走下面链路
5  「把图上的字念一遍」→ 不走模型，逐字照抄
6  AgentRuntime#plan → 模型规划
7  写入本轮用户消息
8  SafetyGuard#evaluateModel / #evaluate  → 紧急 / 越界第二道
9  【仅规则回退模式】备忘、健康数值、健康周报、目录查询等关键词路由
10 prepareModelIntentState（按 intent 决定是否清草稿）
11 stopped() 守卫：取消/紧急终态下，非白名单路由一律拒绝
12 模型模式的日常三类（备忘/数值/发周报）优先于预约流程
13 pendingEntity 待确认候选
14 长期记忆里的医院「是的」
15 取消支线（CANCEL_EXISTING_APPOINTMENT）承接
16 地图候选支线（SELECT_TRAVEL_APPOINTMENT）承接
17 AWAITING_CONFIRMATION 下，页面指令不得挤掉确认卡
18 COMPLETED 下，短肯定句可直开地图
19 ACTIVE 且在问医院/科室：走目录匹配（不信任模型编的名字）
20 「Java 举着推荐号源 / 是非题」时，短肯定句由 Java 自己认领
21 规则模式下，接不住的话 → 把当前这一步再问一遍（或转 PAUSED）
22 advancesTask(route) → 置 FOLLOWUP_FLOW、PAUSED→ACTIVE
23 只读工具循环 runModelToolLoop（最多 3 轮）
24 dispatchOutcome → 按 Route 分派到具体业务方法
```

出口统一收敛到三个函数，**写库与落消息只在这一层发生**：

| 出口 | 是否经回答模型改写 | 用于 |
| --- | --- | --- |
| `#finish` | 是（`AnswerGenerator` 润色） | 普通补问、闲聊、查询结果 |
| `#finishWithoutModel` | 否（原文直出） | 确认摘要、完成卡、越界提示、紧急提示 |
| `#finalizeToolEvidence` | 否 | 工具循环终局，把权威工具结果原样交付 |

**为什么确认卡与完成卡必须走 `finishWithoutModel`**：确认摘要里的时间、地点、陪同、材料、通知对象是「用户即将据以授权的凭据」。这类文本一旦交给语言模型压缩，就可能悄悄变形，而「用户看到的」与「真正会执行的」必须逐字一致。

## 3 情况一：用户要改上一步 —— 分级失效，不是全部重来

这是问得最核心的一个问题。答案是：**局部重算，按依赖清场；全量重来只留给三个显式入口。**

### 3.1 21 个阶段值（`ConversationState.Stage`）

| 分组 | 值 |
| --- | --- |
| 补问漏斗（7） | `ASK_HOSPITAL` `ASK_DEPARTMENT` `ASK_DATE` `ASK_ALTERNATIVE` `ASK_COMPANION` `ASK_TRAVEL` `ASK_TRANSPORT` `ASK_NOTIFY`（8 个） |
| 选时段（4） | `SELECT_PERIOD` `CONFIRM_SLOT` `SELECT_SLOT` `NO_SLOT` |
| 检查与确认（3） | `READY_TO_PLAN` `CONFLICT` `AWAITING_CONFIRMATION` |
| 终态与异常（5） | `COMPLETED` `CANCELLED` `EMERGENCY_PAUSED` `PARTIAL` `TOOL_ERROR` |
| 借用的子流程（1） | `MEMO_TIME`（备忘追问钟点期间临时占用） |

### 3.2 三级失效函数：改得越靠前，清得越多

`FollowupAgentService` 用四个函数表达「失效半径」：

| 函数 | 清掉什么 | 保留什么 | 用户改的是 |
| --- | --- | --- | --- |
| `#invalidate` | `confirmationId`、`pendingAppointmentIds`、`scheduleChecked`、`travelPlan`；若正处于 `AWAITING_CONFIRMATION` 则退回 `READY_TO_PLAN` | **号源、日期、材料、所有偏好字段全保留** | 任何会影响确认内容的字段（最小颗粒） |
| `#resetAfterDate` | `invalidate` + 日期、号源、推荐号源、时段偏好、指定时刻、候选项、出行、材料；stage → `ASK_DATE` | 医院、科室、陪同、出行开关、交通、通知、联系人 | 改日期 |
| `#resetAfterDepartment` | 科室、日期、号源、候补、医生诉求、出行、材料、**连带 acceptAlternative / 陪同 / 出行 / 交通 / 通知 / 联系人全部置 null**；stage → `ASK_DEPARTMENT` | 医院 | 改科室 |
| `#resetAfterHospital` | `invalidate` + 待确认候选 + 医院、科室、日期、号源、医生诉求、出行、材料；stage → `ASK_HOSPITAL` | 无（科室以下全清） | 改医院 |
| `#clearDraft`（全量） | 上面全部 + `pendingAction`、`appointmentId`、`pendingAppointmentId`、`originalAppointmentId`、三个 `*Done` 标志、`scheduleChecked`、`conflictKept`、打断栈 | 会话身份、长期记忆、已落库的预约 | 重新办理 |

**注意「改科室为什么连陪同、交通、通知都清」**：这些偏好是围绕「这次复诊」的答案，科室一换，往返路线、是否需要陪同的结论都可能不成立。反过来「改日期」不清陪同，因为陪同需求跟着人走、不跟日期走。这正是「按依赖清场」而不是「按位置清场」。

### 3.3 统一的自然语言入口：`#applyFacts`

自由语言改字段走的是另一条路，但规则一致 —— `#applyFacts` 在写字段前后做差量比对：

```java
if (!Objects.equals(oldHospital, state.hospitalId)
        || !Objects.equals(oldDepartment, state.department)
        || !Objects.equals(oldDate, state.date)) {
    state.selectedSlot = null;  state.recommendedSlot = null;
    state.alternatives = List.of();  state.materials = List.of();
    invalidate(state);          // 确认凭据、日程检查、出行全部作废
}
```

也就是说，**「改医院/科室/日期」这件事不管从按钮来还是从一句话来，最终都落到同一段重算逻辑**。这一条是需求 4.5「中途修改医院/日期」的正面回应：不允许出现「按钮路径清了、自然语言路径没清」的两套行为。

另外两处细节：`notifyFamily=false` 时连带清 `contact`（不通知就不该留着联系人）；`selectedTime` 与已选号源不一致时清空 `selectedSlot`。

### 3.4 用户改的是「已完成预约」：独立变更草稿

`EDIT_BOOKING` 按钮（见 `#actInternal`）：

```
stage 必须是 COMPLETED，否则回「请先补办未完成事项，或取消预约」
originalAppointmentId = appointmentId   ← 旧预约原地留着
appointmentId = null                    ← 会话与旧预约解绑
三个 *Done 标志复位、pendingAction=CREATE、invalidate
回复：「原预约仍然有效。请修改草稿，确认新方案后才会变更原预约。」
```

确认时若 `originalAppointmentId != null` 就走 `AppointmentTool#reschedule`（**原位换号源，不停旧记录**），而不是新建。设计后果很好：**改期失败 = 什么都没发生**，原预约和原提醒一律保留，不会出现「旧预约被撤了、新号源又没拿到」的空档。照护端走 `CareBookingService#modify`，同理。

### 3.5 全量重来的三个显式入口

| 入口 | 触发 | 行为 |
| --- | --- | --- |
| `NEW_BOOKING` 按钮 / `RESTART_TASK` 路由 | 用户点「新建办理」，或模型判 `RESTART_TASK`，或 `CREATE_FOLLOWUP` 且当前无进行中任务 | `#restartInCurrentConversation` → `clearDraft` → `askHospital` |
| `CONTINUE` / `RETURN_TO_FLOW` 且 `taskStatus ∈ {NONE, CANCELLED, COMPLETED}` | 用户在终态下点了「开始办理」 | 同上，走新建 |
| `#prepareModelIntentState` 的 `RESTART_TASK` 分支 | 模型明确识别为「重新办」 | `clearDraft` + `taskStatus=ACTIVE` |

**设计要点**：全量重来必须是用户的**显式意图**（点按钮、说「重新办」），绝不能因为「改了一个字段」就自动发生。反过来，只要用户只是改一项，「继续办理」就一定能回到原来那一问。

## 4 情况二：用户答非所问（说的事与预约无关）

这是适老场景里最高频的情况：老人答一句「我闺女明天来」，或突然说「我有点害怕」。

### 4.1 分流表

| 用户说了什么 | 路由 | 状态变化 | 是否丢草稿 |
| --- | --- | --- | --- |
| 情绪表达（害怕、累、孤单） | `EMOTIONAL_SUPPORT` → `DialogueService#support` | `dialogueMode=SUPPORT`，`ACTIVE→PAUSED` | 否 |
| 普通闲聊（谢谢、随便聊聊） | `SMALL_TALK` → `#smallTalk` | `dialogueMode=SMALL_TALK`，`ACTIVE→PAUSED` | 否 |
| 身体不舒服但说不清 | `CLARIFY_DISCOMFORT` | 同上 + 复述 120 提示 | 否 |
| 模型判 `ANSWER` 且 intent 属会话型 | `DIRECT_ANSWER` → `DialogueService#modelReply` | `dialogueMode=GENERAL_CHAT`，`ACTIVE→PAUSED` | 否 |
| 只读查询（查流程、查医院、查我的预约、看地图） | 对应只读路由 | 任务状态**不动**（若本来 ACTIVE 仍 ACTIVE） | 否 |
| 流程内的追问（模型用 `ASK_USER` 问下一项） | `CURRENT_FLOW` | 保持 `FOLLOWUP_FLOW` | 否 |

`pauseActiveTask` 只做一件事：`if (taskStatus == ACTIVE) taskStatus = PAUSED`。**它从不碰 `stage`，也不碰任何草稿字段**。

### 4.2 一句「没听懂」的兜底，也被专门设计过

规则模式下，如果这轮话里**一个业务字段都没提取到**（`!hasTaskFacts(facts)`）且 intent 是 `UNKNOWN` / `PROVIDE_INFORMATION`：

```java
List<QuickReply> waitingReplies = ACTIVE ? modelSuggestedReplies(state) : List.of();
if (!waitingReplies.isEmpty()) return respond(state, clarificationDraft(state), waitingReplies);
// 否则才降级为 PAUSED + 回程按钮
```

`#clarificationDraft` 按当前 stage 逐项给出**针对那一问的重述**，而不是笼统的「我没太听明白」。例如：

- `ASK_COMPANION` → 「我还没听准这一步：这次复诊需要家属陪同吗？回答『需要』或『不需要』都可以。」
- `ASK_TRANSPORT` → 「我还没听准这一步：您打算怎么去医院？可以说家属开车、打车或者坐公交。」

**为什么要专门写这一段**（代码注释里的原话）：这几个阶段以前没有自己的兜底，一句「要」没被接住就直接跳到「我没太听明白」，等于把老人从正在办的事里踢出去。更糟的是任务一旦 `PAUSED`，阶段就不再同步，按钮只剩「继续办理」，老人越答越回到原地。

### 4.3 短肯定句由 Java 自己认领（不等模型）

模型链路里，`facts` 是唯一事实源。但实测模型经常「嘴上说记住了、JSON 里不填字段」，于是同一道是非题被反复问。`#chatInternalBody` 因此在三处加了 Java 侧认领：

1. `#recommendedSlot != null` 且用户说「可以/行/好的」→ 直接 `selectSlot`；
2. `!hasTaskFacts(facts)` 且已选号源、`acceptAlternative != null`，用户说「要/不用」→ 按 `pendingQuestion` 顺序自己记 `needCompanion` / `needTravel` / `notifyFamily`；
3. 交通方式是开放题（「怎么去」接不住「好的」），刻意跳过，交回模型。

## 5 情况三：支线打断与回程（`interruptedStage`）

「用户问了别的，但待会儿还要接着办」这件事有独立的一套栈。

| 机制 | 实现 |
| --- | --- |
| 入栈 | `#rememberInterruptedTask`：仅在 `taskInProgress` 且当前不是 `COMPLETED/CANCELLED` 且栈为空时，保存 `interruptedStage`、`interruptedPendingAction`、`interruptedPendingAppointmentId`，并置 `returnPolicy="ASK_TO_RESUME"`，同时记 `sideTask` |
| 回程按钮 | `#resumeReplies`：有栈 → 「继续刚才办理」(`RESUME_INTERRUPTED`)；无栈但任务在办 → 「继续办理」(`CONTINUE`)；否则 → 「开始复诊办理」 |
| 出栈 | `#resumeInterruptedTask`：恢复 taskStatus=ACTIVE、`stage=interruptedStage`、`pendingAction`、`pendingAppointmentId`；若恢复到的正是 `AWAITING_CONFIRMATION` 且 `pendingAction=CREATE`，**重建确认卡**；否则 `advance` 继续 |
| 出栈即弃 | `#discardInterruption` / `#clearInterruption`：改医院/科室/日期/时间前先丢弃打断栈（用户已经明确转向，旧回程点已无意义） |
| 取消支线与地图支线**分开** | `sideTask ∈ {CANCEL_EXISTING_APPOINTMENT, SELECT_TRAVEL_APPOINTMENT}` 两条各自承接，互不消费；取消支线里 「只有指代没有日期」时重新展示候选，不猜 |

## 6 情况四：越界（医疗服务边界）

### 6.1 判定口径：默认怀疑

判定统一收在 `MedicalBoundaryRules`，口径是「**默认怀疑**」而非「关键词命中才拒绝」——类注释写明理由：越界漏判的表现是**整句话被当成普通信息静默忽略**，老人会以为得到了答复，这个失败模式比多提示一次更贵。

组合条件（不是单张动词表）：

| 词表 | 生效方式 |
| --- | --- |
| `EXPLICIT`（要不要紧、什么病、怎么用药、剂量…） | 命中即越界，无需疑问语气 |
| `SYMPTOMS` + `QUESTION_MARKERS` | 症状词与疑问语气同时出现 |
| `MEDICATIONS` + `QUESTION_MARKERS` | 药物与用药行为同理 |
| `REPORTS` + `LOOK_MARKERS` | 报告类名词与查看诉求同时出现 |
| `LOGISTICS_REQUESTS`（带什么、准备什么） | **优先放行**，属办理事项 |
| `SELF_RECORD_QUERIES`（我最近血压多少） | **优先放行**，属本项目的健康记录回查 |

### 6.2 两条执行路径

| 模式 | 时机 | 方法 |
| --- | --- | --- |
| 规则回退 | 模型调用**之前** | `SafetyGuard#precheck` |
| 模型模式 | 模型规划**之后** | `SafetyGuard#evaluateModel`：认模型的 `MEDICAL_ADVICE` / `HEALTH_CONCERN` intent，**再加一道 `looksLikeMedicalAdvice` 规则兜底** |

兜底那一道是刻意加的：模型漏判时整句话会被静默忽略，比多提示一次更贵。

### 6.3 「只插话、不改办」——越界处理的精髓

`#medicalBoundary` 做三件事，并**刻意什么都不改**：

1. 给一句权威回复（不能诊断、判断原因、解读检查结果、调整用药，建议咨询医生）；
2. 附一个 `Notice(MEDICAL_BOUNDARY)`，前端渲染成独立的橙色 `role="alert"` 区块（`BoundaryAlert`），**卡上不放任何按钮**；
3. **把原来那张确认卡连同原 `confirmationId` 原样交回**（`#pendingConfirmation`）。

```java
// 刻意不动 stage，也不清 confirmationId
return respondWithoutModel(state, message, resumeReplies(state, q("咨询人工","CONTACT_HUMAN","")), null,
        new Notice(MEDICAL_BOUNDARY, "超出我的服务范围", framing), pendingConfirmation(state));
```

**为什么这是最容易做错的地方**：老人问到一半药，手里那张「确认办理」如果跟着消失，他会以为办不成了 —— 而服务端那张卡其实一直有效。所以 `#medicalBoundary` 不改 `stage`、不清 `confirmationId`，`#pendingConfirmation` 也不重建卡片，只把同一张卡交回。**卡片内容始终只有一处来源**（`#confirmationCard`），避免「看到的」和「会执行的」不一致。

## 7 情况五：紧急

### 7.1 触发与效果（`#emergency`）

```java
state.confirmationId = null;
if (taskStatus == ACTIVE) taskStatus = PAUSED;   // 只暂停，不取消
state.stage = EMERGENCY_PAUSED;
notifyArranger(state, "emergency", "紧急通知：…触发紧急求助…");
return emergencyNotice(state);   // 文字 + 一个「人工帮助」按钮，绝不自动跳页
```

触发源：规则模式的 `SafetyGuard#precheck` 词表（胸痛、心口疼、胸闷、呼吸困难、昏迷、大出血、喘不上气、想不开…）；模型模式认主模型给出的 `EMERGENCY` intent。

### 7.2 紧急之后，旧动作全部失效

| 入口 | 守卫 |
| --- | --- |
| `/messages` | `stopped(state) && !allowedWhenStopped(route)` → `stoppedResponse` |
| `/actions` | `if (stopped(state)) return stoppedResponse(state)`（`NEW_BOOKING`/`CONTACT_HUMAN` 在此之前处理） |
| `/confirmations` | `if (stopped(state)) return stoppedResponse(state)` —— **旧确认卡直接作废** |

`#allowedWhenStopped` 的白名单：`DIRECT_ANSWER`、`EMOTIONAL_SUPPORT`、`SMALL_TALK`、`CLARIFY_DISCOMFORT`、`RESTART_TASK`、`QUERY_CARE_GUIDE`、`MULTI_READ_TOOLS`、`QUERY_MY_APPOINTMENTS`、`CANCEL_EXISTING_APPOINTMENT`、`QUERY_TRAVEL_GUIDE`、`QUERY_LOCATION_GUIDE`。

**为什么不提前无条件 return**（代码注释）：判断要按「本轮落在哪条路由」来 —— 紧急暂停期间问「到医院怎么走」仍要回带 120 的安全提示，而页面跳转一律不给。提前 return 的话，安全提示里就只剩「旧操作不会继续执行」，反倒把最要紧的求助信息盖掉了。

**恢复办理必须显式**：`EMERGENCY_PAUSED` 下 `taskStatus` 是 `PAUSED`，所以 `CONTINUE` 会被 `stopped` 拦下，只有 `NEW_BOOKING`（显式新建）能出去。这是「不能由旧快捷按钮或『继续』隐式恢复」的落地。

## 8 情况六：三种「取消」必须分清

老人说「我不想弄了」和「把 9 月 18 日那个取消掉」是两件完全不同的事，系统有三个出口：

| 动作 | 入口 | 效果 | 是否碰数据库 |
| --- | --- | --- | --- |
| 停止本次办理 | `CANCEL_TASK`（`#cancelTask`） | `confirmationId=null`；若有 `appointmentId` → 保留预约、置 `CANCELLED`；否则 `clearDraft` + `CANCELLED` | 不写库 |
| 取消已有预约 | `CANCEL_APPOINTMENT` → `#beginCancelExistingAppointment` → 确认卡 → `confirm` | 先查真实预约 → 绑定 `pendingAppointmentId(s)` → 二次确认 → `AppointmentTool#cancelAll` | 确认后才写 |
| 代约的取消 | `MANAGE_MANAGED` → `CANCEL_MANAGED` → `#confirmManagedCancelCard` → `confirm` | 走 `CareBookingService#cancelUpcoming` | 确认后才写 |

`#cancelTask` 的措辞是分开的：有预约时「已经确认的预约仍然保留，可在事项页面查看」；无预约时「本次办理已停止，未提交预约」；改期草稿时「变更草稿已取消，原预约和提醒保留」。**「已取消/已保留/未提交」三种状态不允许混用一句「已取消」。**

另外，「取消掉 9 月 18 日那个」还有一层校验：如果老人手里**已经开着**一张确认卡，`#chatInternalBody` 会拦住「打开地图」这类只读跳转（见骨架第 17 步），要求先处理完这张重要操作 —— 避免只读动作把确认卡挤掉。

## 9 情况七：指定日期无号（`NO_SLOT`）

`#querySlots` 在真实查询返回空列表时进入 `NO_SLOT`，三步：

```java
state.stage = NO_SLOT;
state.alternatives = List.of();
if (acceptAlternative == null)  → 问「这天暂无号源，您接受附近的其他日期吗？」
if (!acceptAlternative)         → 尊重：「已保留只选这一天的意愿」+ 稍后再查 / 主动修改日期 / 换医院
acceptAlternative = true        → 调 appointment.queryAlternatives 查附近
```

三条硬口径：

1. **先问后查**。`acceptAlternative == null` 时只提问，**不默认展开附近日期**。
2. **拒绝就尊重**。明确说不换日期时不默认选一个。
3. **「附近日期」= 只往后 3 天**（`MockAppointmentTool#queryAlternatives`：`date.plusDays(1)` 到 `date.plusDays(3)`）。代码注释写明：往前会捞出已经过去的时段；把当天其它时段算进「附近日期」还会和上一句「这天暂无号源」自相矛盾。**当天之内换时段由 `SELECT_PERIOD` 那条路单独负责，两条路不重叠**。

选定新号源后走 `#selectSlot` → `advance` → **重新执行 `#checkSchedule`** —— 新时间经过新的检查、新的确认卡，即验收清单中「新时间经过新的确认」。

## 10 情况八：日程冲突（`CONFLICT`）

判据是**区间相交**（`start_at < end AND end_at > start`），所以 09:00（结束 10:00）与 10:00–11:00 的体检**不算冲突**，正好是不冲突的对照组。

### 10.1 检查点有两个，而且是刻意留的

| 检查点 | 时机 | 方法 |
| --- | --- | --- |
| 号源锁定预检 | `#selectSlot` 内 | `#slotBlocked` → `#slotConflicts` |
| 提交前检查 | `ready()` 成立后 | `#checkSchedule` |

**为什么提前问**（`#slotBlocked` 注释）：这两道检查原来都挂在 `ready()` 之后，等于要老人把陪同、出行、交通、通知全答完才告诉他「这个时间您已经有约了」—— 那些答案全白答，而且他已经把这件事当成定局了。

### 10.2 `conflictKept`：一个专门为「同一冲突不被问第二次」而生的标记

```java
// checkSchedule
if (state.conflictKept && !state.conflicts.isEmpty()) return checkDuplicate(state);  // 短路
```

不给两次冲突提示的理由：冲突在第一道就提示了，那时 `ready()` 不成立；老人答完陪同、出行、通知之后还会再走一遍 `checkSchedule`，**没有这个标记，同一个冲突会被问第二次，他永远到不了确认卡**。

`conflictKept` 刻意**不放进 `invalidate()`**：答「需要陪同」这类问题不该作废「保留时间」这个决定，而 `invalidate` 会被每一个 `SET_*` 动作触发。它的清零点是**换号源**（`#slotBlocked` 开头 `conflictKept=false`）与**新建办理**。

### 10.3 两条出口与「不静默覆盖」

| 用户选择 | 路径 | 结果 |
| --- | --- | --- |
| 换一个不冲突的号源 | `#selectSlot` → `advance` → `#checkSchedule` | `conflicts` 清空，确认卡不再有冲突行 |
| 明确保留冲突 | `KEEP_CONFLICT` → `#keepConflict` | `scheduleChecked=true`、`conflictKept=true`，进入后续检查 |

保留时确认卡会多一行：`已知冲突：与"社区体检"（10:00 至 11:00）时间重叠，您已选择保留`。**冲突不会被静默覆盖：保留只影响确认卡的内容，原有日程没有任何写操作。**

UI 上还有一条：**当天候选只给一个**（加上「重新选择日期」「仍保留这个时间」正好三个，一屏放得下）。给两个的话「仍保留这个时间」会被挤到第二页，老人翻不到。

## 11 情况九：同一时刻重复预约

`#checkDuplicate` 是提交前最后一道业务闸门。口径是 **同一位就诊人 + 同一天 + 同一个时刻**，**不再比医院和科室**：

> 老人只有一个身子，同一时刻不可能同时坐在两个科室里。同一天**换时段**仍然放行 —— 一天看两个科室是正常需求，只有时刻撞上才自相矛盾。改期时把原来那条自己排除掉（`originalAppointmentId`），否则「原时间不动、只换医生」会被自己拦下。

回复给三条出路：`保留已有预约`(CANCEL_TASK) / `重新选择时间`(CHANGE_TIME) / `查看我的预约`。当天的重复还会把日期说成「今天」而不是完整日期 —— 老人脑子里装的就是「今天上午我不是约过了吗」。

## 12 情况十：名称模糊 / 目录对不上

医院和科室都不信任模型给的名字，由 `CatalogEntityResolver` 在真实目录上判四种结果（`#resolveHospitalInput` / `#resolveDepartmentInput`）：

| 匹配结果 | 处理 | 状态影响 |
| --- | --- | --- |
| `EXACT` | 直接采用，`advance` 继续 | 正常 |
| `UNIQUE_APPROXIMATE` | `#rememberEntityCandidate` 暂存候选 → 问「是不是这家」 | `pendingEntityType/Id/Name/Raw`，等 `CONFIRM_ENTITY` / `REJECT_ENTITY` |
| `AMBIGUOUS` | 只列真实候选，请用户说完整名称 | 不猜、不选 |
| `UNCLEAR` | 引导去看就诊记录、预约通知、问家属或服务台 | 不新增名称 |
| 完全不匹配 | 明确说没找到 + **列出系统当前支持的医院/科室** | 绝不把不存在的名称写进流程 |

候选确认还有一个容错：`#handlePendingEntityConfirmation` 里，用户没答「是/不是」而是**直接给了另一个名称**时 —— 放弃旧候选、清空，让本轮重新解析。这避免了「必须先否定再重说」的两步卡顿。

科室这一路还有一条安全边界：**不依据症状推断科室**。`UNCLEAR` 的回复是「请查看上次病历或医生交代的复诊科室。仍不确定时可以咨询医院导诊台，我不会根据症状替您判断科室。」

## 13 情况十一：日期越界

号源可查范围是**今天到一个月后**，两处校验：

- `#continueCurrentFlow`：`facts.date()` 早于今天或晚于 `today+1month` → 「目前可以查询今天到一个月后的模拟号源」+ 「查看可预约日期」/「我自己说日期」按钮；
- `#changeDate`：同一口径；
- `#querySlots` 追加一条：日期已过去 → `resetAfterDate` + 回 `ASK_DATE`（「这个日期已经过去，请重新选择复诊日期」）。

## 14 情况十二：工具失败与部分完成

### 14.1 执行是可续的，不是原子的

`#confirm` 放行后**分步执行、每步成功即存**：

```
subimit/reschedule → materialReminder(前一天) → departureReminder(出发前10分钟) → family.notify → materialPreparation.initialize
```

每个 `*Done` 标志在成功后立刻 `conversations.save(state, null)`。因此**任一步抛异常时，已成功的步骤不会被重做**。

### 14.2 `#toolError` 的三分支

| 前提 | 新状态 | 措辞与出口 |
| --- | --- | --- |
| 有 `appointmentId` 且 `pendingAction == CANCEL` | `COMPLETED` | 「取消未完成，原预约保留：…」+ 已预约动作 |
| 有 `appointmentId`（预约已成功） | `PARTIAL` | **「预约已保留，后续事项未全部完成：…可补办未完成事项，不会重复预约」** |
| 无 `appointmentId` | `TOOL_ERROR` + `taskStatus=ACTIVE` | 「本步骤未完成：…已保留信息，请重试或修改」+ 重试检查 / 修改日期 / 人工帮助 |

### 14.3 `PARTIAL` 的补办

`RETRY_EXECUTION`（按钮「补办未完成事项」）→ 直接 `#buildConfirmation` 重新出确认卡。因为三个 `*Done` 标志已经记住了哪些成了，**重试只会执行失败的那几步**。结果卡的措辞也是分开的：`reminderStatusLabel` 会输出「复诊提醒已创建，出发提醒未完成」这类逐项状态，**绝不写成「办理失败」**（预约确实成了）。

### 14.4 照护端的可读错误

`#executeCaregiverBooking` 单独捕获 `IllegalArgumentException`（号源已失效、已有进行中的预约、关系被撤销）并**原样报出用户能听懂、也改得动的消息**，附「先取消已有预约 / 重新选择时间 / 联系人工帮助」。只有其他 `RuntimeException` 才落 `#toolError`。

## 15 情况十三：确认门禁与凭据失效

### 15.1 门禁是双重校验

```java
if (closed(state)) return closedResponse(state);          // ① 会话已结束
if (stopped(state)) return stoppedResponse(state);         // ② 已取消/紧急暂停
if (stage != AWAITING_CONFIRMATION || confirmationId == null
        || !confirmationId.equals(state.confirmationId)) {  // ③ 阶段 + 凭据
    return respondWithPlan(state, "这份确认已经失效或已办理，请查看当前计划后重新确认。", …);
}
state.confirmationId = null;   // ④ 单次消费
```

四道依次过：会话未结束 → 未停机 → 阶段与凭据都对 → 消费掉。

### 15.2 失效的两条保险

1. **显式 `#invalidate`**：清 `confirmationId`（改字段时由 `#applyFacts`、`SET_*`/`CHANGE_*` 按钮触发）；
2. **阶段隐式兜底**：即使 `confirmationId` 没被清，各 `CHANGE_*` / `resetAfter*` 都会把 `stage` 移出 `AWAITING_CONFIRMATION`，第 ③ 道就会拒绝。

`#buildConfirmation` 里还有一条反向保护：**重建卡片时保留原 `confirmationId`**（`if (confirmationId == null) 才新生成`）—— 用户在确认卡前说「打开地图」导致重述时，不会让已经看到的按钮突然失效。

### 15.3 拒绝确认（`approved == false`）也是一条完整分支

| `pendingAction` | 效果 |
| --- | --- |
| `CANCEL` / `CANCEL_EXISTING` | 清 pending 字段；有 `interruptedStage` → 回该阶段 + 「原预约已经保留，要继续刚才的办理吗？」；否则 `COMPLETED` |
| `MEMO` / `CANCEL_MANAGED` | 各自子分支 |
| 其他（预约） | `pendingAction=CREATE`；`appointmentId==null` → `READY_TO_PLAN` + `taskStatus=ACTIVE`；已有预约且都完成 → `COMPLETED`；否则 → `PARTIAL`。措辞：「没有执行本次操作，已有预约保留。您可以返回修改。」 |

**「返回修改」因此不是一句空话**：它把 stage 退回可编辑态，并附「修改日期 / 修改偏好 / 检查计划」三个按钮。

## 16 情况十四：终态守卫与会话生命周期

| 概念 | 判定 | 行为 |
| --- | --- | --- |
| `stopped` | `stage ∈ {CANCELLED, EMERGENCY_PAUSED}` | 见 §7.2 的白名单制守卫 |
| `closed` | `status == CLOSED` | `/messages`、`/actions`、`/confirmations`、图片入口一律 `#closedResponse`；**被拒的话不落库**（见 PITFALLS） |
| `EXPIRED` | 空闲超时 | `#reactivateIfExpired` 直接改回 `ACTIVE`：**只标记、不丢草稿**，老人过一会儿再说话照常继续 |
| `COMPLETED` | 办成 | 仍有 `EDIT_BOOKING`（变更草稿）、`CANCEL_APPOINTMENT`、`QUERY_APPOINTMENTS`、`NEW_BOOKING` 四条路 |
| `PARTIAL` | 部分完成 | 多一条 `RETRY_EXECUTION` |

`#closedResponse` **刻意不落库**：这是一句拒绝，不是一轮对话。落库的话，一个还开着确认卡的老页面每重试一次就多一条一模一样的「已经结束」，老人回头翻历史，真正聊过的内容反倒被一串复读淹掉。

## 17 情况十五：模型越权与规则回退

模型不能执行写操作，`AgentRuntime#modelProposal` 对模型动作逐条审核：

| 模型动作 | 审核 | 结果 |
| --- | --- | --- |
| `CALL_READ_TOOL(S)` 且工具在白名单、`risk == READ_ONLY`、角色可见 | `ToolPolicy#evaluate` | 通过 → 执行；>1 个时按依赖判断能否并行 |
| `CALL_READ_TOOL` 但工具是 `CONFIRMATION_ONLY` | 降级 | `DENY_SIDE_EFFECT` → **不执行，但转成进入 Java 确认流程**，不能静默变成一段没有卡片的回答 |
| 工具未注册 / 角色不可见 / 是写工具 | `REFUSE_UNSUPPORTED_TOOL` 或按 intent 回既有工作流 | **绝不执行**，也**绝不复用模型话术** |
| `CALL_CONFIRMATION_TOOL(interaction.requestConfirmation)` | `ToolPolicy#evaluateConfirmation` | 只进确认状态机 |
| `interaction.respondConfirmation` 且 `decision=CONFIRM/DENY` | 映射到 `CONFIRM_PENDING` / `DENY_PENDING` | 仍需 `confirmationId` 校验 |
| `ANSWER` / `ASK_USER` 且回复含「预约成功/已经取消/已通知家属/建议服用…」 | `ActionValidator#safeDirectReply` | 拒绝，转工作流 |

`ActionValidator` 是一道**文案级护栏**：模型可以自由说话，但不能在直接回答里声称任何未执行的写操作成功。禁止词包括「预约成功 / 已经预约 / 取消成功 / 已创建提醒 / 已通知家属 / 建议服用 / 增加剂量 / 我可以停药…」。

`REFUSE_UNSUPPORTED_TOOL` 单独成一个路由的设计理由（代码注释）：`DIRECT_ANSWER` 会 `pauseActiveTask`，把正在办的预约流程停掉；而「这条工具我不认」不该动任务状态。

### 规则回退模式的确定性护栏

模型不可用时，`AgentOrchestrator#deterministicOverride` 承接高价值口语：流程问句 → `QUERY_CARE_GUIDE`；含「预约/原来的号」+「取消/退掉/作废/不要」→ `CANCEL_EXISTING_APPOINTMENT`；不带筛选条件的短口令（≤10 字，且不含日期、医院、科室、「上次」类指代）→ 页面指令。**带日期或指代的长句一律交回模型**，否则「看看 9 月 8 号的地图」会被截成默认地图，用户说出的日期在 Java 阶段就丢了。

## 18 情况十六：身份与代办（同一套状态机）

- 会话身份两条轴：`userId`（数据轴，服务谁）与 `actorUserId`（能力轴，谁在操作），身份由 `AgentRole` 表示（`ELDER` / `FAMILY` / `VOLUNTEER`），**由后端查 `care_relations` 判定后固化进 `ConversationState`，不采信前端角色字段、也不由模型输出**。
- 为什么必须持久化：`POST /api/agent/confirmations` 只带 `conversationId`，不带身份 —— 不存下来，在确认那一刻就无从判断谁在替谁办理。
- **同一套状态机复用**，只有一处分支：`#notifySettled` 在 `caregiving()` 时直接返回 true，即**代办不问「通知哪位家属」**（操作者本人就是被通知方，且 `CareBookingService` 会自行通知其他照护者，选的这个联系人根本不会被用到）。
- 执行时 `#executeCaregiverBooking` 走 `CareBookingService`（带归属校验、防重复、给老人的提醒、对家属的协同通知），而不是在老人端重写一遍 —— 避免同一个业务有两条会逐渐走散的实现。
- 代办时的确认卡第一行必须说清「服务对象」；`actorId` 只用于关系校验与话术，**不注入任何工具参数**。

## 20 可以直接写进设计文档的几条结论

1. **失效是「按依赖」而不是「按步骤位置」**。改日期不清陪同，改科室才清 —— 因为陪同跟着人不跟日期。这比「改任何一步都回起点」体验好一个量级，也比「改了什么都不清」安全。
2. **「还不知道」与「已经明确不需要」是两个字段值，不是同一个 null**。`needCompanion = null`（没问过）与 `= false`（明确不要）驱动完全不同的按钮与话术。
3. **越界与紧急的处置方向相反，且都是有意的**：越界是「只插话、不改办」（保留确认卡，因为用户没说想中断）；紧急是「冻结 + 作废旧确认」（因为继续办就是错的）。
4. **异常分支不终止对话**。每个异常都给可继续的选项（换日期、换号源、保留、稍后再查、人工帮助），只有 `CANCELLED` 与 `EMERGENCY_PAUSED` 是「需要显式新建才能继续」的停机态。
5. **写入路径唯一**。模型、快捷按钮、图片输入全部经过 `#confirm` 的四道校验；`stopped` 与 `closed` 两道守卫在所有入口前置。
6. **展示文案与事实同源**。确认卡、完成卡、计划卡、越界提示块全部由 `ConversationState` 确定性拼装（`#confirmationCard` / `#plan` / `#completionNarration`），不经语言模型改写；因此「用户看到的」与「系统会执行的」不可能分叉。

## 21 复核时注意到的几处不对称（供参考，未改动代码）

以下不是 bug 结论，只是读代码时发现的**口径不完全一致**处，若设计文档要写「实现与设计完全一致」，建议先确认：

1. **`#resetAfterDepartment` 不自行调用 `#invalidate`**（`#resetAfterDate` / `#resetAfterHospital` 都调）。按钮路径下没问题（`#actInternal` 对 `CHANGE_*` 先统一 `invalidate`），模型路径下（`dispatchOutcome` → `#changeDepartment`）`confirmationId` 未被显式清空，靠 `stage` 移出 `AWAITING_CONFIRMATION` 让 `#confirm` 的第 ③ 道拒绝。行为上安全，但「失效」有两条不同来源，写文档时不宜说成单一机制。`#changeTime` 同此模式（清 `selectedSlot` + 改 stage，未显式清凭据）。
2. **模型模式下紧急词表不前置**。`SafetyGuard#precheck` 的紧急词表只在 `!modelAvailable()` 时执行；模型模式认主模型的 `EMERGENCY` intent，**没有**像越界那样补一道 `looksLikeMedicalAdvice` 式的规则兜底。这一点 `docs/13-demo-scenarios-workflow.md` §7.1 已有记录，与 `Design.md` 中「高优先级规则前置」的目标之间存在差距。
3. **`#resetAfterDepartment` 会把 `acceptAlternative` / `needCompanion` / `needTravel` / `notifyFamily` / `transport` 全部置 null**，而 `#resetAfterDate` / `#resetAfterHospital` 不置 null（`resetAfterHospital` 把它们留在原值）。前者是「科室变了，这些结论可能不成立」，后者是「医院变了但陪同需求还在」—— 口径可以解释得通，但三者的清场范围差异较大，文档里值得明确写出各自的理由。
