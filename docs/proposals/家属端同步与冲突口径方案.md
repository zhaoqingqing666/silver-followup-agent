# 家属端（协同照护端）：医生号源同步、老人自约可见、冲突口径收口

> 状态：**A 已实施**（纯前端，`tsc --noEmit` 通过，3 文件 +13 行）；
> **B 待确认**；**可见性口径（第五节）推荐"不改可见性、只把文案说准"**——理由与替代方案在第五节。
> 需求来源：2026-09-16 业务口径补充（家属端"智能性可以不高"；"只有老人通知了家属，家属那边才能看到预约"）。
> 相关文档：`records/DECISIONS.md`（DEC-024、DEC-025、DEC-026、DEC-029、DEC-032）、
> `records/PROGRESS.md`（「待后续 ② 照护端口径差」）、`records/INTERFACE_CHANGES.md`。
> 涉及需求：家属/志愿者代约；家属端要能看清"约的是谁"；同一位就诊人的预约冲突判定。

## 〇、先把补充理解清楚（若与你的意思不符，先改这里再谈方案）

1. **家属端"帮助预约"的智能性可以不高。** 家属不像老人，本来就会自己预约。
   ⇒ 老人端助手侧那套"智能"**不搬**：不搬自然语言解析、不搬冲突预检的对话流、
   不搬"今天上午的号已经过了"这类半天理由口播、不搬快捷按钮分页。只做**数据与展示层**的同步。
2. **只把这次加的「医生 / 号别 / 挂号费」相关逻辑同步到家属端。**
   ⇒ 家属在任何一个页面都该看得见"约的是哪位医生、什么号别、多少钱"。
3. **老人自己约的，家属端要能直接看到。**
4. **改掉口径冲突。** 家属端 `CareBookingService.hasUpcoming()` 现在是「同一位老人名下**只留一个**进行中预约」，
   比老人端严；改成与老人端一致——**同一位就诊人 + 同一天 + 同一时刻**才算冲突，
   同一天换时段/换医生照旧放行。
5. **（新增，2026-09-16 晚）"只有老人通知了家属，家属那边才能看到预约"。**
   ⇒ **这一条我建议不做**，理由见第五节；替代做法是**把老人端那几句"不通知家属"改成说准**。

一句话概括这次的范围：**家属端只补"看得见"和"口径一致"，不补"更聪明"、也不补"更难看见"。**

## 二、方案

### A. 家属端四处补医生 / 号别 / 挂号费 —— 纯前端，零后端 ✅ 已实施

统一调 `doctorLine(row)`，与老人端共用同一份拼法（连带继承"医生信息未记录"的兜底）。

| # | 文件 | 位置 | 状态 |
|---|---|---|---|
| A1 | `care-appointments-view.tsx` | 预约列表卡片（科室下面加一行） | ✅ |
| A2 | `care-appointment-detail-view.tsx` | 复诊详情页（科室下面加一行） | ✅ |
| A3 | `care-booking-view.tsx` | 帮助预约**第 3 步确认页**（科室·就诊位置下面） | ✅ |
| A4 | `care-booking-view.tsx` | 帮助预约**"现有安排"管理视图**（医院·科室下面） | ✅ |

实际改动：3 个文件 +13 行（含 2 处 `import`），`tsc --noEmit` EXIT=0。`lib/appointment-display.ts` 一字未动。

**仍不做**：家属端首页那行摘要（`care-home-view.tsx:31-37` 的 `elderLine()`）不放医生——
那行是"医院 科室"级别的**单行**摘要（`truncate`），塞医生会挤掉医院名；而且它是**本轮唯一需要动接口契约**的地方
（`ElderSummary.AppointmentSnapshot` 不含医生四个字段），收益只是摘要多几个字。见 C 段。

### B. 冲突口径收口 —— 后端，唯一有行为变化的一处

**B1. 把 `hasUpcoming()` 换成老人端同口径。**

老人端这条规则的**唯一出处**是 `FollowupAgentService.slotDuplicates()`（`:3770-3777`）：
用 `search(userId, date, null, null)` 取该人**当天全部**预约，再按 `time` 相等过滤
——即 **同一位就诊人 + 同一天 + 同一时刻**（不分医院、不分科室），同日换时段放行。

落地两种做法，建议先 a：

- **B1-a（小，本轮推荐）**：`CareBookingService` 里按同口径自己判一遍，
  `records.allFor(elderUserId)` 过滤 `status=CONFIRMED && date.equals(选中日) && time.equals(选中时刻)`。约 5 行。
- **B1-b（中，可后置）**：把"同日同时刻"抽成 `AppointmentTool` 上的一个查询方法
  （如 `findSameMoment(userId, date, time)`），老人端 `slotDuplicates` 与家属端都调它。
  好处是**规则只有一处实现**（与 DEC-025「冲突只有一处实现」的精神一致）；
  代价是 `AppointmentTool` 是接口、`MockAppointmentTool` 是唯一实现，**这是一次真正的接口改动，要登记 `INTERFACE_CHANGES.md`**。

**B2. 行为变化（要写进 DEC）：**

- 家属现在能给同一位老人约**同一天的不同时段**（例如已有 14:00，再约 10:30 → 放行）；
- **同一时刻仍然被拦**（例如已有 10:30，再约 10:30 → 拒绝）。

**B3. 拒绝话术要跟上。** 现在那句"这位就诊人已有一个进行中的复诊预约，请先调整或取消已有预约，再重新安排"
在新口径下已经**不准确**（明明只是同一时刻撞了）。建议改成与老人端一致的"这个时段已经预约过了"，
并按"是否当天"决定用"今天"还是具体日期（老人端 `duplicateReply` 就是这么分的）。

**B4. 连带影响（放开口径后唯一真正的风险点，必须一起处理）。**

`modify()`（`:173-176`）、`toggleAccompany()`（`:242-245`）、`cancelUpcoming()`（`:318-321`）三处都是：

```java
records.allFor(elderUserId).stream()
    .filter(item -> "CONFIRMED".equals(item.status()) && !item.date().isBefore(clock.today()))
    .findFirst()   // ← 因为"只会有一张"，从没关心过拿到的是哪一张
```

口径放开后"进行中"会有多张，`findFirst()` 就成了"最近创建的那张"（`allFor` 按 `created_at DESC`）——
**家属点"调整这次复诊"，改到的可能不是他正在看的那一张。** 这不是理论风险，是这次改动直接引入的。

前端同一处也有：`care-booking-view.tsx:107` 用 `rows.find(...)` 挑"当前这张"来决定进管理视图还是进向导。

三种处理方式，**需要你拍板**：

| 方案 | 做法 | 代价 |
|---|---|---|
| ① 保持现状 | `findFirst()` 不动，前端也取第一张 | 改动最小；但"改错一张"是静默的，家属看不出来 |
| ② **按 id 操作**（建议） | 前端把手上那张的 `appointmentId` 一起传上来；`modify`/`cancel`/`accompany` 优先按 id 定位，取不到再退回"唯一一张"的旧行为 | 后端 3 处加个可空参数，前端 3 个调用点带上 id；接口请求体有变化 |
| ③ 管理视图列出全部 | 管理页改成"进行中的复诊"列表，逐条可改/可取消 | 最一致，但这一屏要重画，超出"智能性可以不高"的范围 |

### C. 家属端首页摘要要不要带医生 —— 可选，本轮建议不做

家属首页那张"最近预约"走的是 `CareService.latestSnapshot()`（`:200-213`），
快照 record `ElderSummary.AppointmentSnapshot`（`:253-257`）**不含医生四个字段**。

- 要做：改后端 record + 前端 `CareAppointmentSnapshot`（`types/domain.ts:284-299`）+ 登记 `INTERFACE_CHANGES.md`。
- **建议本轮不做**：这是本轮唯一需要动接口契约的地方，而收益只是首页一行摘要多几个字；
  点进"复诊预约"就能看到医生（A1/A2 已覆盖）。

### D. 明确不做（写下来免得以后被当成漏做）

- **不搬老人端助手侧的智能**：不搬 `halfReason` / `noSlotLead`（"今天上午 9 点、10 点半的号已经过了"）、
  不搬冲突预检的对话流、不搬快捷按钮每屏 3 个的分页、不改家属端助手的布局（DEC-029 的承诺继续有效）。
  理由：你已定"家属端智能性可以不高"，而且家属端的冲突提示本来就是浏览器盯着页面就能避开的事。
- 不改老人端任何行为（第五节的文案除外）、不动额度/名额模型、不动排班、**不动 `schema.sql`**。
- **不动 `care-assistant-view.tsx`**：家属端助手接的就是**同一个** `FollowupAgentService`
  （`startConversation(elderId, caregiverId)`），DEC-032 的时钟、"已经过了"话术、DEC-031 的冲突预检
  **在那边本来就已经同步**，不需要重复做。
- 暂不处理家属端那三份客户端"今天"（`care-home-view.tsx:19-28`、`care-appointments-view.tsx:20-25`、
  `care-booking-view.tsx:35-40` 各写了一遍 `todayLocal()`），与 DEC-032 的"客户端算出今天"是同类问题。
  本轮只做展示与口径，**留待后续**。

## 三、可见性口径（原问题 2）："通知了家属才可见" —— **推荐不做**

### 3.1 需求与现状的差距

**需求**：只有老人选了"通知家属"，家属端才看得到这张预约。

**现状**：卡片与消息是两条独立的出口——

| 出口 | 数据来源 | 受老人选择控制吗 |
|---|---|---|
| 卡片（复诊预约列表 / 详情 / 首页摘要） | `appointments` 表，`AppointmentRecordStore.allFor(userId)`（`:36-72`） | **否**，无条件可见 |
| 就诊动态 | `CareService.timeline():121-137`（聚合 `tool_call_logs`） | **否** |
| 消息通知 | `family_notifications`（唯一写入方 `MockFamilyNotificationTool.notify`） | **是** |

⇒ 老人选"不通知"，只等于**不发消息**，不等于"家属不知情"。

### 3.2 为什么现有字段撑不起来（三个候选都被排除）

1. **`family_notifications` 没有 `appointment_id`。** 字段只有
   `id / contact_id / content / status / created_at`（`schema.sql:213-219`）——它记的是"发过哪些消息"，
   不是"哪张预约授权给谁看"，**反查不出可见性**。
2. **`contact_id` 上根本没有家属账号维度。** 它指向 `family_contacts`，而 `CareService:84-90` 是拿
   `fc.user_id` 去 join `users` 取**长辈**名字的；家属账号在另一张表（`care_relations.caregiver_id`）。
   ⇒ "通知了**谁**、**谁**才可见"在数据上做不到，**最多退化成"通知过任意一位家属 ⇒ 全体家属可见"**。
3. **`appointments.family_status` 是写给人念的句子，不能当判据。**
   它存的是 `无需通知家属` / `家属通知未完成` / `已通知女儿 余柔欣`（`FollowupAgentService:1777-1780`）。
   拿它当过滤条件，文案一改就**静默失效**——这正是 DEC-026 那条"结果写死在行上、但别去解析它"的边界。

⇒ 真要做得干净，**必须新增一列**（如 `family_visible BOOLEAN`），在写 `family_status` 的同一处按
`state.notifyFamily` 写死（两者同源，才不会各说各话）。

### 3.3 硬做的代价（第 2 条是硬伤）

1. **要动 schema**：`ALTER TABLE appointments ADD COLUMN IF NOT EXISTS family_visible BOOLEAN DEFAULT TRUE`
   （本仓库现成惯例），写入点 1 处、代约另置 TRUE、改期保留原值。
2. ⚠️ **`hasUpcoming()` 不跟着改就会死锁。** 它查的是**全表**（`CareBookingService:269-272`），不看可见性：

   > 老人自约 + 选"不通知" → 家属端列表空、首页"最近预约"空 → 家属以为没安排，
   > 一点"帮助预约"却被拒「这位就诊人已有一个进行中的复诊预约」，
   > 而他在界面上**既看不到这张、也没法取消或改期**。

   解开只有两条路，都很难看：

   - **a) 校验也只算可见的那些** ⇒ 家属能再约一条，出现"同一老人同一时刻两条预约"——
     **这正是老人端明令禁止的情形**（DEC-025 / DEC-030），等于家属端比老人端更松；
   - **b) 校验保持全表，家属端被拦时明说"已有一项预约未同步给您"** ⇒ **等于泄露了存在性**，
     隐私收益基本归零，还多出一句解释不清的话。

3. **改动面横跨全部读取点**：`allFor` 要分视角，但 `/api/users/{elderId}/appointments`
   是**老人端与家属端共用**的接口 ⇒ 加视角就要加查询参数或新开接口（**真正的接口改动，要登记
   `INTERFACE_CHANGES.md`**）；再加 `CareService` 两处（`latestSnapshot`、`alertFor`）、前端三处、
   `care-booking-view.tsx:107` 的"进行中"判断。还有一条隐蔽的：**"就诊动态"要不要一起挡**——
   `CareService.timeline()` 第 1 段走的是 `tool_call_logs`，卡片挡住了，时间线照样会说"预约已提交并确认"。

### 3.4 我的推荐：**不做可见性，只把老人端那几句"不通知家属"改成说准**

理由（按重要度）：

1. **与产品定位相悖。** 这是"协同照护"端，家属是执行方（陪同、送医、代约、看路线）。
   让预约对家属隐形，家属就没法陪同，也无法解释"为什么这里叫协同"。演示时更容易出"家属端一片空白"的尴尬。
2. **语义本来就已经是清楚的，是文案在骗人。** 老人选的从来是"**发不发这条消息**"，
   不是"能不能看见"。而老人端确认卡上直接写着 **`不会通知家属。`**（`FollowupAgentService:3963`）、
   确认卡条目写 **`不通知家属`**（`:3929`）、预约行上写 **`无需通知家属`**（`:1778`）。
   三句都让人以为"家属不知情"，而事实是家属在协同页看得到。
   **把这三句改成说清"不发消息、家属仍可在协同页看到"，成本极低，是这次真正该做的。**
3. **成本与收益倒挂。** 按 3.3，改动面横跨 schema / 后端 5 处 / 接口契约 / 前端 3 处 / 测试若干，
   换来的是一个会制造死锁、且会泄露存在性的半吊子隐私。

**具体改法（未实施，等你点头）——4 处文案，其中 1 处要同步改一条断言：**

| 位置 | 现在 | 建议改成 |
|---|---|---|
| `FollowupAgentService:3963`（结果口播） | `不会通知家属。` | `不额外给家属发消息；家属在"就诊动态"里仍能看到这次安排。` |
| `FollowupAgentService:3929`（确认卡条目） | `不通知家属` | `不给家属发消息（协同页仍可见）` |
| `FollowupAgentService:1778`（预约行 `family_status`） | `无需通知家属` | `未发送通知（协同页可见）` |
| `FollowupAgentService:3081`（问句 + 按钮） | `需要通知家属吗？` / `需要通知` / `不用通知` | `要不要给家属发一条消息？` / `要发` / `不发` |

已在测试里查过，代价很小：

- `SilverAgentApplicationTests:377` 断言 `contains("不通知家属")` ⇒ **要跟着改**（1 条）；
- `CaregiverSessionTests:146` 是 `doesNotContain("不会通知家属")`（代约路径）⇒ **不受影响**；
- `无需通知家属` 没有任何测试钉住。

### 3.5 如果一定要做，最佳设计（连同它仍然抹不掉的三个洞）

1. `schema.sql`：`appointments` 加 `family_visible BOOLEAN NOT NULL DEFAULT TRUE`（存量数据可见）。
2. 写入：放在 `FollowupAgentService` 写 `family_status` 的**同一处**（`:1777-1780` 附近），
   值取 `state.caregiving() || Boolean.TRUE.equals(state.notifyFamily)`；
   `CareBookingService.book()` 代约置 TRUE；`modify()` 保留原值（不要重算）。
