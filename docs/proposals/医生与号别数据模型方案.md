# 医生与号别：数据模型改造方案

> 状态：**阶段 1 已实施**（2026-09-13，见 DEC-021），其中**排班那部分已被 DEC-022 重做**；**阶段 2 未开始**。
> 本文保留当初的方案与取舍，落地时实际选定：号源 id 走 **B1**、`slot_type` **手工指定在医生行上**（不按职称推导）、
> 老号源**整批重建**（不回填默认医生）、**加 `fee_cents`（以分为单位）**。
> ⚠️ **唯一一处口径已经改了**：本文提的「错开出诊星期」已被 **DEC-022 撤销**——排班改成「每科室固定 3 个放号日 ＋
> 上午 1 位专家 + 1 位普通 / 下午 1~2 位」，即用**「上午 / 下午」分组**替代原来的「同一天只有一位医生」来组织候选。
> 阶段 1 只做数据模型 + 数据库字段 + 前端展示，**不动交互**；阶段 2 才接「助手推荐 / 直呼姓名」两条选医路径。
> 涉及需求：号源要能区分「普通号 / 专家号」；一个科室要有多个医生；医生带姓名与职称；
> 选医生有两条路——助手推荐、或老人直接说名字。
> 相关文档：`06-mock-data-design.md`、`05-api-contracts.md`、`records/DECISIONS.md`（DEC-021）、`records/INTERFACE_CHANGES.md`。

## 一、结论先说

**号源表要加「医生」这一维，号别挂在号源上、跟着医生走。**

现在的号源表是「科室 × 日期 × 时间」；改完之后是「医生 × 日期 × 时间」。
一个科室有几个医生，同一天同一时段就会有几条号源，医生各自的职称决定这条号源是普通号还是专家号。

---

## 二、现状：三张表 + 一个生成器

### 2.1 表

```
hospitals(h001 市第一医院, h002 市人民医院)
  └─ departments(d001 心内科, d002 神经内科, d005 内分泌科, d003 内分泌科, d004 骨科, d006 心内科)
        └─ clinic_locations(loc-d001 …)      ← 只回答「在哪看」，不含医生
appointment_slots(id, hospital_id, hospital_name, department, date, time, available, clinic_location_id)
appointments(id, slot_id, user_id, status, created_at, departure_time, transport,
             reminder_status, family_status, materials, conversation_id, arranged_by, accompanied_by)
```

现有数据：**2 家医院、6 个科室、601 条号源（598 条空闲）、5 条预约记录**。

### 2.2 号源生成器 `RollingAppointmentSlotInitializer`

- 每个启用科室 × 今天起一个月内每个**工作日** × 4 个固定时段（09:00 / 10:30 / 14:00 / 15:30）；
- 号源 id = `r-<科室id>-<yyyyMMdd>-<HHmm>`，例如 `r-d006-20260917-0900`；
  注释里写明这是**硬约定**（"只此一处"），回滚重放、场景重置、回归用例都按这个拼法找号源；
- 周末**故意不排**，留给「当天暂无号源」的演示场景。

### 2.3 三个结构性事实，决定了方案的形状

| # | 事实 | 影响 |
|---|---|---|
| 1 | `appointment_slots.department` 存的是**科室名字**（字符串），不是 `departments.id` 外键 | 医生没法直接用科室外键串起来，需要补一列 `department_id` |
| 2 | 号源**完全没有医生维度**，同一科室一天 4 条号源除了时间没有任何区别 | 现在根本表达不了「普通号 / 专家号」 |
| 3 | `appointment_slots.hospital_id` 存的是**医院 id**，但号源 id 里嵌的是**科室 id** | 字段名与内容错位，加医生时容易顺手写错，建议一并理清 |

## 三、需求拆成 6 条可验证的约束

1. 医生有**姓名**和**职称**；
2. 一个科室有**多个**医生；
3. 每条号源可判定是**普通号**还是**专家号**；
4. 不同医生放出的号别**可以不同**；
5. 老人可以说「我要专家号」，助手能**只推荐专家号**；
6. 老人可以直接说「我要找张医生」，助手能**按姓名定位到医生**（重名要列出来让他选）。

## 四、表设计

### 4.1 新增 `doctors`

```sql
CREATE TABLE IF NOT EXISTS doctors (
  id            VARCHAR(40)  PRIMARY KEY,   -- doc-<科室id>-<序号>，如 doc-d006-01
  hospital_id   VARCHAR(40)  NOT NULL,
  department_id VARCHAR(40)  NOT NULL,
  name          VARCHAR(40)  NOT NULL,
  title         VARCHAR(40)  NOT NULL,      -- 主任医师 / 副主任医师 / 主治医师 / 住院医师
  good_at       VARCHAR(300),               -- 擅长，推荐时要念给老人听
  introduction  VARCHAR(300),
  enabled       BOOLEAN DEFAULT TRUE NOT NULL
);
```

id 沿用仓库现有风格（`d001`、`loc-d001`、`m001`）：**科室 id 打头**，好处是看号源 id 就能反推科室。

### 4.2 号别放哪：挂号源，规则来自职称

两个选择：

- **A. 号别挂医生**（`doctors.default_slot_type`），号源继承。
  简单，但表达不了「同一个医生既出普通号又出专家号」。
- **B. 号别挂号源**，由排班决定。
  灵活，但严格来说要引入 `doctor_schedules` 排班表。

**推荐 B 的轻量版**：`appointment_slots` 加 `doctor_id` + `slot_type`，`slot_type` 由生成器按
「医生职称 → 号别」推导（主任医师 / 副主任医师 = 专家号，主治 / 住院医师 = 普通号）。
先不建排班表——演示要的是「不同医生放不同号」，不需要真排班。
将来真要「同一医生两种号」，只需再加 `doctor_schedules` 覆盖 `slot_type`，**列不用改**。

### 4.3 `appointment_slots` 扩展

```sql
ALTER TABLE appointment_slots ADD COLUMN IF NOT EXISTS doctor_id     VARCHAR(40);
ALTER TABLE appointment_slots ADD COLUMN IF NOT EXISTS slot_type     VARCHAR(20);  -- NORMAL / EXPERT
ALTER TABLE appointment_slots ADD COLUMN IF NOT EXISTS department_id VARCHAR(40);
ALTER TABLE appointment_slots ADD COLUMN IF NOT EXISTS fee_cents     INT;          -- 可选：挂号费
```

- `department_id` 是为了不再靠「科室名字」做关联（改一次名字就断）；
- `department` 名字列**保留不动**，现有查询和前端都不用改；
- `ALTER … IF NOT EXISTS` 是仓库既有风格（`schema.sql` 通篇如此），旧库启动时自动长出列。

### 4.4 `appointments` 要存医生快照

**要存。** 理由：号源会被滚动重建（周末号源会删、老日期会过期），预约记录必须自己说得清「当时约的是谁」。

```sql
ALTER TABLE appointments ADD COLUMN IF NOT EXISTS doctor_name  VARCHAR(40);
ALTER TABLE appointments ADD COLUMN IF NOT EXISTS doctor_title VARCHAR(40);
ALTER TABLE appointments ADD COLUMN IF NOT EXISTS slot_type    VARCHAR(20);
```

这与 `appointments` 现在的做法一致——`reminder_status` / `family_status` / `materials`
都是把结果写死在预约行上，而不是每次去关联查询。

## 五、号源生成器怎么改

`RollingAppointmentSlotInitializer.seed()` 现在是「遍历科室」，改成「遍历科室 → 遍历医生」：

```
for 科室 in 启用科室:
    for 医生 in 该科室的启用医生:
        for 日期 in 今天..一个月（跳过周末）:
            for 时段 in [09:00, 10:30, 14:00, 15:30]:
                插入号源(doctor_id, slot_type=按职称推导, department_id, fee_cents)
```

### ⚠️ 号源 id 拼法是本次最关键的一个决定

现状：`r-<科室id>-<yyyyMMdd>-<HHmm>`。
加了医生之后，同一科室同一时段会有 N 条号源，**id 必须带医生 id，否则会撞主键**。

两个选项：

| 方案 | 拼法 | 代价 |
|---|---|---|
| **B1（推荐）** | `r-<医生id>-<yyyyMMdd>-<HHmm>`，如 `r-doc-d006-01-20260917-0900` | 改 `slotId()` 一处；但所有**按前缀找号源**的地方（回滚重放、场景重置、回归用例）要一起核 |
| B2（兼容） | 保留 `r-<科室id>-…` 当「科室通用号源」，另加 `r-<医生id>-…` | 不用改老拼法，但两套号源并存，「点进去看到的是谁」会含糊 |

推荐 **B1**：医生 id 里本来就含科室 id，语义比现在更准。
**但这是一次跨模块的约定变更**，按仓库惯例应当先在 `DECISIONS.md` 登记一条，再动手。

**推荐规则建议**（复用已有的 `REQUEST_RECOMMENDATION` 意图，不新造一套）：

1. 老人说了症状或科室 → 在该科室医生里选：**先看谁最近有可约号源**，同样有号时**职称高者优先**；
2. 老人说「要专家号」→ 只列 `slot_type = EXPERT` 的号源；
3. 老人说了医生姓名 → 在该科室/该医院内精确匹配 `doctors.name`；**命中多人（重名）必须把几位都列出来让他选**，不能替他挑一个。

## 七、兼容与迁移：两个必须处理的坑

### 坑 1：601 条老号源会变成「没有医生的号」

滚动生成器**只插入、不更新**。新加的 `doctor_id` 在存量号源上是 `NULL`，
如果不管，演示时点进去会看到「医生：—」。

处理方式（二选一）：

- **回填**：在 `data.sql` 或生成器里补一步——`doctor_id IS NULL` 的号源，按 `department` 匹配该科室**排序第一名**医生，`slot_type` 记为 `NORMAL`；
- **重建**：让生成器在检测到「该科室还没有带医生的号源」时，把老号源删掉重新生成（周末清理逻辑已经是这个套路，改造成本低）。

推荐**重建**：反正号源是滚动生成的演示数据，删了不心疼，也不会留下半新半旧的两套。

### 坑 2：老预约记录没有医生信息

`appointments.doctor_name / doctor_title / slot_type` 在 5 条既有记录上是 `NULL`。
- 前端**必须优雅降级**：显示「医生信息未记录」，而不是空白或 `null`；
- 不要为了让页面好看去**伪造**医生名——这与仓库「不虚构任何内容」的既有约定（见 `appointmentNarration` 注释）冲突。

## 十、风险

- **号源条数会翻几倍**（601 → 约 1800）：**当时靠「错开出诊星期」消解**——同一科室同一天只有一位医生
  在诊，实际约 496 条。**但这个风险后来真的回来了**：需求要「选好科室和日期后，列出这天有哪几位医生可约」，
  一天只有一位医生等于没有可选性，于是 DEC-022 撤销了错开，改成「每科室固定 3 个放号日 ＋ 上午 1 专家 +
  1 普通 / 下午 1~2 位」。**本段当初预判的缓解办法正是最后采用的办法**——按「上午 / 下午」分组组织候选，
  并让单次最多只给老人 **2 个候选号源**。总量仍在几百条量级（每科室每周 3 天）。
- **科室名字串关联**是个隐雷：`appointment_slots.department` 与 `material_templates.department`
  都是按**名字**匹配的。本次会补 `department_id`，但短期内两套并存，改科室名时要记得两边都改。
  〔**已经应验过一次**：排班重做时新写的回归用例按 `department`（名字）分组，把两家医院同名的
  「心内科」「内分泌科」并成一组，断言数字静默翻倍——凡按科室聚合 / 判重一律用 `department_id`，
  见 `records/PITFALLS.md` 2026-09-13 同名条目。〕
- **`care_relations` / 代约流程**也吃号源列表，阶段 2 改 `CareBookingService` 时要一起回归。
