# 科室扩到「两院各 6 科」＋号源加名额：数据层改造方案（阶段 1）

> 状态：**已实施（2026-09-14）**，落地为 `records/DECISIONS.md` 的 **DEC-026**。
> 本文保留为设计依据与影响面清单；与实现的一处出入是**名额字段名**——实际用的是
> `capacity` / `booked`（`available` 降级为派生位），不是需求稿里的 `stock`，理由见 DEC-026 决定四。
> 阶段边界：**只动数据层**（`schema.sql` / `data.sql` / 生成器 / 号源的扣减与释放），
> **不动助手的交互逻辑**（推荐排序、去重、口播、候选卡片、前端展示字段）。与 DEC-021 那次的分期方式一致。
>
> 涉及需求：
> ① 两家医院都要有 心内科 / 神经内科 / 内分泌科 / 骨科 / 呼吸内科 / 消化内科；
> ② **每科室 4 名医生**（01 主任医师 + **04 副主任医师** + 02 / 03 主治医师）；
> ③ 主任（含副主任医师）只出**专家号**、主治只出**普通号**；
> ④ **上午、下午都要有专家号和普通号**；
> ⑤ 每位医生在本科室 3 个放号日里**至少出诊一次**；
> ⑥ 同一时段专家号放 **3** 个名额、普通号放 **4** 个名额（新增 `stock` 口径）；
> ⑦ 科室在原有 id 基础上**追加**（d007~d012），现有 d001~d006 不动。
>
> 相关文档：`records/DECISIONS.md`（DEC-021/022/023/024/025）、`proposals/医生与号别数据模型方案.md`、
> `06-mock-data-design.md`、`records/PITFALLS.md`。

## 一、这一版相对上一版改了什么

你这次要「每个科室再加一个主任」，理由是「只有一个主任的话，他 3 天都要出诊、每天 2 次，比主治还忙」。
这个判断是对的，加上第二个主任后，排班从下面左列变成右列：

| 上一版 | 本版（你这次定的） |
|---|---|
| 每科室 **3** 位医生（1 主任 + 2 主治） | 每科室 **4** 位医生（01 主任医师 + **04 副主任医师** + 02 / 03 主治医师） |
| 1 位主任上下午各坐 1 格 = 每天 2 格 / **每周 6 格** | 两位主任在 3 天里**对调上下午** = 每位每天 1 格 / **每周 3 格** |
| 主任 6 格 vs 主治 3 格（**主任比主治忙一倍**） | 四位医生**各 3 格，完全相等** |
| 医生总数 18 → 36 | 医生总数 18 → **48** |

**其余全部保留**：科室追加 d007~d012、放号日「同院内不重复」、
`capacity` / `booked` 两列与 `available` 降级为派生位、名额 3 / 4、
「普通号名额 > 专家号名额」按名额比、启动自愈、四个槽位的时刻与号别。

## 二、结论先说

1. **号源条数与名额数一条都不变。** 每天仍是 4 格、每格 1 位医生 ⇒ 每科室每放号日 **4 条号源 / 14 个名额**。
   这次改的只是「**谁坐哪一格**」，所以 §3.5 的量级表、既有 `200~1200` 条断言、`capacity` 合计口径**都不用重算**。
2. **每科室 4 位医生**：`MAX_DOCTORS_PER_DEPARTMENT` 由 3 改 4；种子从 18 位扩到 **48 位**（新增 30 位）。
3. **四位医生工作量完全相等**：01 主任 3 格、04 副主任 3 格、02 / 03 主治各 3 格 —— 这正是你要的效果。
   在「主任只出专家号 + 上午下午都要有专家号」这两条约束下，这是**唯一的均衡解**（§3.4 有推导）。
4. **号源表加两列**：`capacity`（这一班放几个名额）+ `booked`（已占几个），
   `available` **保留但降级为派生位**（`available = booked < capacity`）。
   → **查询侧一行都不用改**（推荐 / 列号 / 可约日期 / 照护端代约仍按 `available=TRUE` 过滤）。
   这是「只改数据库、不动助手交互」能成立的**唯一**做法。
5. **名额按号别取**：`EXPERT = 3` / `NORMAL = 4`，写在生成器里（与 `fee_cents` 同一套「号别 → 数值」的做法）。
6. **排班改动集中在生成器一处**：`morningDoctors` / `afternoonDoctors` 换成**按时刻取人**，
   `doctorsAt` 跟着改。号源 id 拼法、`openWeekdays` 的确定性、周末不放号**全部不动**。
7. **代价（必须先说）**：
   - **「下午没有专家号」这个演示场景消失**（这是上一轮「上午下午都要有专家号」的必然结果），
     `AfternoonExpertGuardTests`（4 条）整份作废，`DoctorIntentTests` 有 3 条依赖它；
   - **「点名本科室医生、他当天不出诊」这个场景也消失**——新排班里每位医生每个放号日都在岗（§11）。
   这些是**产品规则变了**，不是掩盖问题，改完必须同时补上新口径的正向用例（§9）。

### 3.2 4 个时刻与号别（不变）

| 时刻 | 号别 | 名额 | 出诊医生 |
|---|---|---|---|
| 09:00 | `EXPERT` | 3 | 01 或 04 号（按放号日轮换） |
| 10:30 | `NORMAL` | 4 | 02 或 03 号（按放号日轮换） |
| 14:00 | `EXPERT` | 3 | 04 或 01 号（与上午对调） |
| 15:30 | `NORMAL` | 4 | 02 或 03 号（与上午对调） |

上午 = 09:00 专家 + 10:30 普通；下午 = 14:00 专家 + 15:30 普通。**上午、下午都有专家号和普通号** ✓

**为什么专家格取每半天的第一格（09:00 / 14:00）**：10:30 是 `DemoSeed.conflictingSlot()`
用的冲突格（号别无关，保住它「和体检撞车」的语义）；09:00 是 `DemoSeed.MORNING` 的锚点。

### 3.3 三天轮换表

以 `openWeekdays = {1,3,5}` 的科室（d001）为例，`roleIndex` 是这天在本周放号日里的序号（0/1/2）：

| 放号日 | roleIndex | 09:00 | 10:30 | 14:00 | 15:30 |
|---|---|---|---|---|---|
| 第 1 天（周一） | 0 | 01 主任·专家 | 02 主治·普通 | 04 副主任·专家 | 03 主治·普通 |
| 第 2 天（周三） | 1 | **04 副主任·专家** | **03 主治·普通** | **01 主任·专家** | **02 主治·普通** |
| 第 3 天（周五） | 2 | 01 主任·专家 | 02 主治·普通 | 04 副主任·专家 | 03 主治·普通 |

**核心是中间那一天（roleIndex = 1）两位主任上下午对调**，第 1 天与第 3 天相同。逐人核对格数：

| 医生 | 第 1 天 | 第 2 天 | 第 3 天 | 合计 |
|---|---|---|---|---|
| 01 主任 | 09:00 | 14:00 | 09:00 | **3 格** |
| 04 副主任 | 14:00 | 09:00 | 14:00 | **3 格** |
| 02 主治 | 10:30 | 15:30 | 10:30 | **3 格** |
| 03 主治 | 15:30 | 10:30 | 15:30 | **3 格** |

**四位完全相等，每人 3 天都在诊、每天恰好 1 格** —— 主任不再比主治忙，你要的效果就是这张表。

纯函数的写法（替代现在的 `morningDoctors` / `afternoonDoctors`）：

```java
/** 专家格：role1 那天两位主任对调，其余两天「上午 01 / 下午 04」。 */
static int expertAt(int role, LocalTime time) {
    boolean morning = time.isBefore(NOON);
    boolean swapped = role == 1;
    if (morning) return swapped ? 4 : 1;
    return swapped ? 1 : 4;
}

/** 普通格：沿用现有轮换口径（role1 时 02/03 也换边）。 */
static int normalAt(int role, LocalTime time) {
    boolean morning = time.isBefore(NOON);
    boolean second = role == 1;
    if (morning) return second ? 3 : 2;
    return second ? 2 : 3;
}
```

### 3.4 为什么这是唯一的均衡解

三条约束叠加后就没有别的选择了：

1. 每天 4 个格（09:00 / 10:30 / 14:00 / 15:30），**每格 1 位医生**（上一版已定：同一时刻不再摆两位医生）；
2. 主任只出专家号、主治只出普通号 ⇒ 2 个专家格**只能**由 2 位主任分，2 个普通格**只能**由 2 位主治分；
3. 专家格 2 个 / 天，两位主任 ⇒ **每人每天恰好 1 格**，3 天就是 3 格，且三天都得在位。

所以「主任每天 2 格」「主任比主治忙」在加了第二位主任之后**结构上就不可能发生**。
反过来说，只要有任何一位医生少出一天，就必然有另一位一天要坐 2 格——
而「一天坐 2 格」正是你这次要消掉的现象。

### 3.5 与现有演示坐标的吻合（已逐条核过）

`DemoSeed` 的坐标是按**时刻**取号源的，轮换一改，它们拿到的医生就变了。核对结果
（体检日**下周三**，d001 的放号日 `{1,3,5}` ⇒ 周三是 `roleIndex = 1`）：

| 演示坐标 | 时刻 | 现在解析到 | 影响 |
|---|---|---|---|
| `morningSlot()` | 周三 09:00 | **04 号王建华·专家**（原 01 张建国） | 医生换了人，但它是「取当天 09:00 那一条」的语义，**调用方都是动态断言，不受影响** |
| `conflictingSlot()` | 周三 10:30 | 03 号陈凤兰·普通 | 冲突场景只看时间，**无影响** |
| `plainSlot()` | 周三 14:00 | **01 号张建国·专家** | 号别仍是专家号；它是「普通（非冲突）办理」的意思，**不是「普通号」**，改注释即可 |
| `secondSlot()` | 周三 15:30 | 02 号李秀英·普通 | **无影响** |
| `laterDaySlot()` | 周五（role2）14:00 | 04 号王建华·专家 | 改期只看「换号源」，**无影响** |
| `endocrinologySlot()` | 周五（d003 role2）14:00 | 04 号·专家 | 同上，**无影响** |

> `DoctorSlotModelTests.slotIdsCarryTheDoctor...` / `bookingWritesTheDoctorSnapshot...` /
> `DemoSeedDataTests` 都是**从库里动态取**医生与号别再断言，换人不影响它们。

### 3.6 容量与量级（与上一版相同，加主任不改变任何数字）

| 量 | 数值 |
|---|---|
| 号源 / 科室 / 放号日 | 4 条（2 专家 + 2 普通） |
| 号源 / 科室 / 月（约 13 个放号日） | 52 条 |
| 号源 / 全院 / 月（12 科室） | **≈ 624 条**（现状 6 科室 ≈ 520 条）→ 仍在既有 `200~1200` 断言内 |
| 名额 / 科室 / 放号日 | 2×3 + 2×4 = **14 个** |
| 名额 / 全院 / 月 | ≈ **2184 个**（现状 520 个） |
| 普通 : 专家（名额） | 8 : 6 ≈ **57% : 43%**，供给侧原则（普通号名额 > 专家号名额）成立 |

> `everyDepartmentHasMoreNormalSlotsThanExpertSlots` 这条既有约束**必须改成按名额比**：
> 按**条数**是 2 : 2（相等），按**名额**才是 8 : 6。名额才是「真正能约上的人数」，语义也更准。

## 四、表设计（`schema.sql`）

```sql
-- 号源名额：一条号源 = 一位医生在一个时刻里的一班，capacity 是这一班能接几位。
-- 旧模型「一条号源 = 一个号」用 available 布尔表达；现在一条号源可以接多位，
-- 于是 available 降级为**派生位**（booked < capacity），只保留给现有查询继续用。
-- 默认 1 是刻意的：旧库上的存量行、以及测试里手工 INSERT 的号源，都自动等价于旧模型，
-- 不会因为「新列没填」而变得不可约。
ALTER TABLE appointment_slots ADD COLUMN IF NOT EXISTS capacity INT NOT NULL DEFAULT 1;
ALTER TABLE appointment_slots ADD COLUMN IF NOT EXISTS booked   INT NOT NULL DEFAULT 0;
```

- **不改** `available` 的类型，也不把它做成计算列（H2 的计算列不可写，而现有 4 处写入都写它）；
  它由 §7 的四个写点维持，另加一条启动自愈（§6.4）与一条不变式回归（§9）。
- 不变式：`0 <= booked <= capacity`，且 `available = (booked < capacity)`。
- **不新增 `doctor_schedules` 排班表**：排班仍由生成器算（DEC-022 决定七：出诊日不落库）。
- **`appointments` 一行不动**：一次预约仍指向一条号源，只是现在多条预约可以指向同一条。
  已核实 `appointments` 对 `slot_id` **没有唯一约束**，所以不需要动预约表。
- `doctors` 表**不加列**：名额是「这一班放几个」的属性，属于号源这一层（§6.3 有理由）。

### 6.3 名额进库

照 `fee_cents` 的既有做法，在生成器里做「号别 → 数值」一步映射：

```java
public static final int EXPERT_CAPACITY = 3;
public static final int NORMAL_CAPACITY = 4;

private static int capacityFor(String slotType) {
    return SLOT_TYPE_EXPERT.equals(slotType) ? EXPERT_CAPACITY : NORMAL_CAPACITY;
}
```

`insertIfMissing` 的 INSERT 补两列：`capacity = capacityFor(slotType)`、`booked = 0`。

**为什么名额不挂在 `doctors` 上**：名额是「这一班放几个」的属性，属于号源这一层。
挂在医生上会变成「主任永远 3 个名额」这种写死的耦合，也重犯「挂号费不能挂医生」那条错误（DEC-024 决定三同源）。

### 6.4 启动自愈（新增，建议做）

`insertIfMissing` 是按 `id` 判重的，而 `slotId` 的拼法（`r-<医生id>-<日期>-<时刻>`）**没有变**。
现有 `removeStaleGeneratedSlots()` 每次启动会把**所有没有预约占用的 `r-%` 行整批删掉重建**，
所以新行一定会带上正确的 `capacity`——但**有预约占用而留存下来的旧行**会停在 `capacity=1`。
在 `seed()` 末尾加一次全表重算（幂等，代价 = 四条 UPDATE）：

```sql
-- ① 按实际预约数回填 booked（只对有预约的号源有意义，其余被上面整批重建带走）
UPDATE appointment_slots s
   SET booked = (SELECT COUNT(*) FROM appointments a
                  WHERE a.slot_id = s.id AND a.status='CONFIRMED')
 WHERE s.id LIKE 'r-%';

-- ② 按号别修正 capacity（历史行默认 1，要拉回 3 / 4）
UPDATE appointment_slots SET capacity=3 WHERE slot_type='EXPERT' AND capacity<>3;
UPDATE appointment_slots SET capacity=4 WHERE slot_type='NORMAL' AND capacity<>4;

-- ③ 派生位重算，把任何漂移拉回不变式
UPDATE appointment_slots SET available=TRUE  WHERE booked<capacity AND available=FALSE;
UPDATE appointment_slots SET available=FALSE WHERE booked>=capacity AND available=TRUE;
```

### 6.5 存量 H2 库怎么办

`ALTER TABLE ... ADD COLUMN IF NOT EXISTS` + `DEFAULT 1` ⇒ 旧库升级后所有存量行 `capacity=1, booked=0`，
行为与今天**完全一致**；随后启动时的整批重建把它们换成带名额的新号源。
**演示库里已有的预约一条都不会丢**（有预约引用的号源不删，这是既有约定）。

## 七、写入逻辑（这是「只改数据库」里真正会动的代码）

全仓对 `available` 的写入只有 **4 处**（都在 `MockAppointmentTool`）+ **1 处重置**（`DemoScenarioService`）。

### 7.1 建立预约（`MockAppointmentTool:123`）

```sql
-- 改前
UPDATE appointment_slots SET available=FALSE WHERE id=? AND available=TRUE
-- 改后：还有名额就 +1；刚好填满最后一位时把 available 落下，让查询侧照旧看不见它
UPDATE appointment_slots
   SET booked = booked + 1,
       available = CASE WHEN booked + 1 < capacity THEN TRUE ELSE FALSE END
 WHERE id=? AND booked < capacity
```

`changed != 1` 仍抛「该号源刚刚已不可用，请重新选择」——语义从「这一个号被抢了」变成「**这一班约满了**」，
仍是一条**并发安全的乐观锁**。**幂等键（会话 + 就诊人 + 号源）不动**，上一轮刚修的 DEC-025 不受影响。

### 7.2 取消（`MockAppointmentTool:150`）

```sql
-- 改前
UPDATE appointment_slots SET available=TRUE WHERE id=?
-- 改后：空出一个名额就必然重新可约；clamp 住 0，避免异常路径把 booked 减成负数
UPDATE appointment_slots
   SET booked = CASE WHEN booked > 0 THEN booked - 1 ELSE 0 END,
       available = TRUE
 WHERE id=?
```

## 九、新增回归（建议 8 条）

1. **每科室每个放号日恰好 4 条号源，且号别与时刻严格对应**：
   09:00 / 14:00 必须 `EXPERT`，10:30 / 15:30 必须 `NORMAL`。
2. **四位医生工作量相等**：每科室每位医生在 3 个放号日里**恰好 3 格**、且**每天最多 1 格**；
   把 `(医生, 日期)` 里查不到号源的组合列出来必须为空（每人三天都在）。
3. **两位主任在放号日里轮换**：同一科室的 09:00 与 14:00，在 3 个放号日里分别出现过 01 与 04 两位医生
   （钉住 §3.3 那张表的形状，别被改回「一位主任坐满」）。
4. **名额落库正确**：`EXPERT` 号源 `capacity=3`、`NORMAL` 号源 `capacity=4`，且 `capacity` 只有这两档。
5. **名额扣减 / 释放的正向行为**（新口径的核心）：
   - 约 1 次 → `booked=1` 且**仍可约**（`available=TRUE`）；
   - 约满 `capacity` 次 → `available=FALSE`，第 `capacity+1` 次被拒；
   - 取消一次 → `booked` 回落、`available` 回到 TRUE；
   - 两位**不同就诊人**约同一号源 → 各得一条预约（同一位就诊人重复约同一号源仍走幂等，DEC-025 不变）。
6. **全表不变式**：`0 <= booked <= capacity` 且 `available = (booked < capacity)`，扫全表必须为空集。
7. **R1 时段级降级的新演法**：把某个放号日**下午的专家号约满**，再说「我要专家号，下午去」
   → 走 `expertOnlyInOtherPeriodReply`，给上午的专家号并问一句（把 §8.1 第 6 条拆掉的关卡装回来）。
8. **两院科室名集合相同且各 6 个**；同一医院内放号日互不相同。

## 十一、风险

- **两个演示场景消失，这是本次最大的代价**：
  1. **「下午没有专家号」** —— 上一轮「上午下午都要有专家号」的必然结果。
     R1 的能力本身还在，只是要**手工约满**才能演（§9 第 7 条）。
  2. **「点名本科室医生、他当天不出诊」** —— 新排班里每位医生每个放号日都在岗，
     本科室内造不出这个场景（§8.1 第 4 条给了三种改法）。
     注意：这**不是**加主任引入的，而是「每格 1 人 + 只放 3 天」的必然——4 格必须 4 个人坐满。
- **`available` 从「唯一真相」降级为「派生位」**：多了一个可能漂移的字段。
  用 §6.4 的启动自愈 + §9 第 6 条的不变式回归把它夹住，换来的是**查询侧与助手侧零改动**。
  若不接受这点让步，就必须把 4 处查询全部改成 `booked < capacity`，那就不叫「只改数据库」了。
- **同名科室规模翻倍**：6 个科室名现在**两院全都有**，「按科室名字聚合 / 判重」的坑（`PITFALLS` 2026-09-13）
  从「部分科室」扩散到「全部科室」。所有聚合一律用 `department_id`；
  `CareCatalogRepository.hospitalsForDepartment(名字)` 的返回值会从 1~2 家医院变成稳定 2 家，走这条路径的
  「换医院」交互要复测。
- **职称档位从两档变三档**：`SlotRecommender.titleRank` 现在会真正用到「副主任医师 = 2」这一档。
  当前排班里上午/下午各只有一位专家，档位不会打架；但**跨日推荐（7 天内找专家号）**时
  主任医师会稳定排在副主任医师之前，`DoctorIntentTests` 里那条「最近专家号」的断言要按新顺序复核。
- **量级**：每月 624 行号源 / 2184 个名额（现状 520 / 520）。仍是内存库、秒级重建，
  但录屏时「库里有几千个名额」这条口径要在文档里说清。
- **演示坐标依赖**：`d001` 放号日锁死 `{1,3,5}`、`loc-d001` 诊室不变、`slotId` 拼法不变——
  这三条是「下周三体检冲突」「找不到诊室」「按 id 找号源」三类演示的锚点，本次**刻意不动**。

  凡是有测试「按名字」断言 09:00 那位是谁的，都要改成动态取或按新排班写。
