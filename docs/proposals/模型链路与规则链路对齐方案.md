# 模型链路与规则链路对齐方案（时段/日期按钮 + 口语时间兜底）

> 状态：**已实施**（2026-09-14 用户拍板 A+B+C + A3，实现记录见第十节）。
> 前置阅读：`docs/records/DECISIONS.md` 的 DEC-021/022/026/027；`docs/proposals/推荐标记与时段可见性方案.md`（R7~R9，已实施）。
> 本文不重构 `FollowupAgentService`，不改照护端预约规则，不改排班/名额/接口。

---

## 一、演示中暴露的三个问题

1. **日期只能靠嘴说**：助手列了「9月15日（周一）、9月17日（周三）、9月18日（周四）」，**下面一个按钮都没有**。
2. **上午/下午没有档位，说了也不记账**：助手列了「【上午可选】…【下午可选】…」，老人回「我要下午的三点半的」，助手口头说「这就帮您改成下午3点半」，但**下一轮系统说「我还没有确认您想要的时间」**。
3. **答非所问**：老人回「可以」，被弹回上一轮的问题。

问题 2、3 是同一个根因的两个面。问题 1 是另一个。

## 二、机制：不是两条并行模式，是同一入口上的一个开关

一轮请求只有一个入口 `FollowupAgentService.chatInternalBody`（410），它按 `agentRuntime.modelAvailable()` 分叉：

| | 谁决定「说什么」 | 谁决定「记什么」 | 事实（facts）从哪来 |
|---|---|---|---|
| **模型链路** `modelDriven=true` | 主模型（`replyDraft`） | Java | **模型回传的 JSON**（`LlmConversationPlanner.facts` 122-134） |
| **规则链路** `modelDriven=false` | Java 模板（`advance` / `acknowledgement`） | Java | `RuleFactExtractor` 正则（`extract` 28-48） |

- **开关**：`AgentRuntime.modelAvailable()`（381-384）= `gateway.available()`（= `AGENT_MODEL_ENABLED` + base-url + key 三者齐）。**每轮现算**，不是启动快照。
- **这一轮模型失败也算规则链路**：`LlmConversationPlanner.plan`（49-58）的 catch 打
  `Conversation planner failed; using rule fallback`，返回 `RULE_PLANNER_FALLBACK`；
  `AgentRuntime.plan`（43-51）见 `source()` 不以 `MODEL` 开头就走 `legacyProposal`。
  ⇒ **判断「这一轮实际走了哪条链路」，看这句 warn 最直接。**
- **运行环境**：`AGENT_MODEL_ENABLED` 有两处来源——`devcontainer.json` 的 `containerEnv`（`"false"`，**创建容器时注入**）
  与 `.devcontainer/.env`（**`"true"`**，后端 VS Code 任务的 command 里 `set -a && . .env && set +a`）。
  **`.env` 的 true 覆盖容器注入值**，所以演示环境实际是**模型链路**。
  ⚠️ 普通终端里 `echo $AGENT_MODEL_ENABLED` 看到的是注入值 `false`，**不能当判据**。

**关键推论**：**模型链路下 Java 不解析自然语言**（只有 591-616 那两处短肯定/短否定兜底）。
所以「模型嘴上说了 15:30」与「Java 记下了 15:30」是两件事，前者不产生任何状态变更。

## 三、根因（三处，含行号）

### 3.1 按钮：模型链路的按钮清单不全（问题 1、2）

`modelSuggestedReplies`（1135-1156）是**模型链路唯一的按钮来源**，它有两处缺口：

1. 第一个分支**不看 stage**：`selectedSlot == null && !alternatives.isEmpty()` → 直接返回号源按钮；
2. `switch` 里**没有 `ASK_DATE` / `SELECT_PERIOD` / `SELECT_SLOT` / `CONFIRM_SLOT` 的 case** → 落 `default` 空列表。

对照规则链路，这两样**早就写好了**：

| 阶段 | 规则链路的按钮 | 出处 |
|---|---|---|
| 日期未定 | 每个可选日期一个 `SET_DATE` | `showAvailableSlots`（3147-3158） |
| 半天未定 | 上午 / 下午 / 直接选择具体时间（`SET_PERIOD` ×2 + `SHOW_PERIOD_SLOTS`） | `periodReplies`（3334-3345），被 `querySlots`（3079）与 `advance`（3008）使用 |

⇒ **不是要新做按钮，是把已有按钮接到模型链路上。**

### 3.2 记账：facts 是唯一事实源（问题 2 的下半）

- 模型链路里 `state.selectedSlot` 只能由 `facts.selectedTime` 推出来（1103-1105）。
  模型没在 JSON 里填 `selectedTime` ⇒ `state.selectedSlot` 永远是 null，`state.recommendedSlot` 也是 null。
- 因此 591-594 那条短肯定兜底（`recommendedSlot != null` 才认领「可以」）**接不住**。
- 而且即使走规则链路也抽不出这句话：`RuleFactExtractor.TIME`（19）是
  `(\d{1,2})[:：点时](\d{1,2})?`，**只认阿拉伯数字**，「三点半」抽不到（只会退化成 `timePreference=下午`）。

### 3.3 兜底话术错位（问题 3，本方案**不改**）

619-633 那条「一句没被接住的话，就把这一步再问一遍」的分支，条件是 `!outcome.modelDriven()`
⇒ 那一轮模型没给出结论（超时/失败/降级）时命中；它的文案由 `clarificationDraft(state)`（2484-2504）
**按展示用的 `state.stage`** 选，于是把老人刚回答过的问题又问了一遍。
这是语义错配（`syncPresentationStage` 自己的注释写着「Stage 只为旧前端进度展示服务」），
但改它要动「当前待答问题」的建模，**本方案不碰**，列为待办第七节。

## 四、改法

### A. 把已有的日期 / 上午下午按钮接到模型链路（解决「手点」）

**A1｜日期那一步由 Java 出清单**（落点：`modelWorkflowReply` 1069-1125，插在 `syncPresentationStage`（1119）之前）

```java
// 医院、科室都定了但日期还没定：直接由 Java 出真实日期清单（自带 SET_DATE 按钮）。
// 日期是权威数据，不能让模型复述——它编错一天，老人白跑一趟。
if (state.hospitalId != null && state.department != null && state.date == null) {
    return showAvailableSlots(state);
}
```

- `showAvailableSlots`（3124-3158）在 `date == null` 时会查「今天到一个月后」的可约日期，
  给出 `SET_DATE` 按钮 + 「选好后我再为您介绍上午和下午的具体时间」。
- 代价：这一轮改用 Java 文案，模型给出的过渡语不再使用。**安全优先，接受。**

**A2｜上午/下午档位**（落点：`modelSuggestedReplies` 1135，插在第一个分支**之前**）

```java
// 半天还没定：给上午/下午档位（与规则链路一致）。这是「先选半天、再选具体时间」的入口。
if (state.stage == ConversationState.Stage.SELECT_PERIOD) {
    return periodReplies(state.alternatives);
}
```

- `SELECT_PERIOD` 阶段 `alternatives` 必然非空（`syncPresentationStage` 1164-1165 的语义），所以不需要额外判空。
- **顺序很关键**：插在现有第一个分支之前，其它阶段的行为一行不变（最小改动）。

**A3｜（建议一并做）收紧第一个分支**（同 1137-1139）

```java
boolean selectingTime = state.stage == ConversationState.Stage.SELECT_PERIOD
        || state.stage == ConversationState.Stage.SELECT_SLOT
        || state.stage == ConversationState.Stage.CONFIRM_SLOT;
if (selectingTime && state.selectedSlot == null && !state.alternatives.isEmpty()) { …号源按钮… }
```

- ⚠️ **本节初稿的理由是错的，已更正**（见第十节实施记录第 5 条）：初稿写「`switch` 里 `ASK_ALTERNATIVE` /
  `ASK_COMPANION` / `ASK_TRAVEL` / `ASK_TRANSPORT` / `ASK_NOTIFY` 五个 case 永远走不到」，**不成立**——
  `syncPresentationStage` 给这五个阶段设 `stage` 的前提都是 `selectedSlot != null`，而原前置分支的条件是
  `selectedSlot == null`，**两者互斥**，所以那些 case 一直可达。
- 真实成因是 B：`selectedSlot` 为空使 stage 只能停在选时间，**而模型嘴上在问陪同**——回复是
  「需要陪同吗」、按钮却是三个时间段。A3 的实际作用是**收窄号源按钮的适用阶段**，
  让 `stage` 与按钮严格对齐（`NO_SLOT` 等阶段不再从这条旁路拿到跨日期号源按钮）。

### B. 模型链路的口语时间兜底（解决「嘴说」）

**落点：`AgentRuntime.plan`（43-51）** —— 模型成功时给 facts 补一次空，只补不覆盖：

```java
if (proposal.source().startsWith("MODEL")) {
    return modelProposal(withSpokenTimeFallback(proposal, message, context), state);
}
```

`withSpokenTimeFallback` 的规则：

- 仅当 `facts.selectedTime() == null && facts.timePreference() == null`（模型一个时间线索都没给）时生效；
- 用 Java 的解析器从**原话**里再抽一次；抽到才补，抽不到保持原样；
- **绝不覆盖**模型已经给出的字段。

选这个落点的理由：`AgentRuntime` 已经注入了 `RuleFactExtractor`，改动集中在一个类里，
**`FollowupAgentService` 一行不用动**（它在 `dispatchOutcome` 里会照常走
`modelWorkflowReply` → `applyFacts` → 1103-1105 的 `selectedTime` 分支 → `recommendSpecificTime`）。

配套：给 `ExtractedFacts`（6-24）加一个补丁方法，例如
`static ExtractedFacts withSelectedTime(ExtractedFacts base, LocalTime time)`，
用 17 个分量原样拷贝 + 替换一个，避免 18 参构造调用点散落。

### C. 中文数字钟点：**复用 `MemoParser`，不写第二份**

项目里已经有一份成熟的钟点解析（`MemoParser`）：

- `CN_CLOCK`（107-110）：中文数字「一点…十二点」+「半 / 一刻 / 三刻 / 零X分」；
- `CLOCK`（104-105）：阿拉伯数字；
- 护栏（96-97）：`差一点 / 有一点 / 一点点 / 一点儿` 里的「点」不当钟点；
- `periodHour`（551-557）：时段词折算 12/24 小时制并夹取范围；
- 以上由 `clockTime`（524-548）串起来，`MemoParserClockTests` 已有 8 例钉着
  （含「下午三点半 → 15:30」「明天早上七点二十五 → 7:25」「晚上七点 → 19:00」）。

**做法**：把 `clockTime` 提为可复用的公开入口（`MemoParser.clockIn(String)` 之类的薄封装即可），
`RuleFactExtractor.parseTime`（162-171）在**自身正则失配时兜底调用它**。

- **保持既有优先序**：阿拉伯数字正则先走，行为一个字不变，只多认中文数字。
- 不新写第三份钟点正则——项目已有明确惯例（`MedicalBoundaryRules` 的注释：
  「越界口径与 SafetyGuard 共用一份规则：**词表写两遍迟早只剩一份是对的**」）。

## 十、实施记录（2026-09-14）

与方案不一致或方案没写到的落点，逐条记在这里。

1. **B 的落点签名比方案少一个参数**：方案写 `withSpokenTimeFallback(proposal, message, context)`，
   实现只用 `(proposal, message)`——`context` 在本轮没用到，多传一个参数只是摆设。
2. **C 的入口形状**：方案说「把 `clockTime` 提为公开入口」，实现取名为 **`MemoParser.clockIn(String)`**；
   `RuleFactExtractor` 侧则是把钟点抽取**整个提成公开方法 `spokenTime`**，`parseTime` 委托给它。
   这样模型链路的兜底（B）与规则抽取（C）走的是**同一个方法**，不会各拿一份口径。
3. **多认了两件事，都是复用 `MemoParser` 的必然结果，不是新加的语义**：
   - 「一刻 / 三刻 / 零五分」这类中文分钟，以及「晚上 / 中午」的时段折算（`periodHour`）——
     备忘那边本来就认，共用一份实现就一起认了；
   - 「**3点半**」在阿拉伯数字那条原本不认「半」（只取到 `3点`），现在与「三点半」对齐成同一个时刻。
     两条都写进了 `RuleFactExtractorClockTests`，口径可见、不藏着。
4. **「下午」按整句判**：方案只说了「失配时兜底」，没提这一层。演示原话是「我要**下午的**三点半的」——
   「下午」与「三点半」中间隔着一个「的」，只按紧邻时段词（`MemoParser` 的做法）会算出凌晨 3:30，
   再按最近号源推荐就把下午的号推成上午的号。所以 `spokenTime` 在拿到钟点后**再看整句有没有「下午」**，
   有且钟点在 12 点前就补到下午——这正是原来阿拉伯数字那条的老口径，只是现在对中文数字也成立。
5. **⚠️ A3 的理由写错了，实现前已更正**（这是本轮唯一一处「方案判断被证伪」）：
   - 方案 §四 A3 说收紧第一个分支能让 `ASK_ALTERNATIVE` / `ASK_COMPANION` / `ASK_TRAVEL` /
     `ASK_TRANSPORT` / `ASK_NOTIFY` **五个「死 case」复活**。**这句是错的**：`syncPresentationStage`
     给这五个阶段设 `stage` 的前提都是 `selectedSlot != null`，而原前置分支的条件是 `selectedSlot == null`，
     **两者互斥** ⇒ 那些 case 一直可达（`askHospital` / `advance` 直接置 `stage` 的路径也一样，
     它们都在 `selectedSlot == null` 的早返回之后）。
   - 真实成因是 **B**：草稿里没有号源时 `stage` 只能停在 `SELECT_PERIOD` / `SELECT_SLOT`，
     **而模型嘴上在问陪同** ⇒ 回复问「需要陪同吗」、按钮却是三个时间段。
   - 所以 A3 的实际作用是**收窄号源按钮的适用阶段**（`stage` 与按钮严格对齐；`NO_SLOT` 等阶段
     不再从这条旁路拿到跨日期号源按钮），**不是让死代码复活**。实现与测试都按更正后的口径走。
   - `selectingTime` 只含 `SELECT_SLOT` / `CONFIRM_SLOT`：方案示例里还列了 `SELECT_PERIOD`，
     实现里不需要——`SELECT_PERIOD` 由 A2 那一条在前面就返回了。

- `AgentRuntimeSpokenTimeFallbackTests` 是**现有测试里第一条走模型链路的用例**：把假规划器
  （`mode()` 以 `MODEL_` 开头、`source()` 以 `MODEL` 开头）注入 `AgentRuntime`，把「模型回了什么」
  变成可控输入——现有用例全是 `agent.model.enabled=false`，没有一条能覆盖 B。
