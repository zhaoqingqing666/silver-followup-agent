# 踩坑记录

## 2026-09-13 护栏写成「拿另一个谓词的反面兜底」，漏掉的那一类正好每天都要用

- 现象：给确认卡加「目标条数」校验，写成一条链：`singleTargetOnly()` 的必须恰好一条，`cancelsAppointments()` 的至少一条，**其余的一律不许带目标**。前两支都对，第三支用 `!cancelsAppointments()` 兜底——而 `CANCEL_MANAGED`（照护端代约取消）**不该带整批、却必须锁定那一条**，它既不满足第二支，落进第三支就成了「目标集合必须为空」。后果是每一张代约取消卡都在签发时报 `TOOL_ERROR`，功能整个用不了。
- 根因：**把「三类」写成了「两个条件 + 它们的反面」。**`singleTargetOnly` 和 `cancelsAppointments` 不是互补关系：`CANCEL_MANAGED` 落在两个谓词都为假的缝里，而兜底那一支的语义（「这类动作不针对已有预约」）根本不是它的语义。判断依据是「这一类动作要不要求目标」，就必须按这个维度穷举三分，而不是拿另一个维度的谓词反着推。
- 为什么单测没拦住：**用例给的目标集合恰好是空的。**那几条专测签发的用例构造 `CANCEL_MANAGED` 时传 `List.of()`，正好落在旧契约上——绿得毫无信息量。真正发现它的是端到端把卡片发出来那一步：单元测试里没人走过「代约取消卡带着一条目标」这个唯一真实的形态。
- 处理：重写成三条互斥分支、各自早返回，`CANCEL_MANAGED` 明确归入「恰好一条」那一支，并在注释里点明「把它漏进第三类，正是『卡上不写目标、执行时现找』那个老毛病换了个写法」。补 `theTargetCountIsEnforcedAtIssueTime` 覆盖三个分支，含 `CANCEL_MANAGED` 带一条目标必须通过。
- 结论：**兜底分支的语义要单独写清楚，不能写「其余」。**「其余」在新增取值时会悄悄改变含义，而且改的是**签发**这一步——错在这里意味着某类卡片再也发不出来，不是少了一层保护。附带一条：**单元测试里「参数恰好合法」的用例不能证明校验写对了**，得有一例走真实形态（这里是带一条目标的代约取消卡）；发现上面这个错的正是端到端，不是单测。

## 2026-09-13 「再查一遍当前的那一条」是个系统性的坑：签发侧放空 + 执行侧重查 = 卡上写 A、执行 B

- 现象：三处取消都长着同一副面孔——**签发时不把要动的对象写进凭据，执行时按「当前」重新查一条出来**：本人批量取消执行时重新筛「还没取消的」；照护端取消干脆忽略冻结的目标集合、调了那个「取消当前预约」的入口；`CANCEL_MANAGED` 更直接，签发时传 `List.of()`，执行时按展示用的那条记录反推。单看每处都「行为正确」——因为测试里那条「当前」和卡上那条通常是同一个。
- 根因：**把「凭据冻住了动作类型」当成了「凭据冻住了一切」。**授权是「凭据 ＋ 动作类型 ＋ 完整目标集合」三样，漏了第三样，目标就只能从别处现取——而现取的那个「当前」是可变的。真实的破法不需要并发：老人对着卡片上那条更早的预约点了头，期间他刚新约了一条（`created_at` 更新、排序在前），执行时「当前的第一条」就换成了新约的那条。**取消掉一条他根本没打算退的号。**
- 处理：要动的对象在签发那一刻冻进 `targetIds`；执行侧只认凭据里的那条，`AppointmentRecordStore` 的按 id 查询降级为**只取展示与通知字段**（谁安排的、约在哪天），归属/存在性/可否取消一律交给权威的 `appointmentTool.cancel`（`id + user_id + status='CONFIRMED'`），不另开第二套口径。原目标失效就什么都不取消、回一句「原预约保留」，**绝不找一条顶替**。两侧成对护栏：签发侧要求这类卡恰好一条目标，执行侧 `singleTarget()` 在不为一条时返回 `null`（**不是 `get(0)`**）并立刻收场。
- 怎么写出能红的测试：光断言「取消成功」没用——旧实现在测试里也成功。要**刻意制造「最新的那条不是卡片上那条」**：先发卡，再往库里插一条更早、`created_at` 加一秒因而排序在前的竞争预约（`DATEADD('SECOND', 1, CURRENT_TIMESTAMP)`），再确认，断言**卡上那条变了状态、竞争那条原封不动**。这样「取第一行」的旧写法才会红。
- 结论：**「这个对象现在还在不在、还是不是他的」可以现查；「到底动哪一个」不许现查。**前者是校验，每次执行都该重做；后者是授权内容的一部分，签发那一刻就定了，随快照走、随凭据作废。凡是执行路径上出现「找一条当前……」，都要问一句：这里为什么不是凭据里写死的那条。

## 2026-09-13 凭据三样齐全，不等于「执行这条动作需要的东西」齐全

- 现象：备忘确认卡上有正文和提醒时间，可这两个值**不在授权三样（凭据 / 类型 / 目标集合）里**，也不在会话快照里。页面上卡片写得清清楚楚，重启（或任何一次缓存失效）后确认，那两个字段读回来是 `null`——写进库的要么是空白正文，要么按会话里别的什么凑一段。老人对着卡片上那段话点头，记下去的是另一段。
- 根因：**「授权信息」和「执行这条动作要用到的数据」被当成了一回事。**`Kind.MEMO` 说清楚了「要记一条备忘」，可「记哪一条」是另一份数据。别的卡不需要它是因为目标集合本身就是全部所需（预约/取消只要那几条 id）；备忘卡的目标是「一条还不存在的记录」，它的内容只能另有来源，而那份来源同样是**签发那一刻定下的**——它和凭据一样是不可信会话状态里唯一权威的那份。
- 处理：把这类动作执行时要用的草稿与凭据**一起进快照、一起回**（这里是 `pendingMemoText / pendingMemoAt / pendingMemoRepeat / pendingMemoDay / memoReturnStage / memoNeedsApproval` 六个字段）；加 `payloadIntact` 做「这类动作执行所需的东西在不在」的判断，**读回一份凭据时缺了就当整份不可信**——不写残缺内容，作废凭据、请他重说。签发侧同样要求草稿已在（少了是调用点的编程错误，当场炸，而不是留到执行时）。
- 老快照**不做回填**：读出来是 `null`，正是要它被判成不可信。回填一个默认值等于替老人决定记什么，比不写更糟。
- 结论：**给一份授权做「完整」判断时，问的是「执行这条动作所需要的全部输入都在吗」，不是「三样都在吗」。**三样只是骨架；凡是执行时用到的值，要么来自可重查的权威事实（如预约归属，可以重新校验），要么必须冻进凭据——**不存在第三种**。第三种就是「从会话里现凑」，也就是上面那条坑的另一副面孔。

## 2026-09-13 凭据冻住了，执行却在出口按可变字段现算——门禁修在了里面，出口还开着

- 现象：4A 把「这份凭据授权的是哪一类动作、对哪几条对象」冻进了 `PendingOperation`，`confirm()` 也确实照着 `kind` 判了；可**再往下一步的执行分支又各自拿会话字段重判了一遍**——预约那条读 `caregiving()` 和草稿里的 `selectedSlot`，代他人办理那条读 `pendingAction`，代约取消那条读用户面前停在哪一页。同一张卡，进门验的是冻结的授权，出门走的是现算的路。
- 根因：**把「不信任输入」理解成了「不信任上游给我的那个东西」，于是每一层都重判一次。**凭据这道门禁的信息**比任何会话字段都权威**——它是签发那一刻由调用方写死的、随快照持久化、随凭据一起作废的。但在出口处再判一次时，判的已经不是那张卡了，而是「此刻的会话长什么样」。中间只要有一步动过 `pendingAction`、或用户多说了半句话让草稿变样，同一把钥匙执行的就是另一件事：老人对着「取消这次预约」点头，执行出来的是照草稿开一条新单。
- 处理：分派只认 `PendingOperation.Kind` 一个判据，四个取值各有执行器；`pendingAction`、`appointmentId`、`pendingAppointmentIds` 完全不参与「执行什么」的判断，只剩「给界面看」的用途。照护端那一支同样按 `Kind` 分派——核实过按 `pendingAction` 与按 `Kind` 在这个分支上等价（`"CANCEL"` 这个值全代码库从未被赋值，是死条件），所以改的是判据来源，不是行为。
- 附带一条同类的：**「等价」也要核实到赋值点，不能凭条件名像不像。**`"CANCEL_EXISTING"` 看起来是「正在取消」，但唯一的赋值点 `prepareExistingCancellation` 紧接着就签发 `Kind.CANCEL_APPOINTMENTS`，所以它等价于那一类；而 `"CANCEL"` 谁都没写过。两处都不改链路，只把结论写进 Javadoc——**死条件不删**，删掉会让后来的人以为这里曾经有过一条分支。
- 结论：**门禁如果只有一个入口，它保护的就不是那个入口，而是它身后的所有出口。**在出口处再判一次不是「多一层保险」，是**把已经作出的决定重新交还给不可信的状态**——而且这个重判通常不会被测试发现，因为要构造出「门禁通过、出口重判出不同结论」的中间状态，得有人恰好改掉那个字段。这一条的护栏靠**分派级的替身测试**才拦得住：把 `pendingAction` 改成 `CANCEL_EXISTING`、`appointmentId` 指向别人的预约，再按那张 `BOOKING` 卡点头，断言走的是 `BOOKING` 那条路、取消一次都没发生。

## 2026-09-13 拆出去的类要回调进来时，接口会顺手把可见性放大一圈

- 现象：把三类执行搬出 `FollowupAgentService` 之后，执行器需要用到它二十几个会话收尾动作（回一个计划、推进阶段、记一次工具失败、翻工具错误出口……）。最自然的写法是抽一个接口让服务实现，执行器收接口。
- 根因：**接口的方法隐式 public，而实现它的类是 public 的**——实现一个接口，等于顺便把这些方法变成对外 API。`ConversationState` 的字段、`ToolPolicy` 这些都是包级私有，DEC-018 的原则是「新能力不靠加参数、加 public 来接入」；为了让拆出去的类能回调进来而放宽封装，是把结构整理的代价转嫁给封装。这里还叠了一个更实际的后果：这些方法里有 `callTool`、`respondWithPlan` 这种**直接涉及写操作与话术**的，一旦 public，调用方就不止执行器了。
- 处理：改成一个**包级私有抽象类** `ConfirmationSupport`，抽象方法声明成包级私有；`FollowupAgentService extends ConfirmationSupport` 后逐个 `@Override` 成同样的可见性，对外面一个字都没变。这个 support 对象**按方法参数传**进分派（`dispatcher.dispatch(state, operation, approved, this)`），**不在构造器里注入**——否则依赖链是 `FollowupAgentService → Dispatcher → Executor → Support`，而 Support 的实现就是 `FollowupAgentService` 本人，Spring 直接报循环依赖。参数传递还顺手把「谁在执行这一刻代表会话」写显式了。
- 附带一个会静默递归的坑：端口方法名如果和类里已有的私有助手**同名同参**，`@Override` 处解析到的就是它自己（编译期告诉你「不能覆盖自己」，但更常见的情形是同名不同参而导致调用落到错误的重载上）。这里全部刻意错开命名：`draftComplete` ↔ `ready`、`arrangedPlan` ↔ `upcomingArranged`、`resumeInterruptedReplies` ↔ `resumeReplies`；最后一个本来叫 `resumeReplies`，正是撞上这个才改的名。
- 结论：**「谁需要看见什么」应当由调用关系决定，不该由 Java 的语法默认值决定。**拆类时先问一句「这个新类型会不会把原来包级私有的东西顶成 public」，答案是会就该换形态——抽象类、包级私有、原包内继承，都是现成的选项。可见性一旦放宽就收不回来：它不会编译报错，只会让下一个人的调用点越来越多。

## 2026-09-13 「它以前就这样」不是「它可以留着」——拿测试钉住一个降级，等于把副作用升成规格

- 现象：抽 `ConfirmationService` 时发现一次批量取消**重启后只剩一条目标**（`pendingAppointmentIds` 没进快照，回填只回到 `pendingAppointmentId` 那一条）。当时的处理是：不动它，反而**写了一条单测把这个降级钉住**（`aBatchCardDegradesToTheSinglePersistedTargetAfterAReload`），并在 DECISIONS 里写下「会话恢复的降级刻意保持不变，本阶段不修」。评审直接驳回：这条不接受。
- 根因两层：
  1. **把成因当成了决定。**那个降级没有任何产品理由，它是「当初没把目标集合放进快照」的**副作用**，不是我选的行为。而一句「以前就这样、本阶段不修」会让它看起来像经过考虑的设计——下一个读 DEC-022 的人会以为这里必须如此，于是没人再去动它。
  2. **低估了后果的可见性。**抽类前我以为这只是「少取消几条」。实际是：卡片正文写着「2条」，口播也是两条，重启后确认只取消一条，而**界面和「取消成功」长得一模一样**——老人看到成功提示，会认为那个号已经退了，不去医院，而系统里那条预约仍然是 `CONFIRMED`。一个只在重启后出现、界面无差别、后果落在真实就诊上的错。
- 附带教训：`aBatchCardDegradesToTheSinglePersistedTargetAfterAReload` 这类测试**看着是回归护栏，实际是错的固化**。一条测试红了会有人说「改坏了」，所以给它命名和注释时必须诚实——它写的是「当前行为」还是「期望行为」。同一次改动里还有一条自我比较的假断言（`assertThat(x).isEqualTo(cond ? null : x)`，恒真），是同一类「用测试的形态掩盖没验证」的毛病，已删。
- 处理：把动作类型与完整目标集合一起写进 `ConversationState` 与 `Snapshot`，恢复时逐条相同；还原不出完整集合的旧快照**整份作废、要求重新确认，绝不部分执行**。删掉降级测试，换成完整恢复（真库端到端）与旧快照安全失效两条。
- 做法上留着一条可用的：改动过的判据要**反向复现**——把 `Snapshot.from` 强制写成 `null, null`、把 `restored` 退回旧的部分回填，看测试会不会红。两次都红了（后者 6 项），才算把上面这句结论钉在代码上而不是钉在注释里。
- 结论：**碰到既有的可疑行为，先问「这是谁的决定」，答不出来就当缺陷处理**；至少不能写一条测试把它固定下来。测试的每一条断言都在表达「这里应该这样」，写上之前先确认自己真的认为它应该这样。

## 2026-09-13 三条交互通道长得一样，第三条的写法照抄到第二条上就是「非法输入换一次执行」

- 现象：统一 `respondConfirmation` 的参数校验时，最省事的写法是照抄同一段代码里澄清那条分支：`ToolContract.check(...)` 没过就 `rejectedByIntent(...)`，把这一轮退回按 intent 判断。**照抄过去编译通过、没有一条测试变红**——那段分支原先没有任何用例走到，既有 14 项全绿。它改的是没人测过的那一次转弯。
- 根因：`rejectedByIntent` 走的是 `modelRoute(intent, state)`，而当 intent 是 `CONFIRM_ACTION`、会话又停在 `AWAITING_CONFIRMATION` 时，它返回的是 `CONFIRM_PENDING`。也就是说：**模型把 `decision` 写错一个字母（`MAYBE`、多一个空格、干脆漏了这个字段），回退出来的结果是「执行那件待办」**。校验本想挡住一次非法调用，回退却把它变成了授权——参数写错的调用反而换到了一次真的写库。
- 为什么同一条路在澄清那里是对的：澄清**没有下游可依赖**——`askClarification` 校验不过退回 `ASK_CLARIFICATION`，最坏结果是多问一句，不发凭据、不建卡、不执行任何事。而 `respondConfirmation` 是三条通道里**唯一一条「再往下就是执行」**的，它的失败处理一旦回退，回退目标本身就是一次授权。
- 处理：这一条查完只回绝不回退——`return refuse(proposal)`，翻成 `REFUSE_UNSUPPORTED_TOOL`，回一句「抱歉，这个操作我没办法直接执行。您可以换一种说法，或者让我先帮您查一下已确认的预约」。代码注释和测试里都写明「**这里不能像澄清那样按 intent 回退**」，测试断言 `isNotEqualTo(CONFIRM_PENDING)`——把「不要退回执行」写成一条会红的断言，而不是一条注释。
- 结论：**「三条通道写成一个样子」是陷阱。**它们的入口长得像，出口的后果不在一个量级：只读的出口是一次查询，澄清的出口是一句话，确认的出口是**写库**。共用格式化代码没问题，共用**失败处理**——尤其是一段会重新推导意图的失败处理——就是在给非法输入找一条通往执行的路。判断「这一条能不能回退」，依据不是「另外两条怎么写的」，而是「回退出来的那个结果，最坏会发生什么」。附带一条：**这一段的护栏在补齐用例之前是零覆盖的**，所以「照抄后全绿」什么都不能说明。

## 2026-09-13 写操作门禁按「草稿」判，会拦住走同一条路的另一件事

- 现象：`confirm()` 里那道「号源时段已经过去就不能确认」的检查，把**取消已有预约**也一起拦了。老人先约好一条 09:00 的复诊，10:30 回来点「取消这次预约」并确认，助手却回「您选的 2026年9月16日 09:00 已经过去了，请重新选择复诊日期」——取消办不成，还得先重选一遍日期。
- 根因：预约办完之后会话**仍留着当初那份 `selectedSlot`**（完成路径没有清它），`ready(state)` 于是照样为真；而这道检查排在 `CANCEL_EXISTING` 分支之前，取消也被它判了一遍。真正过期的是草稿里那个时段，跟这次取消没有关系。
- 处理：给检查加一个「这次确认是不是照草稿开新预约」的前置条件——`pendingAction` 为 `null` 或 `CREATE` 才算，取消类一律放行。
- 结论：门禁的条件要从**这次操作**推出来，不能从「草稿里还剩什么」推。同一份草稿会被多条路复用（创建、改期、取消、照护代约），残留字段对其中一部分路是无关的，拿它当共同前提就会误伤。判断依据得盯住 `pendingAction` 这类「本轮到底要做什么」，而不是状态里碰巧还留着的值。

## 2026-09-13 「已经过去」和「查得到」的边界必须对齐到同一侧

- 现象：号源查询的口径是 `appointment_time > 当前时间`（等于此刻查不出来），而确认时那道过期检查原先写的是 `时间.isBefore(现在)`——等于此刻时**不算**过期。于是 09:00 整点按确认，能约到一条查询永远查不出来的时段：约完在列表里找不到，看着像凭空多出来的。
- 根因：两处各自写了一遍「算不算过去」，一个用严格大于、一个用严格小于，中间正好漏掉「等于」这一瞬。两个条件互为补集才是对的（`!after` 对应 `after`）。
- 处理：`slotAlreadyPassed` 改成 `!LocalDateTime.of(slot.date(), slot.time()).isAfter(clock.now())`，与查询条件 `appointment_time > ?` 严格互补；补一条整点边界用例（时钟拨到 09:00 整，确认 09:00 的卡必须被拒）。
- 结论：一个时间窗口的「取」和「判」如果分别在两处写，边界归属要靠写测试钉住，不能靠读代码觉得「差不多」。差一个等号在整点、整分这种真实用户会踩到的时刻上就是错的。

## 2026-09-13 SQL 里的 `CURRENT_DATE` 和 Java 里的 `LocalDate.now()` 是两套钟

- 现象：号源查询、可选日期、「这一天的号还在不在」这类判断，在服务器默认时区与业务时区不一致时会给出互相矛盾的结果。开发容器是 UTC、业务是 Asia/Shanghai，北京时间 00:00–08:00 之间 SQL 眼里的「今天」还停在昨天——昨天下午已经过去的时段会被当成可约号源端给老人，而 Java 同一时刻算出来的是今天。
- 原因：`appointment_slots` 的三处查询（`querySlots` / `queryUpcomingSlots` / `queryAlternatives`）和 `CareCatalogRepository.availableDates` 都在 SQL 里写 `appointment_date > CURRENT_DATE OR (… = CURRENT_DATE AND appointment_time > CURRENT_TIME)`。`CURRENT_DATE` 取的是数据库连接的 JVM 默认时区，`LocalDate.now()` 取的是进程默认时区——**同一个进程里也能是两个不同的钟**，一个是数据库驱动会话的，一个是业务代码的。两边都不一定是业务时区。
- 处理：新增可注入的 `BusinessClock`，把截止时间作为**绑定参数**传进 SQL（`Date.valueOf(clock.today())` / `Time.valueOf(clock.time())`），Java 侧同样走这个时钟。判断「现在」只有一个来源。
- 结论：跨语言边界的时间比较不能各自取「现在」。SQL 里的 `CURRENT_DATE`/`CURRENT_TIME`/`CURRENT_TIMESTAMP` 与业务代码的 `now()` 之间没有任何一致性保证，看起来能跑只是因为默认时区恰好等于业务时区——换个容器就变。

## 2026-09-13 审计时间戳与业务时间必须分开看

- 现象：统一时区时，`created_at`、`notified_at` 这类列写的是 JVM 默认时区的时间（容器里是 UTC），而「本周一零点」这类业务边界按北京时间算。两者直接比较，边界会差八小时。
- 原因：历史数据是按服务器默认时区写进去的，同一个字段里混着两种语义的用法；而业务侧新加的时区不该反过来改写历史。
- 处理：分两个钟面。业务钟面（预约日期、号源截止、「今天/明天」、提醒钟面、周报的周一八点、号源与日程播种）走 `BusinessClock`；审计钟面（各类 `created_at` 落库）保持 `LocalDateTime.now()` 不动，只补注释说明它是审计钟面。两钟面之间需要比较时经 `BusinessClock.toAuditClock` 换算（目前只有 `HealthReportService.weeklySentThisWeek` 一处）。**不给历史数据批量加八小时**——那会把旧行改成另一个瞬间。
- 代价（要一并说清，否则「分两个钟面」听起来像没代价）：审计钟面留下的时间戳只要被拿去**展示**，口径就会露出来。已发现的一处是 `memos.created_at`——长驻备忘按它**按月分组**，北京时间月初 00:00–08:00 记的备忘会被归到上个月。这类地方要单独做展示层换算，不能靠改写入口径来修（那会让新旧行混用两种语义）。
- 结论：改时区之前先把字段按语义分类。"服务器时间是错的"是个过于宽的结论：审计时间戳记录的是"那一刻落库"，它本来就是对的；错的是拿它当业务日期用。

## 2026-09-13 父层一个 `overflow-hidden`，让**所有**老人页的页头都失去 sticky

- 现象：报的是「助手页头固定失效」，但真正的原因跟助手页无关——`sticky top-0` 的页头在滚动时跟着页面一起走了。
- 根因：`MobileShell` 里那层 `mx-auto min-h-dvh max-w-[480px]` 用了 `overflow-hidden`。只要 `overflow-y` 不是 `visible`，这一层**就变成滚动容器**；而它的高度是跟着内容长的、自己永远不滚，于是页头在它内部没有任何可以「粘」的滚动余量，`sticky` 形同虚设。凡是套着 `MobileShell` 的页面全中招。
- 解决办法：改成 `overflow-x-clip`。它保留原来横向裁切的本意（挡住超宽内容），但 `clip` 不产生滚动容器，`sticky` 立刻恢复。
- 结论：看到 `sticky` 不生效，先顺着祖先链找 `overflow` 不是 `visible` 的那一层，而不是去改 `sticky` 自己的 `top` 值——`.large-text` 下标题行会变高，写死 `top-[76px]` 的次级栏当时也正因此被压住。

## 2026-09-13 折叠按钮的显示判据不能依赖「此刻是展开还是折叠」

- 现象：预约记录默认摆三条，另外有一颗「展开全部预约记录（N）」；当全部记录都属于「即将到来」时（没有过去的、也没有已取消的），点开之后按钮**消失**，老人再也收不回去。
- 根因：判据写成「隐藏条数 > 0」，而隐藏条数 = 总数 − 当前显示条数。展开后显示条数追上总数，这个差值恰好归零——判据把自己否掉了。
- 解决办法：改成与展开状态无关的问法——「还有更多可看吗」＝ `upcoming.length > 3 || past.length > 0 || cancelled.length > 0`。
- 结论：控制同一元素可见性的条件，不要在它自己的两种状态里取一个会随状态变化的量；先问「有没有内容」再问「现在展开没展开」。这条边界用一组「10 条全是即将到来」的假数据才测得出来——只用混合数据（5 未来 + 2 过去 + 3 已取消）时，展开后隐藏条数仍是 5，看起来一切正常。

## 2026-09-12 `CANCEL_APPOINTMENT` 不能等同于确认当前取消卡

## 2026-09-12 `npm run build` 报 EACCES：`dist/` 被 root 建过一次

- 现象：`npm run build` 失败，`Error: EACCES: permission denied, rmdir '/workspace/frontend/dist/client'`。`dist/` 是 `vscode:vscode` 的时候正常，不知何时变成 `root:root`。

- 结论：容器里跑构建**一律带 `-u vscode`**。以 root 建出来的产物目录会让下一个人（或下一次 CI）构建失败，而报错信息只提一个目录，看不出是属主问题。

- 现象：`profile-view.tsx` 里 `useEffect(() => { void load(); }, [])`，`load()` 第一句是 `setLoading(true)`，oxlint 报 `react(react-compiler) EffectSetState`。

- 处理：改成只在 promise 回调里 setState（`listMemories().then(ok, fail)`），用一个 `cancelled` 标志在清理函数里丢弃迟到结果；「正在读取」这个状态改用 `memories === null` 表达，少一个可能对不上的布尔。重试按钮走 `reloadToken` 递增重新触发 effect，setState 落在事件处理里不受这条规则约束。
- 结论：这条 lint 规则不只是形式要求——它逼出来的写法顺手修掉了「重试连点两下、先发的那次后到把新结果盖回旧的」这个真实竞态。`cancelled` 守卫在这里不是摆设。

## 2026-09-11 `probe=true` 把一条正常的模型通道自检成「密钥无效」

- 现象：`GET /api/demo/channels?probe=true` 返回 `probe.ok=false`、`reason="调用抛异常：密钥无效、余额不足或网络不通"`；但用同一把 key 直接 curl DeepSeek 是 200，回复也正常。

- 结论：推理模型的 token 预算不能按普通模型给；诊断信息已经在异常消息里时，别在 catch 里丢掉它，否则排查方向会被带偏。

## 2026-09-11 祖先的 transform 把 fixed 浮层关进 64px 的盒子

- 现象：按住麦克风时，本该在按钮上方居中的浮层变成一条又高又窄的竖条，「松开手指，取消发送」一个汉字一行往下排，从屏幕中段垂到底部，把整片号源列表盖住。类型检查、代码规范检查、生产构建全绿。
- 根因：浮层是 `position: fixed` + `w-[calc(100%-40px)]` + `bottom-[132px]`，看着是「视口宽度减 40px、离屏幕底 132px」。但它的祖先 `div` 为了给麦克风居中带了 `-translate-x-1/2`——**祖先只要有一个 transform，后代的 `fixed` 就不再以视口为包含块，而是以那个祖先的盒子为包含块**。那个盒子只包着一个 `size-16` 的圆按钮，64×64：`calc(100% - 40px)` = 24px（比 `px-6` 的左右内边距还窄），`bottom: 132px` 变成「这个小盒子上方 132px」，浮层于是被顶到屏幕上半部。它看起来仍然水平居中在按钮上方，正是因为包含块本来就是按钮自己——这个巧合掩盖了「位置算错了」这件事。
- 解决办法：`page.tsx` 的居中改用 `-ml-8`（按钮 `size-16` 的一半，不产生 transform），浮层宽度从百分比改成按视口的 `w-[calc(100vw-40px)]`，两处都写了注释说明为什么不能用 `-translate-x-1/2`。顺手全仓核对了一遍其余 `fixed` 元素，暂无第二个同款组合。
- 无效尝试：只调 `max-w`、只加 `whitespace-nowrap`——都在改「多宽」这个结果，而真正错的是「以谁为基准算宽度」。
- 结论：`fixed` 不等于「相对视口」，它相对的是**最近的、带 transform / filter / will-change / contain 的祖先**（构建工具、动画库、居中小技巧都可能顺手加上）。要断言「相对视口」，就别让祖先带这些属性；宽度也别只写百分比——同一个表达式在两种包含块下算出来的数字能差十倍，而 `tsc`、`oxlint`、构建检查一样都不会报警，只能起来看。

## 2026-09-12 批量改 import 的脚本把注释里的类名当成真引用

- 现象：切包后编译报 `SafetyGuard is not public in com.team.silveragent.application; cannot be accessed from outside package`。报错的两个文件（`agent/MedicalBoundaryRules.java`、`agent/RuleFactExtractor.java`）正文里一次都没用过 `SafetyGuard`，只在**注释**里提到它。
- 根因：迁移脚本判断「这个文件要用哪些类」用的是 `grep -E "\b类名\b"`，注释里的提及和真调用一视同仁，于是给两个文件补了 import。`SafetyGuard` 是包级私有，从别的包 import 它直接编译不过——这次是编译器替我们发现了。
- 更隐蔽的是同一次脚本的另一半：它还给 `health/` 下三个文件补了 `import ...memo.MemoParser` / `MemoStore`，同样只服务注释里的 `{@link}`。这三个**编译得过**，于是悄无声息地让子包依赖图多出三条根本不存在的边（`health → memo`）。下一个做结构分析的人（包括写这段脚本的人）会照着这张假图去理解代码。

## 2026-09-12 移了源码却没清 `target/`，Spring 报 bean 重名

- 现象：把 `MemoryStore` 从 `application/memory/` 移到 `application/longterm/` 后跑测试，**317 项里 207 个错误**，报 `ConflictingBeanDefinitionException: bean name 'memoryStore' for [com.team.silveragent.application.memory.MemoryStore] conflicts with existing, non-compatible bean definition of same name and class [com.team.silveragent.application.longterm.MemoryStore]`。看着像代码改错了。
- 根因：`git mv` 只动源码，`target/classes/` 里旧的 `application/memory/MemoryStore.class` 还在。Spring 扫的是**编译输出目录**，两个 simpleName 相同的类都在 → 默认 bean 名（`memoryStore`）撞车。整个过程**编译完全通过**，所以上一步的「编译过了」并不能说明运行时状态是一致的。
- 附带的坑：`mvn clean` 删不掉 `target/`，报 `Device or resource busy`——占用它的不是 maven，是 **VS Code 的 Java 语言服务器**（`redhat.java`）在盯着这个目录。不用去杀 IDE：`clean` 失败之前已经把内容删空了，接着跑 `mvn test` 就是全新构建。
- 解决办法：清空 `target/` 后重跑，317 项全绿。
- 结论：**改包名或类名之后，唯一算数的验证是「清空 `target/` 再构建」**；增量编译的绿只证明源码能编译，不证明运行时加载到的类是对的。还有一个现成的判据：Spring 应用里同一个 simpleName 的类若同时存在于两个包，bean 名必然冲突、启动必然炸——**没炸就说明没有重复**，可以用它反过来确认历史那几次验证是干净的。

## 2026-09-13 模型已经说清了意图，Java 还用原句关键词把它改回去

- 现象：取消支线立着的时候，老人说一句「我那个号不要了，都不取消也行，就查查我有哪些预约」。模型这一轮给的是**合法**的只读调用 `appointment.queryMine`（它就是照字面意思查一眼），Java 却因为原句里有「都不取消」这四个字，接手生成了**整组**取消确认卡——两条已确认预约全在卡上。老人在屏幕上看到的是一张他没要求的取消卡，只要点一下「确认办理」就真取消了。
- 根因：关键词兜底那段判断的是「动作类型像不像确认」和「句子里有没有批量取消的字眼」，**从不看模型这一轮到底给出了什么**。它是在模型还只会输出 intent 的年代写的，那时 Java 是唯一能理解句子的地方；模型能给出结构化工具调用之后，这段兜底就变成了**第二套意图判断**，而且优先级更高——它覆盖的是已经通过校验的那一套。
- 决定性的细节：它只在「模型没给出可用工具调用」时才该跑。模型给出合法调用的那一刻，意图就已经由**它**说定了；此时再拿原句关键词去覆盖，等于用一套更粗糙的规则否掉一套更精确的结果。所以门不是「有没有取消字眼」，而是「这一轮模型有没有被接受的工具调用」（`AgentRuntime.Outcome.acceptedToolCall()`，即 `modelDriven && proposedTools != null && !proposedTools.isEmpty()`——按构造它必然已经过校验）。
- 怎么确认修好了：把守卫改回旧样子重跑，那张**莫须有的 2 条批量取消卡立刻又出现**；加回守卫就不再出现，库里一条没动。**能反向复现的修复才算修复**——只跑绿色用例不足以说明堵住的是那个洞，只能说明没碰坏别的。
- 结论：**「模型给的合法工具调用」和「Java 的关键词兜底」是两套意图判断，同时生效就一定会有一套是错的，而且错的总是更粗的那套。**规则链路的每一处兜底，都要问一句「模型已经说清了的时候，这一段还跑不跑」；从 intent 时代活到工具调用时代的兜底，是这类错的集中地。
- 后续（2026-09-13，第四阶段）：这条门里的 `AgentRuntime.Outcome.acceptedToolCall()` 已改名为 `hasContractCheckedToolCall()`——名字该说的是「契约查过了」而不只是「有东西」，见 DEC-022 决定六。上面提到的「按构造它必然已经过校验」这一点，现在写进了那个方法的注释里，不再只靠调用点自己知道。

## 2026-09-13 给采集器加一个「兼容用」的旧构造器，生产调用点会静默退回弱校验

- 现象：`PlannerTool` 从 `(name, description, risk, List<String> arguments)` 扩成 `(name, description, risk, List<ToolArgument> arguments, List<ToolConstraint>)` 后，为了让只传旧式参数名的 `LlmConversationPlannerTests` 继续编译，保留了一个收 `List<String>` 的旧构造器。编译到 `ToolRegistry` 时报 `List<ToolArgument> cannot be converted to List<String>`——**编译不过，这次是运气好**。
- 根因：Java 泛型擦除后 `List<String>` 与 `List<ToolArgument>` 的签名一模一样，**两个 4 参构造器不可能共存**，所以旧的那个只能是 `List<String>`。生产侧 `ToolRegistry` 传的却是 `List<ToolArgument>`。如果当初为了「让它编过」而把生产侧的调用点改成传字符串名（看着也一样能跑，只是没有类型），那么所有工具的声明会**静默退回「都算可选字符串」**——必填、枚举、字段组合约束全部消失，而 `mvn test` 仍可能全绿：弱校验放行的正是那些本来就不该被拦的调用，红灯只在有人递上非法参数时才亮。
- 解决办法：生产调用点一律走新的 5 参构造器（`ToolRegistry` 的 `register(...)` 是唯一入口），旧 4 参构造器只留给不启动 Spring 的旧测试，并在注释里写明它的用途。让编译器去挡住这个方向——它这次确实挡住了。
- 结论：**「为了兼容旧调用点」加的弱类型重载，最容易的结局是被新代码误用成正常入口**，然后校验一层层松开而没有任何一方报错。兼容层要窄到只有旧测试能走（包级私有、或名字带 `legacy`），生产入口只留一个；这次更是印证了上一条的老话——**批量改写如果编译不过，那反而是好事**。

## 2026-09-13 只读工具的参数被当成「老人改了草稿」

- 现象：老人手头正在办一笔 9月19日的预约，问一句「帮我查一下下周三心内科有没有号」。真模型给出的参数是 `appointment.querySlots {"hospital":"市第一医院","department":"心内科","date":"2026-09-16"}`——查询本身没错，但**待办理的那笔预约的日期被改成了 9月16日**。老人只是问了一句，草稿就动了。
- 根因有两层，两层都要堵：
  1. `LlmConversationPlanner.facts()` 有一层兼容：模型把参数写在 `arguments` 而不是 `facts` 节点时，仍按老格式抽出来当事实。这层兼容是给办理/确认类动作写的——那类动作的参数确实就是老人刚说的条件；对只读查询则完全相反：参数里的医院和日期是「这次要查什么」，不是「他改了主意」。修法：只读工具（`CALL_READ_TOOL(S)`）不再拿 `arguments` 兜底 facts，事实只认 `facts` 节点。
  2. 就算只认 `facts`，模型仍会把查询条件同时抄进 `facts`（真模型实测：`arguments` 和 `facts` 里都是 09-16）。工具循环里 `applyFacts` 照单全收，草稿照样被改。修法：**模型发起的号源查询这一轮整体不写草稿**——交给业务流程的是 `withoutDraftWrites(...)` 那一份 facts（医院/科室/日期/时间/陪同/通知全部清空，致谢与情绪照旧），`appointment.querySlots` / `appointment.queryNearbySlots` 本身也只走只读出口。
- 结论：**「工具的参数」和「老人对草稿的改动」是两件事，不能共用一条从 arguments 到 facts 的兜底路径。** 只要一条链路上既有「查询」又有「办理」，就要问一句：这个参数是在说「查什么」，还是在说「改成什么」？只读工具的参数永远只属于前者。
- 2026-09-14 补：提示词侧也已明确「只读查询条件写对应工具的 `arguments`，`facts` 只写老人明确要改草稿的事实，只是询问别处时不要同时写进 `facts`」，并加了 `AgentSystemPromptQueryFactsTests` 钉住。**提示词是提醒，不是护栏**——它降低模型这么写的概率，Java 侧「模型发起的号源查询这一轮不写草稿」这条仍然一条不少。
- 附带的一条：`queryNearbySlots` 原来会顺手把 `state.acceptAlternative` 置为 true。查一次附近日期不等于老人答应了「可以换日期」——**一次查询不能替他表态**，这条意愿只能由他自己的话或按钮来表达。

## 2026-09-13 续跑轮把「复述」当成了新查询，标签换一个坏法就换一种

- 现象：工具结果回到模型之后，模型不再提工具，只把它刚查到的条件又抄进 facts、用一句话作答（「9月16日有号，您想约哪个时间？」）。这一轮要是再按「查询」走一遍，同一句话就既改了草稿、又白查一次。真模型**连续 4 次跑出 3 种不同的坏结果**：草稿日期被改成刚查的那天；草稿日期被 `resetAfterDate` 抹成「待确认」；回复里一个按钮都没有。
- 根因：续跑轮没有独立的处理路径，直接 `dispatchOutcome` 进了业务流。业务流按「老人这一轮说了什么」处理，而它拿到的是模型**转述的查询条件**，于是拿草稿+这些条件重新查了一次、并且作答。
- 关键细节：**判据不能看 intent 标签**。实测同一句复述，模型给的标签在 `QUERY_AVAILABLE_SLOTS`、`CREATE_FOLLOWUP`、`CURRENT_FLOW`、`CHANGE_DATE` 之间摇摆；`CHANGE_DATE` 那条最凶——它走 `resetAfterDate`，先把草稿日期抹掉再按带回来的日期重查。按标签判的写法（只看落点是不是号源查询）在真模型下根本不成立，是桩测试里恰好碰对了。
- 修法：**不按标签判、也不留跨轮状态**——工具循环里的每一轮都是「模型看着真实工具结果作答」。所以收口一律走 `finishToolLoopDecision`：只交付三样东西——上一轮那份真实查询结果、模型这句回答、或一句兜底说明，**不写草稿、不重新进预约业务流**。要改草稿，只能等下一轮模型明确提业务动作（`PROPOSE_WORKFLOW_ACTION`），或者完全不经过模型的按钮流程。
- 还有一段同源的：「查医院 → 查号源」链路的第一段（模型用 `hospital.search` 问「您说的是哪一家」）也会把这一轮的日期写进草稿，然后拿**草稿里的旧医院**去查号作答，把模型那句澄清顶掉。老人问的是「市医院」（系统里两家），得到的却是一段市第一医院的号源答复。修法同上：`withoutDraftWrites` 在进业务流程前把医院/科室/日期一并清空，`RESOLVE_HOSPITAL` / `RESOLVE_DEPARTMENT` 这一轮的 facts 落不到草稿上。
- 结论：**续跑轮不是「老人又说了什么」，是「模型看着真实工具结果作答」。** 凡是「按老人这一轮说的话去改状态」的代码，都不该在这一轮跑。同一个道理在 2026-09-13 早先那条「模型已经说清了意图，Java 还用原句关键词把它改回去」上已经出现过一次——那一回被覆盖的是意图，这一回被覆盖的是澄清问句和草稿。

## 2026-09-14 只读出口的分界挂在「参数给没给」上，模型传个空参数就绕回旧状态流程

- 现象：把「模型发起的号源查询只查不改」实现成「**参数非空**才走只读出口」之后，模型调 `appointment.querySlots` / `appointment.queryNearbySlots` 却传 `arguments:{}`（只说了「帮我看看号」「还有别的时间吗」，条件留给草稿）时，`toolArguments` 取回空 Map，代码就掉回 `showAvailableSlots` / `queryNearbySlots` 那条**会改状态**的旧路：阶段被推到 `NO_SLOT`、附近号源写进 `state.alternatives`、回复里带出代表草稿已经推进的 `SELECT_SLOT` 按钮。老人只是问了一句，界面已经摆成「选一个吧」。
- 根因：**分界判据选错了。**真正决定「这一轮该不该动状态」的是**这一轮是不是模型发起的只读调用**，与它给了几个参数无关——参数为空恰恰意味着「条件从草稿里取」，而不是「回到办理流程」。用「参数给没给」当分界，等于把「模型没点名条件」这件常事和「这不是只读查询」混为一谈；而空参数在真模型下很常见（条件都摆在草稿里，它没必要重复一遍）。
- 修法：入口只看 `outcome.modelDriven()`。模型发起的（`arguments` 为空也一样）一律走 `resolveSlotQuery(state, arguments, ...)`——缺的项本来就从草稿里取；够用就 `answerSlotQueryReadOnly`，不够就追问；不推进阶段、不动 `alternatives` / `selectedSlot` / `acceptAlternative` / 确认卡。只有 `modelDriven()==false` 的按钮/规则流程才继续走 `showAvailableSlots` / `queryNearbySlots`。
- 测试里的连带修正：把「`arguments={}` → `NO_SLOT` + `SELECT_SLOT` 按钮」当成正确行为的用例改掉（那是旧实现的产物，不是期望），换成「阶段与草稿原样不动、不出现代表草稿已推进的选择按钮」，并补一条反面对照——非模型的按钮流程仍要能写进草稿、仍要摆出 `SET_PERIOD` / `SELECT_SLOT`，免得把预约办理入口一起收窄掉。
- 结论：**给「只读出口」定分界时，判据要落在「谁发起的」而不是「带了什么参数」。**参数是内容、是这一次查什么；发起方才是权限、是这一轮能不能改状态。把两者混在一处，模型少写一个字段就能把写路径重新打开——而它少写一个字段是完全正常的用法。
- 范围边界（这一轮同时收窄了措辞）：本轮只做到 `appointment.querySlots` 与 `appointment.queryNearbySlots` 的模型调用只查不改。其余只读工具尚未逐个按同一口径核对——`hospital.search` 仍可能更新会话里的解析状态，所以**不能**写成「所有 READ_ONLY 工具都已收口」。

## 2026-09-14 新读取把记忆按来源分了类，可提示词里那条老路仍把全部记忆原文塞给模型

- 现象：8A 新加的 `profile.memorySummary` 仔细按来源把记忆分成「明确偏好（`SOURCE_USER_STATED`）」「预约沉淀（`SOURCE_CONFIRMED_BOOKING`）」「来源不明（只计数、不外带内容）」三摞，测试也据此断言。但同一轮里，**提示词中仍然出现了来源不明那条记忆的原文**——`ProfileReadTests.explicitPreferenceBookingFactTendencyAndCurrentRequestAreToldApart` 里对 `gateway.lastToolPhasePrompt` 的 `doesNotContain("来路不明的一条记录")` 断言失败。
- 根因：**这不是新读取的结论，是一条 8A 之前就有的旁路。**`knownFacts(state)` → `memoryNote(state)` → `memories.digest(state.userId)` 会把**全部 `active=TRUE` 的记忆（不分来源）**用「；」拼成一句，塞进证据的 `appointmentDraft` 字段，原文是「这位老人以前办过的复诊情况（仅供参考，不要当成这次已经定好的安排，拿它少问一句就好）＝…」。它比新读取更早、路径更短，所以新读取分得再干净，也挡不住同一个模型在同一轮的提示词里读到原文。
- **这不是「将来才会出问题」，它当时就已经在违反要求了。**8A 初版把它记成「潜在风险、目前还不会产生实际问题」，理由是唯一写入点只写 `SOURCE_CONFIRMED_BOOKING`、分类不会打架——这个判断是错的，看的是「分类会不会打架」，而真正的要求是「一次预约不能自动成为长期习惯」。而 `rememberBookingPreferences` 恰恰在**只有一次预约**时就写下「常去的医院是……」「常去的科室是……」「习惯上午复诊」，`digest` 又把这三句原样送进每一轮提示词。一次预约 → 一条「常去」→ 模型张口就说「您常去这家」。旁路当场就在生效，跟 `SOURCE_USER_STATED` 有没有写入路径没有关系。
- 修法（本轮已做）：`knownFacts(state)` 里**删掉** `memoryNote(state)`，默认上下文里一个字的记忆都没有，画像统一走 `profile.memorySummary` 按需查（带来源、带更新时间、支持越权拒绝）；`MemoryStore.digest` 保留但降级成「不是主模型的画像入口，新代码不要用」；写入措辞改成中性历史事实——「最近一次确认预约的医院是……」，`kind` 统一成新增的 `MemoryStore.KIND_HISTORY`（原来给时段标的 `PREFERENCE` 会让同一条系统归纳的记录带上「这是偏好」的标签）。
- 测试里的处理：**没有把断言挪到 `ProfileQueryService` 的返回值上绕开**。`ProfileReadTests` 新增 `oneBookingNeverReachesTheModelLabelledAsAHabit`，真走一遍办理+确认（确认后确实写了三条记忆），再开一段新对话，断言**模型收到的每一条非 system 消息**里既没有「常去」「习惯」，也没有那三条记忆的原文；`UserMemoryTests` 新增 `oneBookingIsStoredAsAHistoryFactNotAsAHabit`，在存储层断言措辞里不出现「常去」「习惯」、类别不是偏好。只有系统提示词自己带着「不许说常去／习惯」这条禁令，所以断言过滤掉了 system 消息——禁的是模型把一次预约当习惯说出去，不是禁止提示词教它别说。
- 结论：**入口收窄了，不等于同一份提示词里没有别的入口；「分类不会打架」也不等于「要求已经满足」。**做「按来源分类」这类读取侧改造时，要连带查一遍「同一轮还会不会有别的代码把原始数据拼进去」；判断一条旁路算不算问题，要拿要求的原文去量，而不是拿「新写的这段逻辑会不会被它干扰」去量。这两条各自都能让一个当场生效的缺陷被写成「潜在风险」。

## 2026-09-14 手上已经有确认卡时，只读工具循环压根不叫模型——证据段落是空的

- 现象：写「老人手上已经有一张待确认的卡，这一轮只读推荐要把它原样带回来」这条用例时，断言落在 `gateway.lastToolPhasePrompt`（模型收到的工具证据）上，跑出来是空字符串。第一反应是「工具没执行」或「证据没拼」，但同一用例对「卡还在、`conflicts` 没被写」的断言全过——说明查询确实跑了、卡也带回来了，只是模型没被叫过。
- 根因：`runModelToolLoop` 在 `latestToolResponse.confirmation() != null` 时直接收口（`finalizeToolEvidence(state, latestToolResponse, latestToolResponse.reply())`），**不再调 `continueAfterTools`**。这是 4A/4B 确认链路的既有设计（拿回一张待确认卡就是终态，不该再让模型对着一张卡自由发挥）。`answerReadOnly` 又会把手上那张卡原样挂回响应，于是「只读推荐 + 有卡」这个组合必然走这条短路。
- 为什么容易看错：**这一轮的结论确实产出了，只是写在 `result.reply()` 里而不是证据里。**拿 `lastToolPhasePrompt` 当「Java 说了什么」的通用探针，在「没有卡的普通轮」上一直是对的——正因为它平时都对，空字符串看起来像 bug 而不像「这一轮根本没走到那儿」。
- 处理：这条用例改成断言 `result.reply()`（Java 自己写的冲突结论），并在注释里写明「手上已经有待确认卡时，只读循环会在拿回卡的那一步直接收口，不再叫模型，所以证据段落是空的」。**没有为了迁就断言去改确认链路的短路**——那是 4B 的既定行为，改它会动到「老人对着卡片点头」那条链路。
- 结论：**「证据段落为空」可能是「没走到那一步」，不是「那一步做错了」。**在一个横跨多层（规划 → 工具循环 → 答复生成）的系统里，探针选在哪一层，决定了失败信息到底在说哪一层的事；断言失败时先问「这行代码这一轮跑了吗」，再问「它跑错了么」。

## 2026-09-14 拿模型原文当回复来断言：回答阶段的产物不是规划阶段的产物

- 现象：写「Java 自己拼的推荐明确说不评价医院好坏」这条断言时，拿到的 `result.reply()` 是**一整段原始 JSON**——`{"actionType":"PROPOSE_WORKFLOW_ACTION","intent":"REQUEST_RECOMMENDATION",...}`，一个中文字都没有。
- 根因：**一轮对话里有两次模型调用，用途完全不同。**规划阶段（`LlmConversationPlanner.requestModel`）产出的是决策 JSON；回答阶段（`LlmAnswerGenerator.generate`）产出的是给老人看的一句话。`LlmAnswerGenerator.replyOf` 会先试着把它当 JSON 解出 `reply` 字段，解析不出来就**原样返回整段文本**——而桩模型对自己不认识的提示词只会回同一段规划 JSON，于是那整段 JSON 就成了「回答」。`valid(...)` 判非空即通过，不会拦。
- 为什么容易看错：**在其他用例里这个错误会被掩盖。**桩模型的 `planning` 恰好是一段 `ANSWER` JSON 时，`replyOf` 能抽出 `replyDraft`，看起来一切正常；只有像本条这样把 `planning` 设成 `PROPOSE_WORKFLOW_ACTION` 的用例，才会把「回复 = 模型原文」暴露出来。而且 `quickReplies()` 在两种情况下都对（它由 Java 的 `respond` 摆，跟模型无关），所以「候选数正确」这类断言**同时通过**，更容易误判。
- 处理：给桩网关加一个 `lastAnswerPrompt`（在最后一条用户消息包含「权威回复草稿」时记录），把断言从 `result.reply()` 挪到它上面，并在字段注释里写明「Java 自己拼的推荐话术是作为『权威回复草稿』交给回答模型润色的底稿，只能在回答阶段的提示词上验」。**没有把断言挪到 `recommendHospitals` 的返回值上**——那等于绕开「这句话真的进了模型」这一步，而这一步正是要验的。
- 结论：**一轮对话里的两次模型调用要分开验：规划阶段验「它选了什么」，回答阶段验「Java 给了它什么底稿」。**拿最终回复去反推 Java 的结论，只要桩模型诚实回一句别的话，就会把模型的行为误算成 Java 的行为。

## 2026-09-14 断言里的中文串是从脑子里拼的，不是从代码里读的

- 现象：三条断言一开始都写错，且都不是逻辑错——`预约时段偏上午`（代码拼的是 `预约时段偏是上午`）、`市第一医院（模拟）`（目录读出来的名字没有「（模拟）」）、`市第一医院` 与后面紧跟的一句「不冲突」挂错了对象。
- 根因分两类，**两类都值得分开记**：
  - **纯拼接细节**：`appointmentHistoryText` 里是 `itemLabel(PERIOD)` + `"是"` + `tendencyLabel(...)` 拼出来的，读代码才知道中间那个「是」。凭语感拼串一定会漏掉连接词。
  - **数据来源搞反了**：`data.sql` 里医院名确实写着 `市第一医院（模拟）`，但 `CareCatalogRepository.stripSimulated` 在读出来的时候把「（模拟）」**剥掉了**——所以「库里写的是什么」和「工具返回的是什么」可以不一样。更隐蔽的是，模型收到的那段证据里同时有医生端的**预约记录**（`appointment_slots.hospital_name`，种子值带「（模拟）」）和目录端的**医院名**（被剥过），两个来源共处一段文本，凭印象挑一个就有一半概率挑错。
- 处理：三条断言全部改成从**运行输出**里读回来的真实串（把 surefire 报告按 UTF-8 读出来看 actual），并在注释里写明「目录里的名字带着『（模拟）』已经在 `stripSimulated` 里去掉了，这个标识只能由 Java 自己的措辞兜住」。**没有去改 `stripSimulated`**——那是既有行为，本轮不动。
- 结论：**断言里的中文串要从代码与真实输出里抄，不能从语义里推。**凡是「拼接出来的句子」和「被转换过的数据」，凭印象写的期望值失败率极高；而且这类失败长得像逻辑错（`expected: ... but was: ...` 两个都很像对的中文），会把人往错误的方向带。先读 actual，再决定是代码错了还是断言错了。

## 2026-09-14 用「参数形状」区分两种语义，重叠处必然要发明临时规则

- 现象：8B-1 第一版把 `travel.routePlan` 的两种用法压进「带了哪些参数」：有 `appointmentId` 就是看已确认预约、有 `hospital`/`date`/`time` 就是候选估算。审查一眼指出不成立——**两种用法都可能带交通方式**，参数集合本来就重叠。
- 根因：**「参数形状」只在两组参数互斥时才是判据。**一旦重叠，就必须补一条「谁优先」的规则（比如「同时给了 appointmentId 和 hospital 时按 appointmentId 算」），这条规则对模型是不可见的：它读到的只是工具描述里几行参数说明，没有地方写着这个优先级。更糟的是这种规则**没法被工具描述表达清楚**，只能靠 Java 里的一行 `if` 悄悄生效。重叠处还恰恰是最需要明确答复的地方——老人说「我要打车去市一，顺便看看我那条预约的路线」，两种语义都成立，任何静默选择都可能答错。
- 修法：加一个**结构化的 `mode`（枚举）**，把「是哪一种」变成模型必须显式给出的字段；不给 `mode` 时**只在参数唯一明确时推断**（兼容旧调用），**混着给一律澄清**，不猜。`ToolArgument.enumeration` 的既有归一化（trim + 大写）直接用上，没有新机制。
- 结论：**当两种语义的差别不是「参数集合不同」而是「意图不同」时，就把它写成一个字段，不要指望从参数集合反推意愿。**反推的规则一旦有例外，例外就成了只有 Java 知道、模型和测试都不知道的隐式契约。

## 2026-09-14 多个目标要塞进 `Map<String,String>` 时，最容易顺手发明分隔符

- 现象：要让 Java 知道老人这一轮排除了哪几家医院（可能不止一家），工具参数那层是 `Map<String,String>`，第一反应是「用顿号或逗号拼成一个字符串，Java 再拆」。
- 根因：**医院名自身就可能包含候选分隔符。**目录里的名字带括号（「市第一医院（门诊部）」），老人说话也会带顿号。一旦用分隔符，**切错就等于 Java 替模型猜它排除了谁**——而这一轮的整个要求恰恰是「认不准不能猜」：猜错的后果是把一家老人没排除的医院从候选里拿掉（他可能因此选错医院），或者把一家排除了的留下（直接违反要求）。更根本的是，分隔符约定需要模型和 Java 两边**逐字遵守同一套转义规则**，而转义规则既写不进 `ToolArgument.text` 的描述，也无法被测试穷举。
- 修法：**换一个本来就能表达数组的通道。**规划 JSON 的 `facts` 节点在 `LlmConversationPlanner` 里本来就是 `JsonNode`，直接读数组（单个字符串也接受）是假设最少的表达，于是把它读进 `ExtractedFacts` 的第 17 个组件。**明确不做**：不做中文分词、不做同义词表、不按「、」拆字符串。单个目标也走同一字段（接受字符串形态），不搞两套路径。
- 结论：**当一个契约的表达能力不够时，先问「有没有另一个已经存在的通道能表达它」，而不是先发明一套编码。**自己发明的编码（分隔符、前缀标记、「用 | 分隔」）会把一条本可以被类型系统保证的约束，降级成一条靠所有人自觉遵守的约定。

## 2026-09-14 「等于此刻」的边界，三个地方各写各的，就会有一小时说两种话

- 现象：`checkConflictReadOnly` 原来写 `start.isBefore(clock.now())`，把**正好等于此刻**的整点判成「还没到」，于是老人问「九点冲突吗」得到「不冲突、可以约」；而他真的点确认时，闸门（`slotAlreadyPassed`，`!时间.isAfter(now)`）说已经过去了。**同一个整点，同一个小时里两个答案**——老人拿到的是一个永远确认不成的时段。
- 根因：**同一个边界被写了三遍，其中一遍漏了等号。**号源查询的 SQL 是 `appointment_time > 当前时间`（等于不算），确认闸门是 `!isAfter`（等于算过去），日程比较是 `isBefore`（等于算未来）。三处各自都「看起来合理」，单独读任何一处都挑不出错；只有把三处摆在一起、并且**用一个正好等于此刻的时间去试**，矛盾才会显形。而真实时钟几乎不会停在整点毫秒上，所以这个缺陷在手工测试里基本复现不了。
- 修法：统一成 `!start.isAfter(clock.now())`，并把理由写进那一行的注释（指出另两处的口径，说明不统一的后果）；测试用 `Clock.fixed` 把业务时钟钉在北京时间 09:00 整，**同时验 09:00（边界本身，必须算过去）和 09:30（同一小时里晚一点，必须照常比较）**两个方向——只验边界本身，改回 `isBefore` 也可能碰巧通过。
- 结论：**边界口径要当成一条跨模块的契约来维护，而不是每处各写一遍。**凡是「等于算不算」这类判断，落笔前先找出代码里已有的同类判断，对齐它、并把「我对齐的是谁」写进注释；测试要能证明它**在边界上和在边界外行为不同**，否则测的不是边界。

## 2026-09-14 对着整段提示词断言「不含某家医院」，一定会被 Java 自己的工具结果打脸

- 现象：三条「被排除的医院不能出现在推荐里」的断言，都写成「`lastAnswerPrompt` 不含 `市第一医院`」，跑出来全红；但人工看推荐文字与快捷按钮，**过滤其实是对的**。
- 根因：`lastAnswerPrompt` 是一整段拼起来的提示词，里面除了 Java 要给老人看的那句话，还塞着**这一轮的只读工具结果原文**——`catalog.recommendHospitals` / `catalog.queryHospitals` / `catalog.queryDepartments` 返回的候选与全目录，本来就**完整列出所有医院**，被排除的那家也在里面。于是断言量的其实是「目录里有没有这家医院」，而不是「推荐给老人的话里有没有」。
- 为什么容易写错：**这个探针在别的用例里一直好用。**它是「模型收到了什么」的最短路径，绝大多数断言关心的恰好就是「模型收到的东西里有没有某句不该有的话」。只有当被测的行为**只作用于提示词的一部分**（这里是「权威回复草稿」那一行）时，它才失效——而失效方向是**误报**（过滤对了却红），容易让人去改本来正确的生产代码。
- 修法：加一个 `authoritativeDraft()` 辅助方法，从 `lastAnswerPrompt` 里**只取以「权威回复草稿：」开头的那一行**，六处断言改到它上面。**没有把断言挪到 `recommendHospitals` 的返回值上**（那等于绕开「这句话真的进了模型」这一步），也没有去改工具结果里列全目录的行为（工具本就该返回完整结果）。
- 结论：**断言要落在「被测行为的输出面」上，而不是落在「整个容器」上。**同一个提示词里同时装着「Java 的决定」和「Java 摆给模型的原始证据」，两者混在一起时，「不含 X」这类否定断言会被证据里的 X 误伤；先问清「这个 X 是出现在哪一段」，再决定探针取多宽。

## 2026-09-14 「轮内约束」只在第一轮看，就等于没有——循环里的状态要跟着循环走

- 现象：排除过滤做对了，用例也绿了，但审查一眼看出它只在「模型第一跳就要推荐」时生效。真实的走法是：老人说「推荐心内科，别给我市一」，模型先点 `appointment.history`，拿到结果之后**下一轮才说推荐**——而那一轮的 `facts` 里它未必再写一遍 `excludedHospitals`。排除集合丢在循环外面，被排除的医院照样从推荐里回来。
- 根因：**把「一次用户消息的条件」当成了「某一轮决策的条件」。**`runModelToolLoop` 的每一轮都是一次独立的模型调用，每一轮都有一份自己的 `facts`；只读首轮或只读末轮，都会漏掉中间。而**丢掉的那个方向恰好是危险的方向**：约束丢了，过滤就没有了，而那正是审查要求「不能悄悄恢复」的东西。
- 为什么原来的用例没发现：**旧用例断言的是「没有查历史」**（`traceCount(id, "appointment.history")).isZero()`），也就是它证明的是「这条路上历史没参与」，而不是「历史参与了也不会把它带回来」。**用「某件事没发生」当断言，很容易在真实路径换了之后继续绿**——它绿不代表功能对，只代表那条分支没被走到。
- 修法：引入 `TurnReadConstraint`，进循环时从首轮 facts 建起、每轮 `continueAfterTools` 之后并入新的 facts（排除目标取并集只增不减），收口时用它。它是**循环里的局部变量**——不落会话状态、不进长期记忆，方法返回就没了，所以「下一轮改口就能重新推荐」不需要额外的过期逻辑。
- 结论：**跨轮的状态要显式地跟着轮次走，别指望「第一轮说了后面都还在」。**写这类循环时先问一句「这个约束在第二轮、第三轮还在吗」；反过来，写测试时别用「某个东西没发生」来证明「它发生了也不会出问题」——那种断言在实现换了一条路之后照样是绿的。

## 2026-09-14 说明书说「两种模式都能带」，判据却把它当专有——不一致的地方一定在参数上

- 现象：`travel.routePlan` 的工具说明写着「两种模式都可能带 transport」，而 Java 里 `hasRouteCandidateArguments` 把 transport 算作候选专属。于是 `mode=APPOINTMENT + appointmentId + transport` 被误判成「预约编号与候选条件混用」，正常的看地图请求被拦下来追问一句。
- 根因：**同一条参数契约被写了两遍，两遍不一样。**说明那一遍给模型看，判据那一遍给 Java 用。上一轮的修改正是冲着「不能再把整条工具描述成一概而论」去的，结果只在描述里把两种模式分开写、判据那边没跟着改——**描述改了、判据没改，比两边都含糊更糟**：含糊至少不会把正常请求判错。
- 为什么没被测试发现：混用那条用例给的是 `appointmentId + hospital`——**hospital 在两个口径里都是「候选专属」，所以它对「transport 算不算」完全不敏感**。参数契约的用例要覆盖每一种参数的每一种组合，缺一格就等于没有那一格。
- 修法：定死一种契约（transport 只属于 CANDIDATE，APPOINTMENT 忽略它），然后**四处一起改**：工具描述、系统提示词、Java 注释、测试。并且把判据拆成两个名字——`hasRouteCandidateArguments`（有没有给 CANDIDATE 要的东西，含 transport）与 `hasRouteCandidateLocation`（有没有给「哪一家、哪一天、几点」，不含 transport），混用检测只问后者。
- 结论：**工具参数的契约是一份四处引用的文档，改一处就要顺着找齐另外三处。**改完顺手想一遍「哪一个参数的哪一种组合我还没试过」——参数组合的用例漏掉一格，那一格的判据就没人看。

## 2026-09-14 用来当证据的那张表，Java 自己也在写——顺序错了就等于亲手替模型造证据

- 现象：让模型在 `evidenceRefs` 里写「这条理由出自哪个工具」，Java 去真实工具记录里核。用例却出现「模型引了 `hospital.list`（它这一轮根本没调过），校验却通过了」。
- 根因：**校验函数自己也查目录。**`checkRecommendations` 要靠 `prepareCandidates` 从真实目录算出本轮候选，而那次查询也经过 `ToolTraceStore` 落一条 `catalog.queryHospitals`。写成 `prepareCandidates(...)` 在前、`traces.since(...)` 在后，Java 自己刚写的记录就在「本轮证据」的窗口里了——模型随便引一个目录工具名都能对上。**这不是边界情况，是必现的**：只要校验要算候选，就会写这条追踪。
- 修法：分界线 `evidenceMarker = traces.latestId(state.id)` 在**进循环时**取一次，`traces.since(...)` 在 `prepareCandidates(...)` **之前**调用。并且把这条顺序写进代码注释（「必须先读证据、再算候选」），因为两行调换不会编译不过、也不会立刻报错，只会让校验静默失效。
- 结论：**只要「读证据」和「写证据」共用一张表，读必须排在写之前。**这类错误有个共同特征：它不改变任何一行输出，只让一道闸门变成摆设——所以闸门本身的用例（「引一个没跑过的工具 → 必须被拒」）比正面用例更值钱，没有它这条会一直绿着。

## 2026-09-14 「模型说过这句话」不能只看最后一个提示词——它会被后面那轮覆盖

- 现象：断言「Java 把 `NO_EVIDENCE_AT_ALL` 退回去并明确要求它先查」时，用例读 `gateway.lastToolPhasePrompt`，结果拿到的是**第二轮工具结果**的提示词，断言失败。而功能其实是对的。
- 根因：**`lastToolPhasePrompt` 是「最后一次」，不是「包含这一次」。**模型被退回去之后，先按提示去点了只读工具，于是又走了一轮工具循环，那个提示词把修正轮的提示词覆盖掉了。**「修正轮去过哪里」这件事只能从整份 messages 里找。**
- 修法：加 `modelPromptContains(String)`（`gateway.messages.stream().anyMatch(m -> m.content().contains(text))`），所有「退回去时说了什么」的断言都改走它。`lastToolPhasePrompt` 只留给「这一轮最后看到的是什么」那种断言。
- 结论：**断言「某轮发生过什么」要用整个历史，断言「当前状态是什么」才用那个「最后一个」。**两类断言共用一个字段时，功能正确而用例变红——这种红最容易误导人往功能上改。

## 2026-09-14 「查了」和「查到了」是两回事——`{"total":0}` 不是空 JSON

- 现象：给「首轮一条工具都没查就给推荐 → 退回 → 它去查了 → 下一轮给合法推荐 → 正常展示」写用例，脚本里它确实调了 `appointment.history`，`traceCount == 1` 也过了，但最终展示的是那句安全提示而不是推荐。
- 根因：两层叠在一起。**其一**，用例的 `resetData()` 会 `DELETE FROM appointments`，所以这条会话的 `appointment.history` 查的是空历史，返回 `{"total":0,"confirmedTotal":0,"returned":0,"facts":[],...}`——**它是一个非空 JSON 对象**，只判「响应空不空」的实现会把它当成「查到了」。**其二**，即便判对了「没查到」，用例的原意是「修正之后真的去查了就该给推荐」，所以真正的修法是**先播一条真实预约**让历史真的有内容。
- 修法：`traceHasResult` 除了判 JSON 空不空，还要看工具自报的条数（`total` / `returned` / `count` / `size`），报了条数且全是 0 就是没查到；用例开头 `seedAppointment(...)` 播一条已确认的历史预约。
- 结论：**「调用发生过」不等于「拿到了内容」，而模拟数据默认是空的。**写「先查再答」这类用例时，第一句就该问「它要查的那份数据，库里真的有吗」——`traceCount == 1` 绿着完全不能证明这一点。
