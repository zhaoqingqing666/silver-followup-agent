# 比赛要求逐条映射

本文件把命题要求转换成可实现、可验证的项目项。表中的“最低实现”表示 Demo 至少要做到什么，不代表必须连接真实医院或真实通信平台。

需求来源：[Requirement.md](../Requirement.md)。本表保留需求编号和目标方案；实现状态、源码证据与缺口以 [Design.md 第 2 节](../Design.md#2-按-requirementmd-对齐) 为准。`ConfirmationGate`、`MissingFieldChecker` 等为概念职责，当前集中在 `FollowupAgentService`；现有领域工具接口共七个，并非下表早期描述的五个。

## 一、总体任务

| 编号 | 要求含义 | 最低实现 | 页面证据 | 后端/Agent证据 |
|---|---|---|---|---|
| G-01 | 理解老年人的复诊需求 | 能识别口语化复诊意图，抽取医院、科室、日期等字段 | 对话中展示用户原话和 Agent 理解结果 | 结构化意图对象 `FollowUpIntent` |
| G-02 | 主动询问缺失信息 | 每次只问一个主要问题，不一次抛出七个问题 | 对话气泡突出当前问题 | 必填字段检查器 `MissingFieldChecker` |
| G-03 | 把需求拆成多个步骤 | 显示预约、材料、日程、出行、提醒、通知等步骤 | 任务计划面板 | `FollowUpPlan` 与步骤状态 |
| G-04 | 调用模拟工具执行 | 工具参数、工具名、返回结果都真实由程序产生 | 工具调用记录面板 | 五个 Tool 接口及模拟实现 |
| G-05 | 关键操作前确认 | 未确认时禁止提交预约、创建提醒和通知家属 | 明确的确认卡片 | `ConfirmationGate` 门禁 |
| G-06 | 处理异常 | 无号源、冲突、信息不全、工具失败等都给替代方案 | 错误说明与可选操作 | 异常类型和恢复策略 |
| G-07 | 适老化反馈 | 大字号、高对比、简短句子、少量按钮、可返回取消 | 全部核心页面 | 回复模板和无障碍状态 |

## 二、4.1 用户需求理解

| 编号 | 原要求要点 | 项目中的实现决定 | 验收方式 |
|---|---|---|---|
| U-01 | 理解口语化、不完整、分多次表达 | 会话上下文持续保存字段，不能只处理最后一句 | 分三句话提供信息后仍能形成完整计划 |
| U-02 | 识别用户可能需要复诊 | Agent 输出 `intent=FOLLOW_UP_VISIT` 和置信说明 | 用“医生让我再去看看”触发复诊追问 |
| U-03 | 询问就诊医院 | 缺失时进入 `ASK_HOSPITAL` | Agent 单独询问医院 |
| U-04 | 询问就诊科室 | 缺失时进入 `ASK_DEPARTMENT` | Agent 单独询问科室 |
| U-05 | 询问期望日期 | 保存标准日期，同时在页面显示易读日期 | 输入“下周三”后显示具体年月日供确认 |
| U-06 | 询问是否接受其他日期 | 保存布尔值，供无号源分支使用 | 无号源时根据该字段给出选择 |
| U-07 | 询问是否需要家属陪同 | 与“是否通知家属”分开保存 | 计划中显示陪同需求 |
| U-08 | 询问是否需要出行提醒 | 决定是否创建出发提醒 | 确认卡片显示提醒开关 |
| U-09 | 询问是否通知家属 | 只有需要时才进入家属通知步骤 | 用户拒绝时不调用通知工具 |
| U-10 | 信息不完整时不能虚构结果 | 必填字段未齐全时禁止进入预约提交 | 测试缺医院时不会显示“预约成功” |

## 三、4.2 任务拆解与计划

| 编号 | 必须出现的任务 | 实现模块 | 页面展示 |
|---|---|---|---|
| P-01 | 查询可预约日期 | `AppointmentTool.querySlots` | 显示查询中、成功、失败状态 |
| P-02 | 选择复诊时间 | 工作流保存 `selectedSlot` | 时段选择卡片 |
| P-03 | 生成复诊材料清单 | `MaterialChecklistService` | 材料清单，可标记“已准备” |
| P-04 | 检查已有日程冲突 | `ScheduleTool.checkConflict` | 冲突警告和原日程摘要 |
| P-05 | 生成出发时间建议 | `TravelTool.planTrip` | 交通方式、预计耗时、建议出发时间 |
| P-06 | 创建复诊提醒 | `ScheduleTool.createReminder` | 确认后显示创建结果 |
| P-07 | 通知指定家属 | `FamilyNotificationTool.send` | 通知对象、内容摘要和状态 |
| P-08 | 向用户展示任务计划 | `FollowUpPlan` | 右侧或顶部任务计划面板 |
| P-09 | 允许取消、修改、重新安排 | 工作流支持修改事件和回退状态 | 每个可修改步骤提供明确操作 |

## 四、4.3 模拟工具调用

| 编号 | 工具要求 | 最低方法 | 模拟数据 |
|---|---|---|---|
| T-01 | 预约查询工具 | `querySlots`、`createAppointment`、`cancelAppointment` | 医院、科室、号源时段 |
| T-02 | 日程管理工具 | `checkConflict`、`createReminder` | 用户日历和提醒列表 |
| T-03 | 出行规划工具 | `planTrip` | 模拟住址、医院地址、交通时间矩阵 |
| T-04 | 家属通知工具 | `sendNotification` | 家属联系人和模拟发送记录 |
| T-05 | 本地程序或模拟接口即可 | 所有工具先使用 Java 本地实现 | JSON 文件或内存数据 |
| T-06 | 不连接真实平台 | 不接真实医院、地图、短信 | 页面明确标注“模拟环境” |
| T-07 | 必须真实展示工具过程 | 后端记录工具名、入参、时间、结果、错误 | 工具调用记录面板不能写死 |

材料清单建议作为第五个工具或独立服务。即使比赛只要求四类工具，材料清单仍是任务计划的必需内容。

## 五、4.4 用户确认机制

| 编号 | 操作 | 是否必须确认 | 项目处理 |
|---|---|---|---|
| C-01 | 提交预约 | 是 | 生成 `ConfirmationRequest`，确认前不可调用提交方法 |
| C-02 | 修改或取消预约 | 是 | 展示旧值、新值和影响 |
| C-03 | 创建日程提醒 | 是 | 展示提醒时间和内容 |
| C-04 | 向家属发送信息 | 是 | 展示接收人和消息摘要 |
| C-05 | 修改已确认计划 | 是 | 重新生成确认请求，不沿用旧确认 |
| C-06 | 确认内容清楚 | 是 | 显示操作、医院科室、时间、通知对象和影响 |
| C-07 | 不诱导确认 | 是 | 按钮使用“确认办理”和“返回修改”，不用“我已知晓”等模糊话术 |

确认不是普通聊天文字，而是工作流中的强制门禁。大模型说“用户应该同意了”不能代替用户点击或明确回复。

## 六、4.5 异常处理

| 编号 | 异常 | Agent 应做什么 | 工作流转移 |
|---|---|---|---|
| E-01 | 指定日期无号源 | 说明原因，列出 2 至 3 个替代时段 | `QUERYING_SLOTS → SELECTING_ALTERNATIVE` |
| E-02 | 与已有日程冲突 | 展示冲突事项，提供换时段或保留选择 | `CHECKING_CONFLICT → RESOLVING_CONFLICT` |
| E-03 | 信息不完整 | 回到对应字段询问 | `* → COLLECTING_INFORMATION` |
| E-04 | 模拟工具失败 | 说明当前步骤失败，允许重试、跳过非关键步骤或返回修改 | `EXECUTING → TOOL_ERROR` |
| E-05 | 中途改变医院或日期 | 清除受影响的旧号源、冲突检查和出行结果并重新计算 | `* → REPLANNING` |
| E-06 | 用户取消整个任务 | 询问是否确认取消；确认后停止后续工具 | `* → CANCELLED` |
| E-07 | 异常不能直接结束对话 | 每种异常都有至少一个恢复动作 | 页面始终保留“返回修改/重新尝试/人工帮助” |

## 七、4.6 适老化交互

| 编号 | 要求 | 设计决定 |
|---|---|---|
| A-01 | 文字或模拟语音输入 | 文本输入为主，提供明显的语音按钮；语音可先模拟转写 |
| A-02 | 简短明确 | 回复拆成短句，一屏只突出一个下一步 |
| A-03 | 一次只问一个主要问题 | `QuestionQueue` 每次只取一个字段 |
| A-04 | 重要信息重复确认 | 日期、医院、科室在计划和确认卡片中重复出现 |
| A-05 | 大字号、高对比度 | 正文字号不小于常规 Web 可读标准，关键结果更大；避免浅灰小字 |
| A-06 | 避免大量按钮 | 每一步最多突出一个主要操作和一个返回操作 |
| A-07 | 可返回、取消、人工帮助 | 页面固定保留三个可发现入口 |
| A-08 | 办理完成后生成事项卡片 | 结果页和主页面底部都能查看最终卡片 |
| A-09 | 卡片包含五类信息 | 时间、医院科室、材料、出发时间、通知状态不得缺项 |

## 八、4.7 安全与服务边界

| 编号 | 用户输入 | Agent行为 | 工具行为 |
|---|---|---|---|
| S-01 | 要求疾病诊断 | 明确说明不能诊断，建议咨询医生 | 不调用预约之外的医疗决策工具 |
| S-02 | 要求药品推荐 | 拒绝推荐具体药品 | 不生成药物清单 |
| S-03 | 要求调整剂量 | 拒绝调整，建议联系开药医生 | 不保存剂量修改 |
| S-04 | 要求解读检查结果 | 不做医学结论，可建议携带材料就医 | 材料模块只判断是否上传/是否清晰，不判断病情 |
| S-05 | 要求替代医生决策 | 说明服务边界 | 终止相关医疗决策动作 |
| S-06 | 明显紧急情况 | 优先提示急救或线下帮助，暂停普通预约流程 | 状态进入 `EMERGENCY_REDIRECT` |

## 九、统一录屏场景

项目必须内置四组稳定的模拟场景：

1. 正常办理：有号源、无冲突、确认后全部工具成功。
2. 预约失败：期望日无号源，替代日有号源。
3. 时间冲突：号源存在，但与用户已有日程冲突。
4. 服务越界：用户询问诊断或用药，Agent 拒绝医疗判断。

这些场景不能靠临时修改代码制造，应由 `scenarioId` 或模拟数据开关稳定复现。

## 十、成果材料需要从系统中留下什么证据

- 设计报告需要：需求映射、架构图、状态机、工具定义、确认门禁、异常恢复、适老化和安全边界。
- 汇报 PPT 需要：业务问题、总体架构、主流程、四类工具、界面截图、四个 Demo 场景和创新点。
- 录屏需要：任务计划、工具调用参数和结果、用户确认、正常与异常结果。
