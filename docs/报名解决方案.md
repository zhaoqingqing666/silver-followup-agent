## 一、命题理解与问题判断

老年人复诊并不只是“挂一个号”。一次完整复诊通常还包含选择医院和科室、查询号源、准备材料、检查日程冲突、安排出行、到院后寻找诊室、设置提醒和通知家属。现有能力往往分散在医院小程序、地图、日历和通信软件中，用户需要记忆办理顺序并在多个页面之间切换。

命题真正考察的也不只是大模型能否回答问题，而是智能体能否在自然交流、可靠办理和过程可验证之间取得平衡：既要听懂老人不完整、口语化和会临时改变的话，又不能虚构号源、误提交预约、越过医疗边界；还要让评委能够看到任务拆解、工具参数、返回结果和确认动作之间的对应关系。

因此，本项目把问题凝练为：**如何用一个低交互负担的自然语言入口，把分散的复诊事务组织成一项可暂停、可恢复、可修改、可确认和可追溯的协同任务。**

## 二、解决方案定位

本项目提供一个面向老年用户的复诊事项协同助手。用户既可以正常聊天、询问流程和材料，也可以在明确表达“我要预约复诊”后进入办理。系统围绕同一项复诊任务串联预约、材料、日程、出行、院内指引、提醒和家属通知，并在关键写操作前展示具体影响、等待用户确认。除预约事务外，系统也承接老人日常真的会提出的两类请求：记录自己量到的血压血糖等数值，以及设置可重复的长期备忘。

方案不是医疗诊断助手，也不是把所有权限交给大模型的自由工具智能体。它采用“模型负责自然理解和低风险规划，Java 程序负责状态、权限、确认和写入，领域工具和数据库负责真实结果”的受控混合架构。

系统同时服务两个端：面向老年人的就诊人端，和面向家属与志愿者的协同照护端。两端用的是同一个智能体、同一套工具和同一道确认门禁，区别只在会话身份。这一点靠**双轴身份**实现：能力轴回答“谁在操作”，决定他能用哪些工具；数据轴回答“这次服务谁”，决定所有查询和写入指向哪位老人。两轴都在会话建立时由后端按绑定关系核实，操作者身份不会进入任何工具参数。因此家人和志愿者可以放心代长辈办事，而不必为家属端再维护一套并行流程。

一句话方案：**让大模型负责听懂和规划，让程序负责把关，让工具负责事实，用一个适老化对话入口协同完成复诊前后的事务——长辈能自己办，家人也能替他办。**

## 三、目标用户与典型场景

主要用户是需要复诊但不熟悉数字化服务的老年人。家属或陪同人是经过授权的信息接收者，社区或医院志愿者可批量协助其名下结对的长辈。这两类照护者不只是被动收通知——在长辈不便时，他们可以在授权范围内替长辈办理，包括代约复诊和给长辈留提醒。

例如，用户可以说：“我下周三想去市第一医院心内科复诊，上午方便，出发前提醒我，也告诉女儿。”系统保存已经明确的信息，只补问缺失项，并生成可持续更新的任务计划。如果用户中途说“我有点害怕去医院”，助手先进行支持性交流并暂停任务；用户说“继续刚才的办理”后，系统从原节点恢复，而不是重新开始。

协同照护端的场景不同。家属进入后先确认这次替哪位长辈办理，之后所有操作都以那位长辈为准：问“长辈下次复诊是什么时候”查的是长辈名下的预约；说“提醒我妈明天带身份证”会落进长辈自己的备忘并标明是谁留的；代约走的是和本人一样的流程，只是确认卡会写明服务对象与代约归属，办完通知其他照护者。家属看不到这位长辈的健康记录明细——那与本次协助无关。

## 四、总体解决方案

### 4.1 一个入口协同七项任务

系统把查询可预约日期、选择复诊时间、生成材料清单、检查日程冲突、生成出发建议、创建复诊提醒和通知指定家属组织为结构化计划。每项任务具有前置条件、状态、结果和失败恢复路径。

### 4.2 对话状态与任务状态分离

新会话默认只是普通交流，不会强迫用户选择医院。只有用户明确表达预约目标或点击开始办理后才创建预约任务。聊天、流程知识查询、材料查询和地图查询可以暂停任务但不会清空进度；用户明确停止当前办理后才取消未提交任务，已有预约记录不受影响。

### 4.3 受控工具调用

模型可以提出查询医院、科室、号源、预约记录、材料、办事流程、路线和院内位置等低风险只读工具，家属和志愿者还多两项协同查询。当前共注册 17 个只读工具，按会话身份过滤后下发给模型——老人本人看不到协同照护端的入口。

Java 程序校验工具白名单、参数、身份、当前阶段和调用次数后才真正执行。这里的过滤只是能力清单，不等于安全：真正的判定发生在执行时，每次调用都会再校验一次，且工具读取的是会话里已核实的用户身份。提交预约、取消已有预约、创建提醒和发送家属通知等写操作不允许模型直接执行，必须经过确认门禁。

### 4.4 院外路线与院内指引

出行能力分为两层。院外路线解决“什么时候出发、怎么到医院”，展示距离、预计用时、建议出发时间和路线步骤；院内指引解决“到医院后去哪里”，展示门诊楼、入口、楼层、诊室、报到点、无障碍路径和护士站。楼层房号来自数据库和工具结果，不由模型编造。

### 4.5 办事知识与医疗知识隔离

系统建立复诊办事知识库，回答预约流程、报到方式、材料准备和不清楚时去哪里咨询。知识库不保存诊断、用药和治疗建议，避免把事务协同扩展成未经验证的医疗服务。

### 4.6 一个智能体，两个端

就诊人端和协同照护端共用同一个智能体、同一套工具和同一道确认门禁，区别只在会话身份。身份被拆成两个独立的轴：能力轴决定“谁能办”（老人本人、家属还是志愿者，能用哪些工具、拿到哪段提示词）；数据轴决定“办谁的数据”（这次会话服务哪位长辈，所有查询和写入都指向他）。两轴在会话建立时由后端按绑定关系核实，未绑定的长辈直接拒绝，之后随会话固化。

这样切分带来两个实际好处。第一，不为家属端另写一套并行流程——代办的预约走的就是本人预约那条链路，因此两端不会出现两套互相打架的规则。第二，越权不可达：操作者身份只用于关系校验和措辞，不进入任何工具参数，工具执行时一律取会话里核实过的用户身份，模型传什么参数都不作数。长辈已有一份进行中的预约时，系统开场就点明，并在代约被拦下时给出“先取消已有预约”的正路，而不是让人一路填到最后一屏才被拒绝。

### 4.7 日常事务：健康数值与长期备忘

不是所有事都属于预约流程，但老人日常真的会提。系统另外承接两类：记录自己量到的血压、血糖、心率等数值，以及设置可重复的长期备忘（每天、每周、每月，或只提醒一次）。

这两类事的处理方式刻意与预约流程不同：模型只负责判断“这句话属于哪件事”，真正拆数值和时间、落库，由 Java 的固定解析器完成。数值解析不出来或明显异常时，系统给中性的追问，而不是含糊地说“已经帮您记好了”。这么分是因为数值和时间一旦被模型改写就是错的，而自然语言的入口又必须保留——把判断和精确解析分开，两边都成立。

家属给长辈留提醒是另一条路径：它落进长辈自己的备忘，标明是谁留的，同时在操作者的协同通知里留一条反向记录。这和老人自己记账本是两件事，提示词里明确区分，避免把家属的嘱托写成老人自己的待办。

## 五、关键机制

### 5.1 明确确认

确认卡展示医院、科室、完整日期和时间、陪同需求、建议出发时间、拟创建提醒、通知对象及可能影响。系统不把“好的”“继续”等模糊表达当作授权。每次确认绑定当前操作快照；用户修改参数或取消任务后，旧确认自动失效。

### 5.2 异常恢复

指定日期无号时只往后查 3 天（不含当天）；用户不接受换日期时提供换医院、重新选日或稍后再查。日程冲突时提供同日其他号源、重新选日或明确保留。修改医院或日期后，系统清除受影响的号源、材料和路线并重新计算。提醒或通知失败时保留已经成功的预约，只补办失败项，避免重复预约。

### 5.3 安全边界

系统不诊断疾病、不推荐药品、不调整剂量、不解读检查报告。明显紧急表达由确定性规则优先拦截，使旧确认失效并暂停普通流程，提示用户及时联系急救服务、身边人员或线下医疗机构。模型输出只是建议，预约成功、具体号源、路线、楼层和诊室均以工具结果为准。

### 5.4 规则回退

模型服务不可用时，规则规划器和回答模板继续支持核心办理路径，避免比赛现场因网络或模型接口异常导致整个演示瘫痪。模型适配通过通用网关配置，更换兼容模型不需要重写业务流程和工具权限。

## 六、适老化方案

界面采用大字号、高对比、较大点击区域和明确文字状态；回复使用短句，一次只提出一个主要问题。用户一次说出多项信息时，系统保存已知字段，不重复询问。进入应用时先选择身份，再进入对应界面：就诊人端首页提供下一次复诊摘要和常用入口，助手页承载对话与持续任务卡，事项页集中展示预约、材料、提醒和家属通知，出行详情页统一展示院外路线与院内指引；协同照护端另有长辈列表、复诊动态时间线和代约流程。

两端的助手页外观刻意保持一致。家属和志愿者用的是同一个助手，如果交互长得不一样，反而会让人误以为能力也不同；差别放在内容上而不是样式上——照护端的快捷提问是“长辈下次复诊是什么时候”“帮我给长辈留个提醒”这类，老人端则是关于他自己的事。

当前适老化判断主要来自需求检查和页面视觉验收，后续需要通过真实老年用户试用验证独立完成率、补问轮次、误触次数、确认内容复述正确率、寻找诊室耗时和人工帮助需求。

## 七、相较普通方案的差异

| 普通方案常见做法 | 本项目的改进 | 带来的价值 |
| --- | --- | --- |
| 固定状态机始终追问下一字段 | 对话状态与任务状态分开，任务可暂停恢复 | 能承接闲聊、情绪和临时问题，不丢办理进度 |
| 大模型只能做意图分类和回复润色 | 模型可规划低风险只读工具，Java 保留写权限 | 比纯状态机自然，比自由工具智能体更可控 |
| 只提供院外地图 | 将路线与楼栋、楼层、诊室、报到点连接 | 把服务延伸到真正找到诊室 |
| 流程知识与医疗问答混在一起 | 办事知识和医疗知识隔离 | 回答“怎么办”有依据，同时守住医疗边界 |
| 演示依赖预写对话 | 模型建议、参数、工具结果和事项记录可关联 | 评委能够核验真实调用过程 |
| 绑定单一模型服务 | 通用适配器加规则回退 | 便于团队更换模型并提高现场稳定性 |
| 家属端另写一套并行流程 | 两个端共用同一个智能体，身份拆成能力轴与数据轴 | 不会出现两套互相打架的规则，能力扩展一次即两端生效 |
| 用提示词叮嘱模型“不要越权” | 越权在会话建立阶段由绑定关系表挡下，工具执行只认会话身份 | 越权不可达，不依赖模型的自觉性 |
| 精确解析也一并交给模型 | 健康数值与时间由 Java 固定解析器处理，模型只判断“属于哪件事” | 数值不会被改写，同时保留自然语言的入口 |

## 八、创新规划

当前已经实现的创新重点是对话任务双状态、受控混合智能体、办事知识隔离、双层到院指引、结果可追溯、模型可替换和规则回退，以及本版新增的双轴会话身份、两端共用一个智能体、机械事务与模型判断分层、过程实时可见、多模态入口、跨对话长期记忆和会话有始有终。

过程实时可见：助手页的「查看办理过程」按轮次显示模型理解、决定查什么、**模型真实生成的工具参数**与工具真实返回，办理结束即收起；跨轮的独立评委视图页仍在规划中。

多模态入口：拍照识图（药品说明书、转诊单、材料照片）、按住说话（松开转写、上滑取消）、逐句朗读与语音气泡原话回放。三者的模型服务都可在没有云端 key 时回落到浏览器原生能力或明确关闭，不影响主流程。

跨对话长期记忆：只记确认办成的事（常去的医院、科室与习惯时段），只由确认门禁那一处写入；用户逐条可见、可忘。记住不等于可以替他办事，写操作仍要过确认门禁。

会话有始有终：会话分办理中、已结束、已超时三种状态并落库；结束的会话可以翻看但不能再写，空闲超时只标记、不丢草稿。刷新页面会恢复上一段会话，想从头开始点「新对话」。

后续规划包括：代办的主动送达，让长辈不必重新开会话就能看到家人替他约好的安排；绑定授权的自助管理，由家人发起、长辈确认，替代目前由模拟数据预置的绑定关系；跨轮评委视图，以时间线回看整场会话的模型模式、权限判断、工具参数和返回结果；真实医院、地图、日历和通知平台适配。

上述规划尚未实现，本方案不把它们表述为已完成成果。它们需要在身份授权、隐私保护和误操作防范机制完成后再纳入正式成果——尤其是代办的主动送达和授权的自助管理，这两项触及真实的触达与授权边界，不能只在演示环境里成立就算完成。

## 九、可行性与当前基础

项目采用前端移动界面、Java 模块化单体后端、可替换模型适配器和 H2 模拟数据库，适合在比赛时间内完成端到端验证。当前已具备多轮会话状态、预约及取消确认、号源与个人预约查询、材料、日程、路线、办事知识、院内位置、健康记录与备忘、协同照护端和工具轨迹等基础能力。

截至 2026年9月11日，开发容器内后端 317 项自动测试全部通过（0 失败、0 错误），前端 TypeScript 检查与生产构建成功，代码规范检查未引入新的命中。真实接口验证表明：普通交流不会自动创建预约任务，明确预约目标后任务才进入办理；查询楼层时可同时产生预约查询、路线规划和院内位置工具轨迹。

协同照护端的验证覆盖了四条关键路径：同一个查询工具换成服务对象后结果随之改变（数据隔离）；为未绑定的长辈开会话返回“没有权限查看这位就诊人的信息”（越权拒绝）；代约成功后预约记录记在操作者名下并在结果卡中标注归属；家属给长辈留的提醒落进长辈自己的备忘并标明是谁留的，同时在操作者的协同通知里留下反向记录。

本版新增能力的验证同样以数据库真实状态为准，而不是看回复文案：会话结束时确认被拒且库里没有产生任何预约、提醒或通知；结束的会话仍可读取，新消息与按钮操作被拒，被拒的那句话不落库；空闲超时后草稿与待确认卡仍在；长期记忆在草稿阶段一个字都不记，确认办成后才记下医院、科室与时段，换一家医院再办会覆盖而不是并存，用户忘掉后该条不再进提示词。

多模态部分，识图在未配置云端 key 时第一步就返回“图片识别功能暂时没有开启”，不落入任何模型调用；语音输入在无后端转写时回落到浏览器识别，仍生成可回放的语音气泡；朗读优先用设备本地音色，没有本地中文音色时才回落云端。

## 十、应用价值与推广路径

对老年用户，统一入口可以降低记忆办理顺序和跨应用切换的负担；对家属，经过授权的结构化通知可以减少反复确认时间地点；对社区、养老服务机构和医院互联网服务，工具化架构能够复用对话状态、确认规则和异常恢复机制，只需替换不同医院、地图、日历和消息平台的适配器。

方案可推广到慢病复诊、术后随访准备、康复治疗预约等流程明确且需要多方协同的事务场景。推广边界仍是行政和事务协同，而不是诊断和治疗。真实部署前需补齐身份认证、角色权限、数据最小化、日志脱敏、保存删除策略以及第三方平台授权。

## 结语

本项目的竞争力不在于叠加最多的功能，而在于把自然交流、真实工具、关键确认、异常恢复、到院指引和安全边界组织成一套可验证、可迁移的复诊事务协同方案。模型获得足够的理解和低风险规划空间，程序保留业务和安全控制权，工具与数据库提供可信结果，从而在“像人一样交流”和“像系统一样可靠”之间取得平衡。

双轴会话身份让这套方案不止服务老人本人。家人和志愿者可以在被授权的范围内替他办事，而越权在会话建立时就已不可达——因此两个端能共用同一个智能体，而不是各自维护一套规则。复诊从来不是老人一个人的事，方案把这一点做进了权限模型里，而不是留给提示词去叮嘱。
