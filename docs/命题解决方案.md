# 银龄复诊事项协同助手

**参赛组别：** 企业命题组 产教协同创新组  
**方案版本：** v0.4（评审修订版）  
**更新日期：** 2026年9月14日

**用一个自然语言入口，协同办理复诊预约、材料准备、出行与家属通知，让每一步有进度、关键操作有确认、办理结果可核验。**

> 当前项目为比赛演示原型。医院、用户、号源、路线、提醒和通知采用模拟数据；预约成功表示模拟业务记录写入成功，不代表真实医院挂号成功或消息已送达真实联系人。本文分别说明已实现能力、待完善事项和推广设想。适老化交互、四类模拟工具、确认与异常处理属于命题要求；本项目的贡献主要体现在这些要求在复诊协同场景中的具体组织与工程实现，不主张通用工程方法本身为原创。

## 一、要解决什么问题

一次复诊涉及的不只是预约。用户还需要确认医院与科室、选择时间、准备材料、核对已有日程、安排出行，并与家属沟通陪同和提醒。对不熟悉数字化操作的老人来说，这些事项意味着要记住办理顺序、在不同页面间传递信息，并判断自己究竟办到了哪一步。

项目围绕三个具体困难展开：

- **需求说不完整。** 老人可能分几次补充医院、日期和陪同意愿，也可能中途改口；系统需要保存已有信息，只追问当前缺失项。
- **办理过程容易中断。** 闲聊、担忧或临时问题会打断原任务；用户回来后需要继续办理，而不是重新填写。
- **多人参与容易混淆。** 家属或志愿者代办时，必须分清谁在操作、替谁办理，以及预约和提醒最终属于谁。

本项目将这些事务组织成一项可暂停、可恢复、可修改并有确认环节的复诊任务。目标是减少用户记忆办理顺序和重复传递信息的负担；实际改善幅度仍需通过目标用户测试验证。

## 二、提供怎样的解决方案

银龄复诊事项协同助手面向老年就诊人及其家属、结对志愿者，提供对话办理与协同查看入口。系统串联号源查询、材料清单、日程冲突检查、出发建议、院内位置指引、提醒和家属通知，并通过任务卡展示当前进度和结果。

就诊人可以自行表达需求，也可以由演示系统中已绑定的照护者协助办理。预约记录归属于就诊人，代办人另行标记，便于双方了解安排来源。健康数值记录和重复备忘是辅助能力，用于保存用户提供的信息与提醒事项，不承担诊断、药品推荐、剂量调整或检查结果解读。

系统采用受控混合架构：**模型理解自然表达并提出查询或流程建议，Java 程序管理任务状态、校验和业务写入，领域工具返回可核验的模拟结果。** 用户看到的预约、提醒和通知状态应以工具结果和数据库记录为依据。

## 三、一次典型办理如何完成

用户说：“我下周三想去市第一医院心内科复诊，上午方便，出发前提醒我，也告诉女儿。”

| 环节 | 系统处理 | 用户看到的内容 |
|---|---|---|
| 理解与补问 | 保存已明确的信息，按流程补齐其他日期接受意愿、陪同等缺失项 | 一次一个主要问题，避免重复填写 |
| 查询与选择 | 查询模拟号源，展示可选时段；无号时提供替代日期或修改入口 | 可选日期、时间及下一步操作 |
| 核对安排 | 检查已有日程，生成材料清单和出发建议 | 冲突说明、材料和路线信息 |
| 确认办理 | 对话流程生成确认卡，展示即将执行的操作及影响 | 医院科室、时间、提醒安排和通知对象 |
| 执行与反馈 | 确认通过后执行预约及相关操作，记录工具结果 | 事项卡及各项办理状态 |
| 后续查看 | 展示预约、材料、院内位置和协同信息 | 可回看的复诊安排及代办归属 |

在支持的对话路径中，用户可以暂停任务、修改需求后重新办理，或在中断后继续。无号、冲突和工具失败需要给出原因与后续选项；若部分操作失败，应展示各项状态，不能仅用一句“办理成功”概括。

上述流程用于说明当前原型的主要能力，不代表所有自然表达、异常组合和设备条件都已完成验收。

## 四、支撑方案的三项关键机制

### 4.1 将自然交流与业务执行分开管理

模型参与需求理解和低风险工具规划，程序管理办理阶段、草稿和确认状态。任务进度与对话状态分开保存，使支持性交流和临时问答不必清空原有办理信息。

模型可见工具区分只读查询与确认交互。只读工具经过校验后执行；确认交互用于进入或响应确认流程，业务写入仍由程序执行。工具清单按会话角色过滤，执行前再进行策略检查。

对话确认卡的关键业务事实由程序依据当前状态或数据库结果生成，确认凭据由程序管理和注入，减少模型改写关键内容或自行提供凭据的风险。但凭据校验不能替代对用户真实意愿的判断，自然语言确认仍需验证否定、犹豫和条件表达等情况。

**当前范围：** 就诊人端与照护端的对话入口复用同一智能体流程；照护端另有独立的表单预约服务。现阶段不宣称全系统所有写入口已统一到同一道会话确认门禁，跨入口确认规则的一致性仍需专项验收。

### 4.2 分清操作者与服务对象

会话分别记录“谁在操作”和“本次服务谁”。前者用于角色能力判断，后者用于定位就诊人的业务数据。代办会话建立时，后端校验演示数据中的绑定关系，未绑定的组合会被拒绝。

这一设计用于减少代办时的数据归属混淆：预约写入长辈名下，代办人通过独立字段记录；照护者留下的提醒进入长辈的备忘，并标明来源。

当前身份机制属于演示体系，绑定关系校验不等于真实用户身份认证。真实部署还需要建立可信登录身份、授权关系及其撤销机制，并校验各接口和会话的访问权限。

### 4.3 让关键输入和办理结果能够核验

对文本健康记录和备忘中的数值、时间，项目使用固定解析器处理支持的表达，降低生成模型改写关键值的风险。例如，“高压130、低压80”可作为明确输入；含糊或异常表达应进入追问。固定解析器有适用范围，不能据此宣称任意口语都能准确理解。

工具调用记录保留模型建议、调用参数和返回结果，办理结果可结合数据库核验。模型不可用时，规则规划器与模板支持核心办理路径；这一回退能力不意味着离线状态与模型模式具有相同的理解范围。更换兼容模型后仍需回归验证。

三项机制共同服务于“说清需求、确认影响、核验结果”。项目的设计价值在于针对复诊任务组织这些机制，而非工具数量或单个通用技术方法。

## 五、当前基础与验证证据

### 5.1 已具备的原型能力

项目采用移动端界面、Java 模块化单体后端、可替换模型适配器，以及以 H2 为主的模拟业务数据。当前具备多轮会话、预约和取消确认、号源与个人预约查询、材料、日程、出行、院内位置、健康记录、备忘、协同照护端和工具轨迹等能力。

业务模拟工具不连接真实医院、地图或通信平台。模型、语音及视觉能力涉及外部服务，药品知识等内容也使用本地文件，因此本方案不使用“全部基于H2”或“零外部依赖”的表述。

### 5.2 已有验证记录及其边界

根据[开发记录](records/PROGRESS.md)，2026年9月12日开发容器内后端完整回归为 **341项通过，0失败、0错误、0跳过**；历史记录另有前端类型检查与生产构建成功的结果。这些是既有开发验证记录，本次文档修订未重新运行测试或构建，也不将测试通过数解释为真实模型准确率或老人使用成功率。

已有用例和记录涉及以下内容：

| 验证方向 | 已有证据关注的问题 |
|---|---|
| 会话生命周期 | 已结束会话可读取，但新消息、按钮操作和确认被拒绝；空闲超时后草稿与待确认内容保留 |
| 长期记忆 | 预约确认完成后沉淀偏好，草稿阶段不提前写入该类记忆；删除后不再用于提示词 |
| 代办关系与归属 | 未绑定组合被拒绝；查询随服务对象变化；预约属于长辈并标记代办人 |
| 协同提醒 | 给长辈留下的提醒写入长辈备忘并标明来源 |
| 办理结果 | 结合预约、提醒和通知记录核验实际写入，而非只检查回复文案 |

上述证据说明特定测试条件下的程序行为，不构成对全部入口、全部表达或真实部署环境的保证。最终提交材料应注明对应代码版本、验证日期和模型配置。

### 5.3 可复现的演示场景

项目为正常办理、指定日期无号、时间冲突和服务越界四类场景提供重置能力。号源与日程使用相对当前日期生成的演示数据，减少固定日期过期导致场景失效的问题。

在种子数据初始化或场景重置后，工作日号源与下周三的社区体检可用于构造冲突，周末无号可用于演示替代日期。重置接口返回相应步骤，便于重复核验。复现依赖正确初始化、场景参数和运行环境，最终录屏前仍需按当前版本执行验收。

### 5.4 尚待闭合的事项

- **紧急处理：** 确定性紧急词表目前主要用于模型不可用时的预检；模型模式依赖紧急意图分类，尚缺统一规则兜底。需要补齐后验证各办理阶段均能优先处理紧急表达，不能以单次演示成功代替修复。
- **确认一致性：** 对话与照护端表单属于不同办理入口，需要逐项核验预约、改期、取消、提醒与通知的确认内容和执行约束。
- **真实身份与授权：** 当前演示身份及绑定关系尚不足以支撑真实服务，需要完善认证、授权撤销、会话访问控制及数据处理机制。
- **适老化效果：** 已采用大字号、较大点击区域和分步补问等设计，但尚无本文可引用的老人独立完成率、误操作率或对比测试数据。

## 六、应用价值与试点路径

### 6.1 预期价值与衡量方式

| 对象 | 预期价值 | 试点时应采集的指标 |
|---|---|---|
| 老年就诊人 | 减少记忆步骤、重复输入和寻找入口的负担 | 独立完成率、完成时间、补问次数、需要协助的次数 |
| 家属与志愿者 | 集中查看安排，减少时间地点和代办归属的反复确认 | 信息核对耗时、遗漏事项、协同误解次数 |
| 社区或服务机构 | 使用统一流程协助复诊准备，并保留可核验的办理记录 | 单次协助耗时、人工接管比例、异常恢复成功率 |

这些指标用于验证价值，当前不填写未经测量的提升比例。测试应记录参与者数字化使用经验、设备和协助条件，并在相同任务下与现有办理方式比较。

### 6.2 建议的推进顺序

**第一阶段：完成演示验收。** 优先补齐紧急处理和跨入口确认问题，整理四场景录屏、关键页面、调用轨迹和数据库结果，使文档与实际行为一致。

**第二阶段：开展小范围辅助试用。** 建议选择一个社区服务点或单一复诊服务场景，在人员协助下测试对话、材料核对和安排查看。先测清哪些步骤可独立完成、哪些需要人工接管，再确定功能调整。当前尚未在本文中提供已落实的试点合作证明。

**第三阶段：逐项接入真实服务。** 在获得平台授权并完成身份与数据处理准备后，接入真实预约、日程或通知能力。业务框架具备复用基础，但接入仍涉及号源规则、状态同步、失败恢复、送达反馈和运营维护，不能简化为只替换适配器。

试点前应明确服务流程和院内位置由谁维护、异常由谁接手、授权如何撤销，以及模型调用、接入和运维费用由谁承担。复诊协同验证成熟后，再评估术后随访准备、康复预约等相邻事务场景，不将跨场景推广写成已完成成果。

## 附录B：实现口径与演示默认参数

截至本版静态核对，领域工具接口为 **15个**；`ToolRegistry` 注册 **17个只读工具与2个确认交互工具，共19个**。其中两项协同查询仅照护角色可见，各角色实际看到的清单不同。接口数量与模型工具数量属于不同统计口径。

| 当前选择 | 适用说明 |
|---|---|
| 无号时查询目标日期之后3天 | 当前实现采用有限的向后窗口；不代表前面的未来日期不可选，也不是最优窗口结论 |
| 冲突时默认展示1个当天候选 | 用于控制单屏信息量；候选数量是否合适需经设备和用户测试 |
| 材料提醒提前1天，出发提醒在建议出发前10分钟 | 演示默认参数，实际应用需考虑预约提前量与用户偏好 |
| 路线耗时外加20分钟取号预留 | 演示出发建议，实际需结合医院流程、交通与行动条件调整 |
| 保留冲突选择时展示已知冲突，不覆盖原日程 | 让用户了解冲突及选择影响，不代表冲突已经解决 |
| 普通医疗越界问答保留办理状态 | 便于之后继续事务；紧急表达应采用优先中断普通流程的规则 |
