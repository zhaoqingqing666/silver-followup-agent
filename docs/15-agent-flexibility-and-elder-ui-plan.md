# 智能体灵活性与老人端界面实施方案（供 DeepSeek 接手）

日期：2026-09-13。状态：建议方案，尚未实施。本文件不代表已实现能力。

## 1. 目标与架构选择

沿用 Java / Spring Boot 模块化单体、React 前端和现有主模型。建设单智能体、受控工具调用、有界多轮执行的架构，不要求引入 LangChain、多智能体或微服务。

用户目标：用自然语言办理预约、批量取消、提醒、记录和家属协作；能理解改口、否定与指代，主动澄清歧义；利用真实历史与偏好减少重复问答；全局麦克风能打开对应页面并讲解。

模型负责语义、工具选择、结构化参数和有依据的表达。Java负责权限、数据检索、时间计算、参数与状态校验、确认记录、事务和调度。枚举可以作为工具协议；不能要求用户说枚举对应的固定口令。

工具执行返回结果后，模型可以继续查询或追问。无需每句话都进行多轮推理，更无需每轮增加独立的“自我反思模型”。真实写入有必要，无限制修改数据库或自动从聊天学习业务规则没有必要。

## 3. 必须统一的消息入口

自然语言（文字、语音转写）进入同一主模型，提供当前页面、当前选中对象、待确认快照、最近对话、必要用户摘要与当前时间。

用户说“还是”“不是这个”“明天再说”时，模型必须有机会理解，不能先被 MEMO_TIME、MEMO_DELETE_CONFIRM 等固定状态分支消费。Java先做身份与必要安全检查，业务状态只作为上下文和执行条件，不替模型解释整句意思。

结构化按钮直接调用相同业务处理器，不必绕模型。模型不可用时允许按钮、清晰追问和有限降级；复杂取消、修改或发送请求不得由关键词猜测执行。降级要有可观察原因。

### 语义与计算的分工

| 业务 | 模型输出 | Java执行 |
| --- | --- | --- |
| 预约/改期 | 条件、日期偏好、目标引用 | 查库匹配、冲突检查、草稿、提交 |
| 取消 | 全部、日期范围、选中对象或不明确 | 查库生成目标快照、确认、批量事务 |
| 提醒 | 内容、时间含义、重复方式 | 日期运算、规则校验、调度和存储 |
| 健康记录 | 项目、数值、单位、测量时间、更正 | 格式与单位检查、异常复核、保存 |
| 家属报告 | 收件人指代、时间范围、内容范围 | 联系人授权、预览、确认与发送 |
| 页面控制 | 打开哪页、哪个对象、院内/院外 | 校验页面白名单和对象归属后导航 |

医院别名检索、数字格式检查等确定性解析保留。删除用中文 contains 判断同意/拒绝的正常模型路径；不要机械删除所有正则。

## 4. 澄清、确认和批量执行

澄清是在问“你指什么”，确认是在问“是否执行这份明确操作”，两者分别建模。

- 建议新增 `interaction.askClarification`（拟议名称）：question、候选引用、可选项；模型写自然问句，真实候选由工具提供。一次只问一个关键问题，支持卡片点选与语音自由回答。
- 模型自身输出的置信度不能单独决定是否执行。目标不唯一、日期矛盾、关键参数缺失或用户表达不明确时追问。
- “之前那个”不能变成全部；“12号”在月份不明时结合真实候选缩小，仍不唯一就问，不偷偷补月份。
- 批量确认保存准确目标集合与版本，卡片正文和口播均根据该集合生成；展示数量与完整可展开明细。不能只确认“所有”，到执行时重新把新预约加入集合。
- 修改取消范围立即使旧确认失效；新范围明确后生成新卡；无法明确时先澄清，不允许旧按钮继续生效。
- 同意、拒绝、修改内容使用独立的结构化决定。重复点击、语音重复回传不能重复执行。
- 确认服务检查凭据、有效期、版本和消费状态；业务执行器校验归属与当前状态。批量取消先整组检查，再在事务中操作；关联提醒等更新需纳入一致性设计。
- 提交预约、取消、删除提醒、发送家属报告按需求执行确认。页面导航和查询无需弹确认。低风险记录是否直接保存沿用需求，不统一扩大成所有操作都弹卡。
- 确认卡继续保留红色危险确认、绿色保留，并保留文字标签、语音说明。危险样式用显式语义字段，不再根据按钮中文包含“取消”判断。

## 5. 多工具循环与工具整理

先复用现有有界只读循环，建议初期最多3次续跑，另设整轮超时和工具调用数量上限；这是待评测调优的配置，不是每轮必须跑满。无依赖查询可并行；查医院后查该医院号源等依赖调用顺序执行。

停止条件：已取得足够信息、需要用户澄清/确认、工具失败不可继续、预算用尽。相同参数查询无新状态时不重复；真正成功的写操作不得作为模型重试动作再次执行。无号可以用真实结果继续查附近日期；失败不能变成“成功”。

工具改造：

1. 增加类型、required、enum、范围约束和未知参数处理，后端使用同一契约校验。模型网关支持原生工具调用时可适配；否则保留现有结构化规划输出，不为此更换框架。
2. 明确结果类型：成功、无结果、需澄清、需确认、状态已变、失败。返回必要事实、候选引用和错误，不返回任意可执行指令。
3. `hospital.search/list`、`department.search/list` 对比返回结构后决定合并；先做兼容别名，避免提示词和旧测试同时失效。
4. 重复预约检查与日程冲突保留为不同业务校验；材料、流程、院内、院外工具职责不同，不强行合并。
5. 取消专用申请工具要明确命名；通用确认服务保存业务动作与执行器引用，业务工具负责构造自己的待确认操作，不让一个通用工具承载全部业务参数。
6. 参数中预约引用可来自服务端签发的候选或当前页面选择；必须校验服务对象归属，不能因为是模型提供就信任。模型不得选择当前用户身份或自行生成确认凭据。

### 现状（2026-09-13 已实施 5B，2026-09-14 审查后简化为结构性规则：查询参数与办理草稿分离）

> **号源那两个工具（`appointment.querySlots` / `appointment.queryNearbySlots`）之外，2026-09-14 的 8A 又把 `appointment.history` 与 `profile.memorySummary` 两条新的只读工具按同一口径建起来并核对过**（见下方「画像与预约历史的受控读取」）。**但这不是「所有 READ_ONLY 工具都已收口」**：`hospital.search` / `hospital.list` / `department.search` 一类目录工具仍可能更新会话里的解析状态，尚未逐项核对。

- **已定死的口径**：通过 `ToolContract` 校验的显式参数必须决定本次查询条件；参数省略时才允许沿用当前会话里已有且明确的条件；显式参数非法、医院/科室不唯一或条件不足时停下澄清，**不得退回旧条件查询后装作回答了本次问题**。不采用「草稿非空就忽略工具参数」的兜底。
- **查询条件与办理草稿分开**：查另一日期或另一家医院，不得连带修改待办理预约或仍有效的确认卡。单工具（`appointment.querySlots`）与多工具（`CALL_READ_TOOLS`）路径共用同一套参数解析与查询口径，判据是工具名取参数，不是各写一份。
- **模型发起的号源查询只查不改（结构性规则，分界是「谁发起的」而非「带了什么参数」）**：`appointment.querySlots` 与 `appointment.queryNearbySlots` 只要由模型发起，一律走只读出口——**`arguments` 为空也一样**，缺的条件回草稿里取（`resolveSlotQuery`），够用就查、不够就追问；不推进阶段、不动 `alternatives` / `selectedSlot` / `acceptAlternative` / 确认卡。只有 `modelDriven()==false` 的按钮/规则流程才走原来的 `showAvailableSlots` / `queryNearbySlots`。`LlmConversationPlanner` 对 `CALL_READ_TOOL(S)` 不再把 `arguments` 当事实来源，工具循环每轮进业务流程前统一过一遍 `withoutDraftWrites(...)`（医院/科室/日期/时间/陪同/通知清空，致谢与情绪照旧）。**不再问「查询条件与草稿冲不冲突」**——草稿为空就保持为空，条件与草稿相同也不写。
- **续跑轮不算新查询**：收口统一走 `finishToolLoopDecision`——只交付上一次真实结果、模型那句回答或兜底说明，**不写草稿、不重进业务流**，**不看 intent 标签**（实测同一句复述的标签在 `QUERY_AVAILABLE_SLOTS` / `CHANGE_DATE` / `CURRENT_FLOW` 之间摇摆）。没有跨轮状态（无 ThreadLocal）。
- **改草稿只有两条路**：模型明确提出业务动作（`PROPOSE_WORKFLOW_ACTION`）的那一轮，以及完全不经过模型的既有按钮/规则流程。老人一句「先查，有号再改」时，本轮先查并问「要按这个来吗」，下一轮明确同意后再改。
- **一次查询不能替老人表态**：查附近日期不再自动置 `state.acceptAlternative`；「查医院 → 查号源」链路第一段（`RESOLVE_HOSPITAL` / `RESOLVE_DEPARTMENT`）同样由 `withoutDraftWrites` 挡住。
- **提示词侧同时收口**：`AgentSystemPrompt` 明确「只读查询条件写对应工具的 arguments；facts 只表示用户明确要求写入或修改办理草稿的事实；只是询问别处时不要同时写进 facts；查询结果不得说成已经预约、已经改期、已经取消」。JSON 规划格式、字段与工具清单不变。**提示词是提醒，不是护栏**，Java 侧这条结构性规则独立成立。
- 验证：`SlotQueryArgumentTests` 17 项、`VoiceFirstP1Tests` 7 项、`AgentRuntimeRoutingTests` 17 项共 41 项全绿；邻近的 `LlmConversationPlannerTests` / `VoiceFirstP0Tests` / `DemoScenarioTests` / `ClarificationFlowTests` / `MultimodalImageTurnTests` / `AgentSystemPromptQueryFactsTests` 共 51 项亦全绿。后端全量在本轮改动前为 497 项全绿，**本轮未重跑全量**。真实模型（deepseek-v4-flash）A/B 见 `records/PROGRESS.md` 同日条目（其中「草稿采纳」那条已按最终规则失效，未重跑）。决定见 DEC-025，踩坑见 `records/PITFALLS.md` 同日三条。
- **仍未完成**：`modelSuggestedReplies` 对 `SELECT_SLOT` / `ASK_DATE` / `ASK_HOSPITAL` 等阶段返回空按钮；目录类只读工具（`hospital.search` / `hospital.list` / `department.search` / `department.list`）的「只查不改」尚未逐项核对（`hospital.search` 仍可能更新会话里的解析状态）；整轮超时与工具调用上限仍是配置项，未实现。

### 画像与预约历史的受控读取（2026-09-14 已实施 8A）

本节对应第 7 节「画像」的落地。两条新工具**都只读、都不带 intent 映射**（参数写坏的调用按 intent 回退时不会落到它们上，宁可回绝也不装作答了）。

- **工具**：`appointment.history`（可按 `hospital` / `department` / `status` / `from` / `to` 过滤，**不含 `limit` 参数**——摆几条由 Java 定，`ProfileQueryService.HISTORY_LIMIT = 5`）；`profile.memorySummary`（无参数，返回明确偏好与预约沉淀分开两摞）。**为什么不在 `appointment.queryMine` 上扩**：它只看 `status='CONFIRMED'`，服务于「要取消哪一条、去哪一家、怎么走」的对象选取，且模型调用它走既有业务流程（读 facts、可能记住被打断的任务）；本轮要的是「这个人的预约历史事实」——带已取消、能按时间范围筛、区分「还没到日子」和「日子已经过了」。两条语义不同，硬扩会改到取消与澄清链路的模型行为上。
- **身份由 Java 注入，模型不得传 `userId`。**`ProfileQueryService.requireReadable(actorUserId, actorRole, subjectUserId)`：代办（`actorRole.isCaregiver() && subject != actor`）必须 `CareService.bound(actor, subject)` 为真，否则抛 `IllegalArgumentException(REFUSED)`；本人只能读本人。**越权与「这个人根本不存在」返回逐字相同的 `REFUSED`**，否则拒绝语本身就成了「库里有没有他」的探针；拒绝时**一条 SQL 都不执行、一条留痕都不落**。
- **四类信息分开，不混成一个「用户偏好」**：当轮要求（草稿里已有的医院/科室/日期/时间，Java 单独一段并标明「优先级最高」）、明确偏好（`MemoryStore` 中 `SOURCE_USER_STATED`）、最近预约事实（`FactStatus` 四值：`CONFIRMED_UPCOMING` / `CONFIRMED_PAST` / `CANCELLED` / `UNKNOWN`）、统计倾向（扫已确认预约聚合出的医院/科室/时段，`confirmedTotal >= 2` 才出，且每一条都标明「是多次记录形成的统计，不是老人明确说过的偏好」）。优先级：当轮要求 > 明确偏好 > 统计倾向。
- **只能说「预约过」**：Java 侧只产出纯事实标签（`已预约，还没到日子` / `已预约，日子已经过了` / `已取消` / `状态未知`），刻意不产出「去过 / 看过 / 就诊过 / 到院」这类词；措辞红线写在 `AgentSystemPrompt`：一条记录不能说「您经常去这家医院」，预约成功不等于已经到院。
- **只读是结构性的**：两条走 `answerReadOnly` —— 不推进阶段、不动 `alternatives` / `selectedSlot`、不改草稿、确认卡原样带回；工具结果不回写草稿，用户下一轮明确说「这次还选它」时才走正常业务动作。
- 验证：新增 `ProfileReadTests` 19 项（覆盖要求的 17 条），后端全量 **517 项 0 失败**。真实模型（deepseek-v4-flash，独立 8099 + 内存 H2）四个场景见 `records/PROGRESS.md`。决定见 DEC-026，遗留风险见 `records/PITFALLS.md`。

## 6. 数据读取范围（目标权限矩阵，不代表现在全部开放）

模型通过受控查询工具读取摘要，不能直接连数据库、执行SQL或任意遍历表。每个查询设置字段白名单、分页、时间范围与返回条数上限。

| 数据 | 允许的目的与范围 | 限制 |
| --- | --- | --- |
| hospitals、departments、appointment_slots、clinic_locations | 启用的医院科室、可用号源、院内位置 | 模拟信息保留模拟标识；无数据不编造 |
| care_guide_articles、material_templates、药品知识数据 | 办事说明、材料、已有药品知识 | 不作为诊断或处方建议 |
| appointments、appointment_materials | 当前服务对象的当前/历史预约和材料进度 | 历史、已取消、未来分别标识；未授权用户不可读 |
| users、user_preferences、user_memories | 称呼、明确偏好、出行方式和必要记忆 | 家庭精确地址仅路线工具需要时使用；默认给模型摘要 |
| user_schedules | 预约时段冲突和可选时段 | 优先给占用区间，不暴露无关日程正文 |
| memos、reminders | 本人的提醒查询和管理 | 仅任务相关内容，状态及时间真实 |
| health_records | 用户要求的指标、时间范围、汇总 | 不默认把完整健康记录放进每轮上下文 |
| family_contacts、family_notifications | 已授权收件人选择、发送状态 | 模型看姓名/关系/引用；发送器解析手机号，不默认暴露完整号码 |
| care_relations、care_notifications | 当前操作者被授权协助的长辈和相关通知 | 操作角色与服务对象双重校验；关系撤销立即生效 |
| conversation_messages、vision_results、附件 | 当前授权会话必要历史、识别结果 | 不跨用户或任意读取附件；不把原始图片默认反复送模型 |
| tool_call_logs、内部会话状态 | 管理诊断和必要本轮执行摘要 | 不开放全表查询；密钥、连接串、内部提示词不开放 |

身份由服务端可靠会话/认证上下文确定；实施时检查现有演示身份机制，不能只信客户端 userId。角色过滤工具可见性之外，执行层必须再次检查资源授权。

## 7. 时间、画像与推荐

### 时间

> **现状（2026-09-13 已实施，本节其余内容保持为设想）**：统一时钟 `application/time/BusinessClock` 已落地，业务时区取配置 `business.time.zone`（默认 `Asia/Shanghai`）；预约、取消、提醒、照护代约、周报、号源与日程播种的「今天/现在」都走它，SQL 里的 `CURRENT_DATE`/`CURRENT_TIME` 换成了绑定参数。审计时间戳（`created_at` 一类）刻意不动，见 `records/DECISIONS.md` 的 DEC-019。本节下方的具体做法与验收点仍然有效，作为后续细化的依据。

注入统一 Clock 和业务 ZoneId（当前项目 Asia/Shanghai），逐步替换业务中的无参 now；测试用固定 Clock。每轮提供 now、today、timezone、weekday，模型不能凭训练时间猜今天。续轮更新真实时间；同轮相对日期按明确的轮次时间锚点解释。

模型输出明确日期或相对日期结构，Java计算并验证；两个表述不一致时拒绝或澄清。保存来源表达，例如“明天”，便于确认复述。测试上海凌晨、跨月、跨年、周日说下周一、只说12号、已过时间。勿因“今天有号”而接受今天已过的时段。

临近午夜才确认时，卡片上的绝对日期不自动移动；业务状态或用户相对日期意图已变化需要重新确认。历史记录时区迁移先核实旧字段语义，不直接把所有时间加八小时。

### 画像

> **现状（2026-09-14 已实施 8A，只读那一半）**：受控读取已落地——`appointment.history` + `profile.memorySummary` 两条只读工具、身份由 Java 注入、`care_relations` 越权拒绝、字段白名单与条数上限、四类信息分开标注。**写入侧没动**：本轮不做偏好保存/修改/忘记，不做完整推荐排序，不自动选医院/科室/号源。本节其余内容仍作为后续细化的依据。**当时记下的两处张力已在同日修复轮里修掉**：`knownFacts` 不再挂 `memoryNote`（默认上下文里不再注入任何未经来源分类的记忆，画像一律经 `profile.memorySummary` 按需读取），`MemoryStore` 的写入措辞改为中性的「最近一次确认预约的医院是 X」并用 `KIND_HISTORY` 标注（`digest` 保留但已降级为「新代码不要用」）。修复轮的三处改动与判断依据见 `records/PROGRESS.md` 与 `records/PITFALLS.md` 的同日条目。详见上一节「画像与预约历史的受控读取」。

复用 MemoryStore，区分：用户明确偏好、最近预约事实、统计倾向、当轮临时要求。给每条来源、时间、可撤销标识；一次预约不能自动说“您一直喜欢这家医院”。用户当前明确要求优先于旧偏好。

查询近期历史再问：“您上次预约的是市第一医院心内科，这次还选这里吗？”当前数据库的 CONFIRMED 只证明预约成功，不证明实际到院，不能说“您上次已经去这家医院复诊”。需要证明到院时须另有就诊事实来源。

推荐只基于用户选定的业务条件、真实号源、距离/交通、日程与可核实偏好，给2—3个选择并解释依据。不根据症状替用户诊断选科，不声称某医院医疗效果更好。距离缺失时不说最近；没有近期可用号源时坦诚说明。

近期事实可按成功业务事件记录；显式“以后都优先上午”可通过受控偏好工具保存并反馈，用户可在“我的”修改/忘记。健康隐私、推测性诊断、随口抱怨不自动写为长期画像。

## 8. 六项老人端界面需求

### 8.1 朗读设置移到“我的”（小）

复用 assistant/tts-settings.tsx，移动展示到 profile/profile-view.tsx；偏好仍由 app/page.tsx 共用并保存，助手、事项、地图使用同一设置。保留保存失败提示。不要复制出第二份语速状态。

### 8.2 精简办理区（小—中）

删除两处重复“继续办理”入口，大卡改为仅办理期间显示的紧凑摘要：

> 当前复诊办理
> 市第一医院 · 心内科 · 2026-09-15

字段未确定时不编造；已暂停可标注“已暂停”，完成后撤下。当前实际需要回答的问题放在对话中。减少顶部常驻示例、重复导航占位，但不一刀切删除确认/拒绝、人工帮助和文字输入：麦克风不可用或老人不便说话时仍能操作。

### 8.3 固定助手页头（小—中）

检查 PageHeader、MobileShell、助手滚动容器的 overflow 与实际滚动祖先，已有 sticky 不等于浏览器中已生效。采用一个明确滚动区域，确保页头固定、消息可滚动；顶部次级栏不重复占太多空间。适配大字模式、手机键盘、480px容器与安全区域，防止固定高度遮挡内容。

### 8.4 预约记录默认三条（小—中）

默认口径建议为“从现在起最近三次已确认、尚未到预约时间的预约”，按预约日期和时刻升序。未来少于三条就展示实际数量，不拿已过期但仍CONFIRMED的记录冒充即将复诊。

提供“展开全部预约记录（N）”和“收起”；历史与已取消在展开后分组展示，很多时分页加载。用户若希望过去记录也参与‘最近’排序，可调整此明确口径。取消成功刷新列表；当前选择失效时更新详情，不能保留已取消预约的出发指引。

### 8.5 全局麦克风与页面控制（中—大）

复用 app/page.tsx 的全局语音与 uiDirective 基础，覆盖记录二级页。自然语言送主模型，同时附 currentPage、selectedAppointmentRef、当前路线模式和会话摘要。页面引用只是上下文，服务端校验后才能使用。

“看看我预约的地图”→选择当前明确预约或查询近期预约→有歧义就问哪次→查询真实路线→后端返回经校验的导航指令与讲解→前端打开地图并播报。同一条消息只发送一次、回复只播报一次，不先切助手再闪去地图。

“医院里面怎么走”复用同一预约打开院内指引；“再说一遍”“说慢点”“看材料”“看看提醒”可逐步支持。用户明确复合意图应先过整体理解，不能靠前端短句词表吞掉后半句。紧急请求不能因同时提到地图就只执行导航。

地图讲解可结尾：“不清楚怎么走可以再问我，也可以联系人工；到了医院，可以问我院内怎么走。”路线和楼层来自工具；模拟路线明确说明，不声称实时导航。拨号或联系人工必须基于实际存在的能力，不能只回复‘已联系’。

只读导航不消费、不清除待确认操作；办理请求、需澄清或需确认时进入助手。切页保留未完成草稿。前端允许的导航目标固定白名单，模型不能任意跳URL或执行脚本。导航未成功不能播报已打开。

增加客户端 turn/request 标识，用户切页、重试、录音重复回调时避免重复请求与旧响应抢导航。麦克风开始录音时停止当前播报；识别失败有可见重试与文字入口。

### 8.6 打开老人端的提示气泡（小—中）

每次新进入老人端应用会话显示一次，内部切页不重复。文案：“我是复诊小助手，有什么问题，长按下面的麦克风告诉我。”气泡指向真实麦克风，不遮挡按钮。点击其他位置或开始录音立即隐藏。

默认气泡可见；自动朗读遵守用户开关与浏览器播放能力，失败时保留可点击朗读，不声称所有浏览器都能无交互自动发声。点击隐藏同时停止提示音；不抢占用户正在输入、录音或重要确认。‘我的’可提供关闭开场提示的偏好。

## 9. 分类与实施顺序

不要一次同时改路由、持久化、所有工具与页面。建议按以下可回滚阶段落地，每阶段独立提交；迁移前检查当前分支与工作区，不覆盖其他人的修改。

1. UI精简：语速、摘要、页头、三条记录、开场提示。先不改变预约写接口。
2. 时间与上下文：统一Clock、页面对象上下文、带来源的画像摘要和权限查询。
3. 工具契约与澄清：强类型参数、明确失败结果；迁移备忘/健康记录中模型前截断和模型后二次中文解析。
4. **确认与执行（2026-09-13 完成 4A 与 4B）**：已提取 `application/ConfirmationService`（凭据生命周期）与 `application/CancellationExecutor`（取消族执行器）。范围修订、批量事务、归属校验、重复确认防重逐条保持不变，取消专项（`CancelScopeTests`）全部保留并扩充。**会话恢复的语义按评审改了**（原来一次批量取消重启后只剩一条目标）：一份授权＝凭据＋动作类型＋完整目标集合，三样一起进 `ConversationState` 与快照、一起清；恢复出来的目标集合与签发时逐条相同，**还原不出完整目标集合的旧快照整份作废、要求重新确认，绝不部分执行**；动作类型在签发时定死，认不出来一律 fail closed。另：`respondConfirmation` 的参数校验已统一到 `ToolContract`，`AgentRuntime.Outcome.acceptedToolCall()` 因名不符实改名为 `hasContractCheckedToolCall()`（见 DEC-022）。
   **4B 已完成（2026-09-13）**：预约办理、备忘、代约取消三条也从 `FollowupAgentService.confirm()` 里搬进了各自的执行器（`BookingExecutor` 129 行 / `MemoExecutor` 96 行 / `ManagedCancelExecutor` 98 行），代他人办理另走 `CaregiverBookingExecutor` 137 行；`ConfirmationDispatcher`（142 行）统一持有并**只按签发时冻结的 `PendingOperation.Kind`** 分派，**六个 `Kind` 各有归口**（本人自办与代他人办理各成一类）、任意 `Kind` 都不会误落到 `BOOKING` 那条路，`caregiving()` 在分派里不再出现。执行器回调编排层走包级私有的抽象类 `ConfirmationSupport`（105 行，**抽象类而非接口**，且按方法参数传给分派器，避免 Spring 循环依赖）。`confirm()` 至此只做统一确认流程，**不再按 `pendingAction`、`appointmentId` 等可变会话字段重推授权类型与范围**。执行器**不复制数据库安全校验**（归属、状态、事务原子性仍由现有业务工具负责），每个只处理一种写操作。用户可见行为逐项保持，`confirmationId` 仍只能消费一次，旧凭据与不可信恢复状态继续 fail closed。后端全量 462 项 0 失败 0 错误（新增分派器 10 项、端到端分派 6 项、代约取消执行器 4 项）。
   **4B 修复轮（2026-09-13，评审驳回后当天完成）**：修的是同一类缝——**卡上写 A、执行却是 B**。① `Kind` 从四个拆成六个，路由判据只剩 `Kind`；② 目标条数在**签发与执行两侧成对**校验，`CANCEL_MANAGED` 与 `CANCEL_APPOINTMENTS_CAREGIVER` 要求**恰好一条**，执行侧 `singleTarget()` 不为一条时返回 `null` 并立即收场，**不静默取第一条**；③ 要取消的对象在签发时冻进 `targetIds`，执行时不再现找「当前预约」，原目标失效就什么都不取消、回「原预约保留」；照护端新增按明确 id 的事务入口 `CareBookingService.cancelAppointment(...)`（`cancelUpcoming` 保留给「取消当前预约」那个既有入口）；④ `ConversationStore.Snapshot` 增加备忘草稿六个字段，`payloadIntact` 在读回与签发两处都判，**旧快照缺草稿时整份作废、请他重说，绝不写残缺内容**；⑤ `MemoExecutor.write` 的写库异常收进统一 `toolError`，不再穿成 HTTP 500，失败后凭据已消费、不重复写库。公开接口与 `AgentTurnResponse` 字段零改动。后端全量 **477 项 0 失败 0 错误**（专项 79 项全绿；新增走真实库的 `MemoConfirmationRecoveryTests` 2 项与走 HTTP 的 `MemoToolFailureTests` 2 项，端到端分派 6 → 11 项、代约取消执行器 4 → 7 项、分派器 10 → 11 项、确认服务 28 → 30 项）。决定见 DEC-024。

## 10. 验收与交付约束

- 按 AGENTS.md 在Dev Container执行依赖、测试和构建；宿主机只编辑与检查。使用vscode身份避免dist属主问题。
- 接口新增字段必须同步后端DTO、前端类型和调用、docs/05-api-contracts.md、records/INTERFACE_CHANGES.md；完成后更新PROGRESS、DECISIONS和实际测试结果。
- 不强制前端重做，不顺带更换数据库、模型厂商、前端框架或实现整套多智能体。
- 自动测试覆盖：改范围后旧卡失效、部分目标状态变化整批不执行、重复确认一次执行、跨用户对象拒绝、模糊指代不默认全部、语音补时间时改口、午夜日期计算、设置共用、记录收起展开。
- 真模型评测使用隔离模拟数据，不操作用户真实预约或发送真实家属通知。至少覆盖预约/无号恢复/批量取消/提醒/健康记录/画像/跨页导航；每类含改口、否定、歧义及不同表达，关键场景多次运行。
- 比较工具选择、参数、真实目标集合、确认版本、数据库最终状态、导航对象；另记录耗时、调用次数和模型用量。不能只按回复自然度判成功，也不能把模拟规划器测试称为真模型评测。
- 真模型未配置或额度不足时完成离线验证，明确列出未验证部分与可直接执行的评测步骤，不声称已验证识别率。
- 前端用手机尺寸和大字模式验证：固定页头、键盘遮挡、麦克风覆盖、提示消失、地图单次讲解。页头问题须以实际滚动验证结案。

改动量判断：五项界面调整属小到中等；全局语音导航属中到大；语义入口、工具契约、确认与分模块拆类整体属较大重构。按上述阶段实施可持续维护，不能按“改几个词表”估算。具体工时由接手人检查分支和可用测试环境后再估计。
