# 创新性与价值评估：银龄复诊事项协同助手

评估及检索日期：2026-09-07。源码基线：`4843f45`，开始评估时工作区干净。需求基线：[Requirement.md](../Requirement.md)。

## 1. 结论

**项目有应用整合和工程实现上的亮点，但目前没有足够证据支持原创算法、全新 Agent 架构或行业首创。** 如果比赛评价应用创新，可以围绕“老人能看懂、能改变主意、失败后能接着办的复诊协同”组织论证；如果要求科研创新，当前工作还缺少明确的新方法、对照实验和用户研究。

最值得保留的主线是：**让老年人在复诊事项的变更和失败过程中，仍能知道已办成什么、还差什么，并保有决定权。** 这是价值假设，现有源码可以支撑部分机制，但尚未证明它确实提高了老年用户的完成率或降低了操作负担。

不能把“符合命题”直接写成“创新”：自然语言/语音输入、多轮补问、七步计划、四类工具、关键确认、异常处理、大字卡片和家属通知，在原始需求中均已有要求。项目的增量主要体现为这些要求的实现深度，不能重复计算为团队提出的新问题。

## 2. 本次如何判断

- 核对需求、设计、进度记录、后端编排/工具/测试与前端助手页面，区分源码事实、历史验证记录和未来建议。
- 检索现有医疗服务产品、Agent 框架官方文档、适老化标准说明和作者公开研究，选取八项资料作为比较依据。
- 判断标准：是否超出命题基线；是否区别于公开已有能力；是否有实现；是否有用户收益证据；是否容易被复制。
- 这是限定范围的公开资料调研，不是系统性文献综述或专利查新。产品介绍只能证明其公开宣称的能力，未实测其内部流程；资料没写某功能，不能推断产品没有该功能。
- 本次只做静态审阅和文档修改，未运行服务、构建或测试。`docs/records/PROGRESS.md` 的“用户资料页数据源修正（容器验收通过）”记录了后端 16/16 测试和前端构建成功，这是历史记录，不是本次重跑结果。`Design.md` 中较早的“待容器验收”不能覆盖这条较新记录。

### 必须保留的实现边界

1. 确认凭据是当前状态的随机令牌，不是数字化计划版本、不可变操作快照或分布式授权账本。旧令牌失效有实现，不宜写成“完整版本化确认协议已实现”。
2. 服务入口使用单实例 `synchronized`；它会串行处理该服务实例的请求，不是多实例并发保证，也没有证明可以在执行中的写操作之间实时插入紧急中断。
3. 业务工具写入与会话保存不是同一事务。会话缓存清空后重载测试不等同于任意崩溃时刻的恢复测试，不能宣称跨服务“恰好一次执行”。
4. 家属通知的 `SENT` 是 H2 模拟记录，没有真实投递、已读、是否陪同的回执，也没有家属侧协同页面。
5. 出行建议按数据库路线耗时加固定 20 分钟余量倒推，没有结合步行能力、陪同者日程、动态交通或多目标优化。
6. 大模型开启时会发送当前上下文和近期对话，不应把“规则回退可运行”宣传成“所有模式均完全本地、所有数据不出端”。

## 5. 价值如何落到用户、比赛和应用场景

**老年用户：潜在价值较高，效果尚未验证。** 问题不只在不会点击，还在流程出错后不知道是否已经预约成功。诚实展示部分完成、保留已办结果、只补办剩余事项，有机会减少反复求助。这个判断受到 S7、S8 所述控制感与故障修复问题的启发，具体效果必须由本项目实验验证。

**家属：目前价值有限。** 指定对象、确认后通知可以减少一部分信息转述，但“通知已写入”不代表有人愿意或能够陪同。缺少回执时，不能证明解决了陪同协调问题。

**社区或医院服务人员：有试点假设，未证明节省成本。** 可以设想用于复诊事务引导和人工接续，但现阶段没有实际接入、服务人员工作台、运营流程或采购意愿证据。若探索应用，先验证每次办结需要多少人工时间，再讨论收费或规模。

**比赛：实现深度具有展示价值，创新论证目前偏弱。** 相对于仅展示固定对话的基础 Demo，数据库副作用、过期确认拒绝、故障补办都更有说服力；相对于成熟产品或研究，没有对照数据就不足以主张领先。未获得比赛评分细则，不能预测得分或获奖概率。

**科研与长期竞争力：当前证据不足。** 没有新的模型训练、算法或实验结果。单纯堆加通用模型、工具数量或多 Agent 名称不会自动增加创新性。更有积累价值的是经过用户验证的交互方法、可复现的异常场景评测，以及真实服务协作经验。

## 6. 建议继续验证的三个方向（均未实现，不作为当前成果）

### 方向 A：面向老人的变更解释与故障补办交互（优先）

**研究问题：** 当用户改日期、改通知对象，或某一步失败时，怎样用最少的重新输入，让用户正确理解影响并完成剩余事项？

在当前确认失效和部分完成机制上增加：可追踪的计划版本、具体操作快照、变更前后差异、受影响的提醒与通知、已经完成且会保留的事项、仅待补办动作的确认卡。根据实际依赖重算受影响步骤，避免无关信息反复询问。数字版本和差异展示本身仍属已有方法，候选创新是其针对老年人理解与恢复负担的设计及验证。

例：老人把上午改为下午。界面明确显示“预约时间改为 14:00；出发提醒随之调整；已发送给女儿的旧消息仍存在，本次将发送变更通知”，然后请用户确认这些具体影响。

最小验证：比较当前完整确认卡与差异/补办卡，测变更理解正确率、错误授权次数、恢复操作数、重复提供字段数。若只是界面更漂亮，理解或完成没有改善，就不把它当成已成立的创新成果。

### 方向 B：可拒绝、可重新协商的家属陪同闭环（第二优先）

**研究问题：** 老人的就诊偏好与家属的可陪同时间冲突时，如何在老人保有最终决定权的情况下形成可执行安排？

增加模拟家属端和有限授权：家属可回应“能陪同 / 不能陪同 / 建议其他时段”，系统区分“已发通知”和“已确认陪同”。冲突时展示候选方案及原因，修改预约仍需老人确认；家属看见的内容限制在协同所需事项。不要把未回信自动解释为同意，也不要默认向其他家属转发。

最小验证：使用“老人—家属”配对任务，比较通知模式与回执协商模式的往返次数、协同完成率、计划理解一致率和未授权修改次数。MyChart 已有代理访问（S3），所以必须证明具体协商流程带来的收益，不能只以“有家属端”为创新。

### 方向 C：把适老出行约束纳入号源选择（第三优先）

**研究问题：** 对复诊事务而言，“有号可约”与“这趟行程实际能完成”如何同时满足？

在模拟数据中增加可接受步行量、无障碍设施、最早可出发时间、家属可陪同时段等用户明确提供的约束。先筛除硬约束不满足的方案，再按用户偏好解释候选取舍；无法同时满足时说明冲突，不擅自放宽约束。保持事务范围，不根据疾病推断身体能力或给出临床建议。

最小验证：构造有可行解和无可行解的已知场景，比较当前时段推荐与约束方案的硬约束违反率、可行方案检出率及解释理解率。多约束排期已有先例（S2），创新仍需落在适老约束设计与实证收益上，而不是声称首次做优化。

## 7. 怎样证明价值，而不是只写“提高效率”

### 工程行为评测

先记录并稳定复现现有行为，再增加异常组合。所有构建、运行和测试必须在 VS Code Dev Container 的 `/workspace` 中执行。

| 场景 | 观察证据 | 判定方法 |
| --- | --- | --- |
| 未确认、过期确认、重复确认、计划变更后旧确认 | 当前卡片/凭据、接口响应、预约/提醒/通知记录 | 未授权业务写入数为 0；重复确认不增加业务记录；不把日志写入计为业务副作用 |
| 预约成功后提醒失败、通知失败、随后补办 | 各步记录、事项卡、故障注入位置 | 成功预约保留；失败状态如实展示；补办不重复成功事项 |
| 改期号源被占用 | 变更前后预约和提醒 | 新方案失败时原预约和原有效提醒仍保留 |
| 会话重载与写入边界故障 | 业务记录与持久化会话状态 | 分别验证正常重载和崩溃窗口；对未覆盖边界明确标注，不混称恢复通过 |
| 确认前紧急输入、取消后旧按钮 | 暂停状态、工具调用和业务记录 | 终态/暂停后旧流程不能新增业务动作；不将其延伸为执行中实时中断保证 |

### 用户体验评测

建议先做小规模可用性试验，例如 8–12 位具有不同手机熟练度的老年参与者。该人数只是第一轮问题发现的排期建议，不能据此声称有统计代表性；正式效果研究应根据试验方差和预期差异另定样本量。

对照设置：A 为同功能的逐页表单/菜单；B 为当前助手；C 为加入方向 A 后的助手。三组使用相同模拟医院、号源和任务信息，安排等价任务并平衡体验顺序，避免熟悉流程造成偏差。B 对 A 检验整合体验，C 对 B 检验新增交互贡献。规则模式和大模型模式分别记录，不能合并掩盖识别失败。

| 指标 | 明确定义 | 对应价值 |
| --- | --- | --- |
| 独立办结率 | 无研究人员实质代操作且正确完成任务的人次 / 总任务人次 | 是否减少数字操作障碍 |
| 确认理解正确率 | 正确复述医院、日期时间、提醒与通知对象/影响的检查项 / 总检查项 | 是否真正保有决定权 |
| 恢复负担 | 从故障出现到正确完成的操作数、重述字段数、耗时 | 方向 A 是否减少重新操作 |
| 人工求助次数 | 任务中需要解释或代操作的次数，分别记录 | 是否可能减少家属/工作人员负担 |
| 状态判断正确率 | 正确判断“已预约/待补办/未通知”等状态的人次比例 | 部分完成提示是否清楚 |
| 技术可靠性 | 每种故障下未授权写入数、重复记录数、恢复成功次数 | 实现是否支持承诺 |

记录失败、放弃、误解和求助，不只统计完成者；时间结果同时给中位数及分布。试验前明确主要指标和成功标准，不事后挑选最好看的数值。使用虚构就诊资料并取得参与者同意；不需要真实病历即可验证事务流程。当前没有实验数据，不填“效率提升 50%”或“满意度 95%”等数字。

## 8. 建议的答辩主张

可以表述为：本项目将老年复诊中的预约、材料、出行、提醒和家属通知组织为可确认的办理流程。现有实现重点处理计划变化和部分失败：旧确认失效，已完成预约保留，未完成事项可再次确认补办，并在事项卡中展示真实模拟状态。下一步通过老年用户对照试验验证，这种设计能否减少误操作和故障后的重复操作。

不宜使用“首创医疗 Agent”“自主研发大模型”“全自动替老人决策”“已实现真实家属陪同闭环”“全场景故障恢复”“显著降低爽约率”。目前可以展示的是模拟事务执行和部分可靠性机制，尚未获得真实用户收益或临床结果证据。

## 9. 后续执行顺序

1. 用已有测试和录屏把“旧确认失效、提醒失败补办、改期失败保留预约”三条证据做完整，记录容器内验证结果。
2. 优先做方向 A 的最小交互原型和用户试验；用结果决定是否继续投入，而不是一次堆叠三个方向。
3. 若试验确认主要困难是协调家属，再做方向 B；若主要困难是行程不可执行，再做方向 C。
4. 新功能涉及接口时，同步前端类型/调用、`docs/05-api-contracts.md`、`docs/records/INTERFACE_CHANGES.md`。本次仅记录研究建议，没有修改业务实现或接口。
